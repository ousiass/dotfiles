# issue-sweep-en

Skill that autonomously implements multiple GitHub Issues back to back. It writes the queue to `.sweep/queue.txt` and, together with the Stop Hook (`hooks/check-issue-queue.sh`), keeps Claude from stopping until the queue is empty.

## Arguments

- `/issue-sweep-en` — no label filter (all open Issues)
- `/issue-sweep-en label:<name>` — filter by label (e.g., `label:sprint-1`)
- `/issue-sweep-en #<n1> #<n2> ...` — specify Issue numbers directly
- `/issue-sweep-en #<parent>` — for a specified **phase Issue** (a parent whose children carry the `split-from:#<parent>` label), auto-expand to its child Issues and process only those. The parent itself is not an implementation target (usable for phase-wide batch implementation)
- `/issue-sweep-en --abort` — abort the running sweep and delete the queue / lock (see below)
- `/issue-sweep-en --parallel <N>` — **number of implementation agents running concurrently**. **Always start with 5** (also the upper limit). Pass 1–4 only to reduce load. Do not ask the user for the value
- `/issue-sweep-en --max-inflight <M>` — upper limit on **unmerged PRs held at once** (implementing + waiting for CI + waiting for merge. **Default 10**, max 15). A separate budget from `--parallel` so CI waits do not eat up implementation slots
- `/issue-sweep-en --no-batch` — disable related-Issue batching (phase 1-4); always process 1 Issue = 1 PR
- `/issue-sweep-en --no-follow-spinoffs` — do not re-sweep Issues spun off during the sweep (zero following; detections are only listed in the report)
- `/issue-sweep-en --max-rounds <N>` — max rounds of spinoff following (**default 1, max 20**). By default only "spinoffs directly produced by this sweep" are processed, for 1 round, and **grandchild spinoffs produced by those spinoffs are not followed** (they fall to the report listing). Pass a larger value explicitly only when you want to drain through grandchildren and beyond autonomously
- `/issue-sweep-en --follow-all-spinoffs` — remove the importance filter for followed targets (see 3-0) and re-sweep every detected spinoff regardless of importance
- `/issue-sweep-en --single-pr` — **single integration-branch mode**. Do not create a PR per batch; stack everything on one integration branch and open only one PR to the base branch at the end (see "single-pr mode" below)
- `/issue-sweep-en --multi-pr` — conventional mode: one PR per batch
- `/issue-sweep-en --base <branch>` — base branch (PR merge target)
- `/issue-sweep-en --branch <name>` — integration branch name for single-pr mode. Default `sweep/issue-sweep-<YYYYmmdd-HHMMSS>`

**If `--single-pr` / `--multi-pr` and `--base` are not specified, always ask with `AskUserQuestion` in phase P-0. Never decide by guessing.**

## Prerequisites

- `gh` CLI is authenticated
- **GNU coreutils** (uses `date -d` / `timeout`). On macOS, `brew install coreutils` and put `gdate` / `gtimeout` on PATH
- `.claude/hooks/check-issue-queue.sh` and `.claude/hooks/check-sweep-state.sh` are executable
- The Stop / SessionStart Hooks in `settings.json` are enabled
- The base branch is **confirmed with the user in phase P-0** (`../sweep-common-en/branch-preflight.md`). Whatever HEAD was at startup, never adopt it as the base by guessing

**Location of `.sweep/` (always set first):** to see the same files as sub-skills running inside worktrees, **always point at the main repository side**:

```bash
SWEEP_DIR="${CLAUDE_PROJECT_DIR:-$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")}/.sweep"
mkdir -p "$SWEEP_DIR"
```

From here on, every `.sweep/...` means `$SWEEP_DIR/...`. The Stop Hook looks at the same path.

**The Bash tool starts a new shell per call**; variables and functions are not carried over. `$base_branch` / `$int_branch` / `assert_not_base` are **re-read every time from `$SWEEP_DIR/prelude.sh` generated by P-0-0** (`../sweep-common-en/branch-preflight.md`). Every bash snippet that uses them starts with these 2 lines:

```bash
SWEEP_DIR="${CLAUDE_PROJECT_DIR:-$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)")}/.sweep"
source "$SWEEP_DIR/prelude.sh"
```

## State management `.sweep/state.json`

Progress-state file shared by sweep-family skills. The Stop Hook (`check-sweep-state.sh`) blocks stopping while `phase != "terminal"` (as long as the lock is fresh). **Never set `phase=terminal` on the guess that "the queue looks empty, so we're done".** Before going terminal, always confirm remaining queue = 0 and spinoff detection is done.

**This file is owned by the sweep.** `refine-git` etc. running inside worktrees refrain from writing via the ownership guard in step 4 of `refine-en/references/common-setup.md`, so nothing can set it terminal from the side while the sweep runs.

**Schema (for issue-sweep):**
```json
{
  "skill": "issue-sweep",
  "started_at": "<ISO8601>",
  "round_started_at": "<ISO8601>",
  "updated_at": "<ISO8601>",
  "phase": "iterating" | "terminal",
  "queue_total": <N>,
  "queue_remaining": <N>,
  "processed_count": <N>,
  "merged_count": <N>,
  "failed_count": <N>,
  "round": <K>,
  "max_rounds": <M>,
  "termination_reason": null | "queue_empty" | "manual_intervention" | "batch_failed" | "aborted"
}
```

**The audit trail is `$SWEEP_DIR/metrics.jsonl` alone.** The `evidence` array that copied metrics line numbers into state.json and the always-null `last_counts` have been removed (the Stop Hook decides only from `phase` and lock freshness; evidence was used for display only).

**Update timing:**
- After queue construction completes in phase 0/1, initialize with `phase=iterating, queue_total, queue_remaining=queue_total, processed_count=0, ...`
- On each batch completion: `queue_remaining -= 1`, `processed_count += 1`, increment `merged_count` or `failed_count`, update `updated_at`
- On spinoff-following round update: `round += 1`, set `round_started_at` to now, set `queue_remaining` to the new queue size
- At the end of phase 3, set `phase=terminal` + `termination_reason`. **Even when aborting on failure, always go terminal and produce the report** (leaving `phase=iterating` leaves no record at all)

## --abort handling

If the argument is `--abort`, run the procedure in `references/abort-and-recovery.md` and exit (do not proceed to other phases).

## single-pr mode (`--single-pr`)

**Do not create a PR per batch; stack everything onto the one integration branch cut at the start, and open only one PR to the base branch at the end.** When enabled, **read `../sweep-common-en/single-branch-mode.md` first**, then enter phase 0. Phase order:

`phase 0 (lock) → P-0 (confirm mode/base) → S-0 (create integration branch) → phase 1 (build queue) → phase 2 (apply S-1 differences) → 3-0 (spinoff judgment) → S-2 (integration polish, final PR, CI check) → S-3 (report)`

The differences from normal mode are only the places below. Everything else stays as is:

| Place | Replacement in single-pr |
|---|---|
| Right after P-0 | Run S-0. Cut the integration branch from the base confirmed in P-0 and push it |
| Presentation at 1-5 | Present `base → integration branch → final 1 PR` instead of "base branch" |
| state.json at 1-6 | Add `mode` / `base_branch` / `int_branch` / `pr_number` / `integrated_count` (S-0-3) |
| PR list fetch at 2-0 | Not needed (no PRs in flight). Only heartbeat and base refresh |
| Idempotency check at 2-1 | Decide by **presence of local branch `<work_branch>`**, not PR. If already integrated (`git merge-base --is-ancestor` true), delete the queue line and go next |
| Agent prompt at 2-2 | Worktree branches from `$int_branch`; **forbid** `gh pr create` and **`/refine-git-en` in step 4** (polish happens once on the integration branch in S-2-0); read the merge gate in step 5 as "tests and lint pass"; reply JSON uses `work_branch` instead of `pr_number` (S-1) |
| Judgment table at 2-3 | Not PR state observation but **agent reply → integration merge**. On conflict: one rebase agent, then give up (S-1) |
| Issue close at 2-4 | Do not close. **The final PR is not merged by the sweep, so Issues are not closed either**. S-3 just lists them as "Issues to close after merge" |
| Completion report at 3-1 | Run S-2 → S-3 before writing the report. The Summary must include mode, base, integration branch, PR URL (**still open**) |

## Phase 0: Duplicate-launch check (acquire lock)

Always run before phase 1. The lock judges staleness by **heartbeat** (PID comparison is not used because it is fragile depending on Bash child-process spawn relations).

1. Check whether `$SWEEP_DIR/lock` exists
2. If it exists: read the content `<owner_pid>:<unix-ts>` and compare `unix-ts` with the current time
   - **Within 2 hours** → another session is running a sweep. Display `echo "他セッションが sweep 実行中（lock の最終更新は <時刻>）。停止するには /issue-sweep-en --abort を実行"` and exit
   - **Over 2 hours** → stale lock; delete with `rm "$SWEEP_DIR/lock"` and continue
3. Write the lock: `echo "$PPID:$(date +%s)" > "$SWEEP_DIR/lock"`
4. **Update the heartbeat** at the start of each round in phase 2 (2-0)
5. Always `rm -f "$SWEEP_DIR/lock"` at the end of phase 3 / on interruption / on `--abort`

## Phase P-0: Confirm mode and base branch (required)

**Read `../sweep-common-en/branch-preflight.md` and execute exactly per its procedure. Cannot be skipped.**
The interview (P-0-2) may be skipped only when both `--single-pr` / `--multi-pr` and `--base` are fixed by arguments.

What is confirmed here:

- `mode` (`single-pr` = one integration branch + one final PR / `multi-pr` = a PR per batch)
- `base_branch` (PR merge target. **Never adopt the current HEAD by guessing**)
- `main_worktree` and the pre-guard function `assert_not_base`

If `mode=single-pr`, continue to S-0; if `multi-pr`, go to phase 1.

## Phase 1: Build the Issue queue

### 1-1. Fetch target Issues

Interpret the arguments and collect targets:

- No arguments: `gh issue list --state open --json number,labels,title --limit 200`
- `label:<name>`: same with `--label <name>`
- `#<n>` list: run `gh issue list --state open --json number,labels,title --limit 200` just once and extract the specified numbers from its result (do not run `gh issue view` per Issue)

**Auto-expansion of parent Issues**: fetch Issues with the `split-from:` label **in a single call** and group them by parent locally (previously `gh issue list --search` was run per Issue):

```bash
gh issue list --state open --search "label:split-from" \
  --json number,labels,title --limit 200
```

- If a `#<n>` in the targets has children in the result above, that parent is **treated as a tracker and excluded from the queue**, and its child Issues are included in the queue
- A `#<n>` without children stays in the queue itself
- This lets `/issue-sweep-en #100` (a phase Issue with 5 children) process "just that phase's 5 items" one after another

### 1-2. Issue analysis (1 Issue = 1 agent = 1 pass)

**Issue bodies are read only here.** Previously the same body was read 3 times: for "dependency / no-parallel judgment", "`issue-split-auto` split judgment", and "scope reading for batching". Have it all returned in one analysis.

Issues with the `bug` label or the `split-from:` label (already-split children) **skip only the split judgment; scope / dependency analysis is still done**.

Launch with `Agent(subagent_type=review, model=sonnet)`. **On Claude Code, explicitly specify `sonnet`** (it only returns JSON, so opus is unnecessary). **On Cursor, do not set `model`** (`harness-model`). **At most 5 concurrently** (a fixed cap independent of `--parallel`). With 6 or more, split into waves of 5 and launch the next wave only after each wave completes.

```
Analyze Issue #<n> and return exactly one line of JSON. Do not implement anything.

1. Split judgment (skip this step if the `bug` / `split-from:` label is present):
   Run `/issue-split-auto #<n>` via the Skill tool; if scopes are mixed, split into child Issues.
   **Do not decide beforehand from surface metrics such as character count or number of H2s** — even a
   short one can mix scopes, and even a long one can be a single feature needing no split. Judge by
   actually reading the body and related specs.
2. For each Issue after splitting (or #<n> itself if not split), read the following from the body:
   - `scope`: the set of target file / directory paths readable from "## スコープ", "## 影響範囲",
     "## ファイル" etc. Empty array if unreadable
   - `depends_on`: numbers in "依存: #N", "blocked by #N", "Depends on #N", "Closes/Fixes #N"
   - `serial_only`: true if any of the following applies
     - `serial-only` / `no-parallel` / `isolated` label
     - the body explicitly says "並列禁止", "sequential only", "do not parallelize", etc.
     - `migration` / `schema-change` / `breaking-change` label
     - the body mentions DB migrations, major dependency-package updates, or changes to config files
       (CI / Lint / package.json etc.)
   - `priority`: the value if there is a `priority:p0` / `p1` etc. label

JSON to return (units has 1 element if not split):
{"parent": <n>, "split": <true|false>, "units": [{"issue": <n>, "scope": ["apps/web/foo/"], "depends_on": [12], "serial_only": false, "priority": "p1"}]}

On failure: {"parent": <n>, "error": "<cause in 1 line>"}

Reply rule: include nothing other than the JSON above in the final message.
```

An Issue for which `error` is returned is not split and is treated as a standalone batch, with `scope` empty and `serial_only` false (analysis failure must not stop the sweep).

### 1-3. Batch formation

Using the `units` returned by 1-2, **the main thread forms groups without reading bodies**. A batch is processed as **1 worktree / 1 branch / 1 PR** and merged together:

- **Units whose `scope` overlaps, or siblings of the same parent, go in the same batch** (implemented in order in the same worktree, so no conflicts)
- **Units whose `scope` is disjoint go in separate batches**
- **A unit with empty `scope` (unreadable) joins the batch of a same-parent sibling if any; with no sibling it is a standalone batch** (err on the conservative side rather than mixing unrelated Issues into one PR through misjudgment)
- A `serial_only` unit is a standalone batch, not mixed with others
- Within a batch, order in a line by following `depends_on`. If circular, split
- Put higher-`priority` batches first, and put a `depends_on` dependency's batch before it

**Parallelism is a result of batch formation.** Same batch = serial (implemented in order in 1 worktree), different batches = parallel. Scope-overlap judgment happens in this one place only and nowhere else.

There is no upper limit on count. However, **only when making a batch of 6 or more**, declare in one line "#a,#b,… の N 件を 1 PR にまとめます（PR が大きくなります）" before proceeding (no confirmation is taken).

### 1-4. Write the queue

Write to `$SWEEP_DIR/queue.txt` with **1 line = 1 batch** (no blank lines or comments). Batches are comma-separated; a standalone one is as is:

```
12,13,14
27
```

At the same time initialize `$SWEEP_DIR/attempts.json` with `{}` (attempt counts per batch; used in 2-7). **Lines are deleted by exact match with `grep -vxF`, so never mix attempt counts or anything else into queue.txt lines.**

### 1-5. Present to the user

1. Show the queue size (number of batches and total Issues) and the breakdown by label
2. Show the `mode` and `base_branch` confirmed in P-0 (plus the integration branch name for single-pr). Do not re-fetch from `git branch --show-current` here
3. Announce in one line "To stop, run `/issue-sweep-en --abort`"

### 1-6. Initialize state.json

```bash
queue_total=$(wc -l < "$SWEEP_DIR/queue.txt" | tr -d ' ')
max_rounds=${max_rounds:-1}   # default when --max-rounds is not specified
jq -n --arg now "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
      --arg mode "$mode" --arg base "$base_branch" --arg int "${int_branch:-}" \
      --argjson qt "$queue_total" --argjson mr "$max_rounds" \
      --argjson par "${parallel_n:-5}" --argjson mi "${max_inflight:-10}" '{
  skill: "issue-sweep",
  started_at: $now, round_started_at: $now, updated_at: $now,
  phase: "iterating",
  mode: $mode, base_branch: $base, int_branch: (if $int == "" then null else $int end),
  queue_total: $qt, queue_remaining: $qt,
  processed_count: 0, merged_count: 0, failed_count: 0,
  parallel: $par, max_inflight: $mi,
  round: 0, max_rounds: $mr,
  termination_reason: null
}' > "$SWEEP_DIR/state.json"
```

**Always carry over the `mode` / `base_branch` / `int_branch` confirmed in P-0 / S-0 here** (this initialization overwrites state.json, so dropping them erases P-0's decisions).

## Phase 2: In-flight pipeline (until the queue is empty)

**Do not create the barrier "N implementations → wait for all CI → N more".** In a project where CI takes 10 minutes, that barrier becomes 10 minutes with 0 implementation agents. Instead, **launch the next batch the moment a slot frees up**.

Budgets are split in two (so neither eats the other):

- `--parallel N` (always 5; 1–4 only to reduce) = **number of implementation agents running concurrently**
- `--max-inflight M` (default 10, max 15) = **number of unmerged PRs held at once** (implementing + waiting for CI + waiting for merge)

Even when CI-waiting PRs pile up, implementation slots still free up, so implementation does not stall.

**Important — context design:** **Implementation of one batch (Develop→Commit→Push→PR creation→polish) is always delegated wholesale to the `Agent` tool.** The main thread does only "queue operations / fetching the PR list / launching agents / judgment / merging / failure handling", and accumulates only PR numbers and states in the main context.

### in-flight table

Held by the main thread across rounds (carried as text in messages; not written to a file):

| Column | Content |
|---|---|
| `batch_line` | The corresponding queue.txt line as is (e.g., `12,13,14`). Exact-match key for queue deletion |
| `issues` | Issue numbers of the batch |
| `branch` | `sweep/issues-<a>-<b>-…` |
| `pr` | PR number (null if not yet created) |
| `stage` | `implementing` / `ci` / `fixing` |
| `ci_respawns` | Number of CI fix agent restarts |
| `zero_check_rounds` | Consecutive rounds in which `checks_total == 0` was observed (used for the no-CI judgment in 2-3) |
| `worktree` | Absolute path of the worktree returned by the agent |
| `start_ts` | Batch start unix time (for metrics) |

### Main loop

Repeat the following once each, top to bottom, until in-flight is 0 and the queue is empty.

#### 2-0. Start of round (heartbeat / refresh base / bulk-fetch PR list)

```bash
source "$SWEEP_DIR/prelude.sh"
echo "$PPID:$(date +%s)" > "$SWEEP_DIR/lock"
git fetch origin "$base_branch" 2>/dev/null || true
git pull --ff-only origin "$base_branch" 2>/dev/null || true

# Get the PR info used in this round with **just one call**.
# Both the idempotency check (2-1) and the state judgment (2-3) use this result.
# Narrow to **only PRs created by the sweep** with `head:sweep/`. Without it, others' PRs and
# dependabot fill the window, and PRs with long CI waits get pushed out of the 100.
gh pr list --search "head:sweep/" --state all --limit 100 \
  --json number,headRefName,state,mergedAt,statusCheckRollup \
  | jq -c '[.[] | {
      pr: .number,
      branch: .headRefName,
      state: .state,
      merged: (.mergedAt != null),
      failed_checks: [.statusCheckRollup[]? | select(.conclusion == "FAILURE") | .name],
      waiting: ([.statusCheckRollup[]? | select(.conclusion == null and .status != "COMPLETED")] | length),
      checks_total: ([.statusCheckRollup[]?] | length)
    }]'
```

If a fast-forward is not possible, only warn and continue. The Stop Hook blocks stopping while queue lines remain, so it keeps flowing without stopping midway.

**Do not run `gh` per PR / per batch.** Previously the idempotency check ran per batch and state observation per PR, so the number of calls per round was proportional to the number in flight. The sweep decides the branch names, so one list fetch resolves everything.

#### 2-1. Refill slots (launch)

If `implementing < parallel` and `in_flight < max_inflight` and **launchable** batches remain in the queue, launch as many as there are free slots.

```bash
head -n20 "$SWEEP_DIR/queue.txt"   # glance at candidates. 1 line = 1 batch
```

Launchability conditions:

- The Issues the batch depends on remain neither in the queue nor in in-flight
- A `serial_only` batch is launched **only when in-flight is 0** (run alone). Conversely, while a `serial_only` batch is in flight, launch nothing else

**Idempotency check** (look for `branch == "sweep/issues-<a>-<b>"` in the PR list fetched in 2-0; make no additional `gh` call):

- `merged == true` → do not launch an agent; go to 2-4 (Issue close) → 2-5 (queue deletion)
- `state == "OPEN"` → an existing PR exists. Skip launching the agent and put it in in-flight with that PR number and `stage=ci`
- Not found → launch in 2-2

#### 2-2. Launch the implementation agent

Call the `Agent` tool with:

- `subagent_type`: `develop` (launch per `harness-model`. Do not use `claude`. On Cursor, do not pass `model`)
- `description`: `"Batch #<a>[,#<b>…] implementation"`
- `prompt`: the **unified prompt** below (the same one is used even for a batch of 1)

**The sweep side always creates exactly one worktree.** Previously it branched as "for 1 item, leave the worktree to the wt-version skill; for 2 or more, the sweep creates it", which split the launch prompt in two and, since "who created the worktree is unclear", required a before/after snapshot diff. Always having the sweep create it eliminates both.

```
Process Issue #<a>[, #<b>, #<c>] **together in one worktree**. Return only JSON to the main thread.

Steps:
1. Create one worktree (do all subsequent work inside this directory):
   git worktree add <repo>-sweep-<a> -b sweep/issues-<a>[-<b>-<c>] <base_branch>

   If creation succeeds, **always** verify before starting work:
   cd <repo>-sweep-<a>
   cur=$(git rev-parse --abbrev-ref HEAD)
   [[ "$cur" != "<base_branch>" && "$cur" != "main" && "$cur" != "develop" ]] || exit 2

   If worktree creation fails, **do not work in the main repository instead**.
   Return {"issues": [...], "failure": "worktree creation failed: <reason>"} and exit immediately.
   Run the same verification once more before the first `git commit`.
2. Process each Issue one at a time, **in dependency order**. For each Issue, check labels with `gh issue view <n> --json labels` and choose the skill.
   **Always add `--auto --no-pr`** (call the Japanese sub-skills here: `/impl-en`, `/bug-fix-en`, `/design-fix-en` do not implement `--auto` / `--no-pr`):
   - bug → `/bug-fix #<n> --auto --no-pr`
   - design → `/design-fix #<n> --auto --no-pr`
   - otherwise → `/impl #<n> --auto --no-pr`
   `--auto` = autonomous mode (do not stop to ask for confirmation / leave Review to the later refine-git /
   lighten Plan for Issues with explicit scope). `--no-pr` = do not create a PR, since the caller creates one.
   **Do not use the wt versions (/impl-wt, /bug-fix-wt)** (the worktree was already created in 1; calling a wt version would create a second one).
   Strictly observe the other forbidden actions of each sub-skill (skipping tests, silent skips, not filing out-of-scope findings as issues).
3. When all Issues are implemented, push and create **exactly one PR** with `gh pr create --base <base_branch>`:
   - Include all Issue numbers in the title
   - List all target Issues in the body, with one line each on what was done for each Issue
   - Link all of them with `gh pr edit <PR number> --add-issue <each Issue URL>` (do not use Closes)
4. Launch `/refine-git-en --no-merge --skip-minor --max-iter 2` via the Skill tool to polish.
   - **`--skip-minor` is required**: the sweep's merge gate does not look at minor. Each minor fix widens the
     diff and grows new minors, so iterating for minor is entirely wasted
   - **`--max-iter 2` is required**: detect and fix in round 1, confirm in round 2. If critical/major still
     remain, judge them as findings that cannot be fixed automatically and hand back to a human
   - **Always use `refine-git-en`, not `refine-en`** (`refine` targets the whole repository; pre-existing
     problems unrelated to the Issue would fail the merge gate permanently)
5. **Merge gate judgment** (required): if the JSON returned by refine-git satisfies
   `critical_remaining == 0 ∧ major_remaining == 0`, **do not run the merge command**; return after
   PR creation (merging is the main thread's responsibility). If not satisfied, return it as a failure.
   Even if `status` is not `clean` (`iter_limit` / `no_progress`), it passes if these two are 0.
6. One-line JSON on success (`skills` is an array in the same order and length as `issues`; use base skill names without the `-en` suffix):
   {"issues": [<a>,<b>,<c>], "pr_number": <N>, "pr_url": "<URL>", "branch": "sweep/issues-<a>", "worktree": "<absolute path of worktree>", "skills": ["impl","bug-fix","impl"], "refine_status": "<clean|iter_limit|no_progress>", "refine_iters": <K>, "critical_remaining": 0, "major_remaining": 0, "minor_remaining": <N>}
7. JSON on failure (**always include which Issue it tripped on**; used for triage):
   {"failure": "<cause in 1 line>", "phase": "<which phase>", "failed_issue": <n>, "completed_issues": [<Issues implemented through completion>], "worktree": "<absolute path if created>", "pr_number": <if any>, "pr_url": "<if any>"}

Reply rules:
- Include nothing other than the JSON above in the final message (the main thread parses it).
- Do not stop with "I'll confirm with the user before moving on" etc. Proceed until failure or completion.
- The main thread does the merge (do not run `gh pr merge`).
- **Never return the success JSON of 6 while critical/major remain** (always pass the gate judgment of 5).
- **Always assign the Issues you start to yourself with `gh issue edit <n> --add-assignee @me`.**
  The sub-skill's phase 1 has this step, but since `--auto` prioritizes not stopping,
  this procedure that does not block the build tends to be dropped. Pass `--issue <n>` to the
  sub-skill and always pass the assignee check of the verification gate (`verify-scope.sh`).
```

Record the returned JSON's `worktree` in the in-flight table (used for cleanup in 2-6).

#### 2-3. Judgment and execution (main thread)

Look up each in-flight PR in the PR list fetched in 2-0, and execute the first row that matches, top to bottom. **Judgment and agent restarts are done here (LLM side). The `Agent` tool cannot be called inside a bash `while` loop.**

| Condition | Action |
|---|---|
| `merged == true` | 2-4 (Issue close) → 2-5 (queue deletion) → 2-6 (worktree cleanup) → remove from in-flight |
| `state == "CLOSED" ∧ merged == false` | Manually closed. If `ci_respawns == 0`, restart via 2-2 (the idempotency check of 2-1 picks up the existing PR). If 1 or more, give up: `sweep_notify "Manual intervention needed"`, remove from in-flight, record `manual_close` in metrics, and delete the line from the queue |
| `failed_checks` non-empty ∧ `waiting == 0` | CI definitively failed. If `ci_respawns >= 2`, give up (below). Otherwise `ci_respawns += 1`, record the attempt with `gh pr comment`, **launch an agent with the CI fix prompt below**, and set `stage=fixing` |
| `checks_total == 0 ∧ zero_check_rounds < 2` | **Do not merge yet.** Right after PR creation, checks may simply not be registered yet. `zero_check_rounds += 1` and go to the next round. If **0 for 2 consecutive rounds**, judge it a "repository without CI" and proceed to the merge in the next row |
| `waiting == 0 ∧ failed_checks empty ∧ state == "OPEN" ∧ (checks_total >= 1 ∨ zero_check_rounds >= 2)` | Run `gh pr merge <PR> --merge --delete-branch`. On success, `merged` is detected next round. On failure, `sweep_notify "merge failed"`, remove from in-flight, and route to user report |
| **PR not found in the list** | Missed. Run `gh pr view <PR> --json state,mergedAt,statusCheckRollup` **for that PR only**, once, and re-judge. If still not found, `sweep_notify "PR lost"`, remove from in-flight, record `pr_lost` in metrics, and delete the queue line |
| Otherwise | CI running. Leave it in in-flight as is |

When giving up on CI:

```bash
gh pr comment "$pr" --body "sweep: CI が 3 回連続で失敗（checks: $failed_checks）。自動修正を諦めユーザー判断を仰ぎます。"
sweep_notify "Manual intervention needed" "PR #${pr}: CI 3回連続失敗 ($failed_checks)" ":rotating_light:"
```

Remove the abandoned PR from in-flight **for that PR only**, record `ci_gave_up` in metrics, and **also delete its line from the queue** (leaving it makes the Stop Hook block stopping forever). Continue processing the other in-flight items.

**CI fix launch prompt** (a batch still has just one PR, so it can be used as is):

```
The following checks failed in CI for PR #<PR number> (branch: <branch>):
- <check name 1>: <summary>
- <check name 2>: <summary>

Task:
1. Switch to the target branch with `git fetch && git checkout <branch>` (reuse an existing worktree if any).
2. Fetch the failed checks' logs with `gh run view --log-failed --job <job-id>` etc. and identify the cause.
3. Push a fix commit. Add tests if needed.
4. Pushing is enough (the main thread watches the CI re-run turn green and merges directly).
5. When done, return:
   {"pr_number": <N>, "fixed": true, "commit": "<sha>"}
   If unfixable:
   {"pr_number": <N>, "failure": "<cause in 1 line>"}

Reply rule: include nothing other than the JSON above in the final message.
```

**Always pass the failed check names.** "Just re-run it" leads to blindly touching things with the cause unknown.

#### 2-4. Close Issues (sweep-only behavior)

After the merge completes, explicitly close **all Issues in the batch** (1 PR closes multiple Issues):

```bash
for n in $batch_issues; do
  gh issue close "$n" --comment "Closed by PR #<PR番号> (merged via /issue-sweep, CI respawns=${ci_respawns})" || true
done
sweep_notify "Merged" "#$(echo $batch_issues | tr ' ' ',') (PR #${PR}, $(( $(date +%s) - start_ts ))s)" ":white_check_mark:"
```

- The parent sub-skills are designed not to use `Closes #N` on purpose, but the sweep wants merge → close tied directly, so the sweep supplements it
- For a child Issue with the `split-from:#<parent>` label, check whether all siblings are closed, and if all are closed, also close the parent with `gh issue close <parent> --comment "All split children merged"`
- Continue queue processing even if the close fails (permissions, already closed, etc.)

#### 2-5. Delete from queue + update state.json

**Run after the Issue close completes, for that batch only** (in-flight completion times are not aligned, so do not delete the first line by fixed assumption):

```bash
grep -vxF "$batch_line" "$SWEEP_DIR/queue.txt" > "$SWEEP_DIR/queue.tmp" \
  && mv "$SWEEP_DIR/queue.tmp" "$SWEEP_DIR/queue.txt"

final_status=$(tail -n1 "$SWEEP_DIR/metrics.jsonl" | jq -r '.status // "merged"')
jq --arg status "$final_status" --arg now "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
   '.queue_remaining = (.queue_remaining - 1)
    | .processed_count = (.processed_count + 1)
    | (if $status == "merged" then .merged_count = (.merged_count + 1) else .failed_count = (.failed_count + 1) end)
    | .updated_at = $now' \
   "$SWEEP_DIR/state.json" > "$SWEEP_DIR/state.json.tmp" \
   && mv "$SWEEP_DIR/state.json.tmp" "$SWEEP_DIR/state.json"
```

#### 2-6. Worktree cleanup

Remove the `worktree` path in the agent's returned JSON as is. It is the single one the sweep had created, so no searching is needed:

```bash
git worktree remove --force "$wt_path" 2>/dev/null || true
```

- **Always** remove it even when the agent returned `failure` (the worktree name would collide when restarting the same batch)
- On success with merge complete, the remote branch is already handled by `--delete-branch`, so remove only the local worktree

#### 2-7. On batch failure (persist attempt counts)

When the agent returns `failure`, record the attempt count **somewhere that can be counted across sessions**. With an in-memory counter, re-establishing the session would retry the same batch forever:

```bash
attempts=$(jq -r --arg b "$batch_line" '.[$b] // 0' "$SWEEP_DIR/attempts.json")
attempts=$((attempts + 1))
jq --arg b "$batch_line" --argjson n "$attempts" '.[$b] = $n' \
   "$SWEEP_DIR/attempts.json" > "$SWEEP_DIR/attempts.tmp" \
   && mv "$SWEEP_DIR/attempts.tmp" "$SWEEP_DIR/attempts.json"
```

- `attempts < 2` → remove from in-flight and leave it in the queue (launched again by 2-1 in the next round)
- `attempts >= 2` → **give up on that batch**:
  - `gh issue comment <n> --body "sweep: 実装失敗（$failure）。2 回試行して通らなかったため手動対応が必要です。"`
  - `sweep_notify "Agent failed" "Issue #${n}: $failure" ":x:"`
  - record `status: agent_failed` in metrics
  - **delete that line from the queue** (leaving it makes the Stop Hook block stopping forever, and the sweep can never finish)
  - **Continue processing the other batches. One batch's failure must not stop the whole sweep**

#### 2-8. Wait

Only when this round made no progress (0 merges, 0 new launches) and in-flight remains, run `sleep 60` and then return to 2-0. If there was progress, go to the next round without waiting (if a slot freed up, refill it immediately).

**Always wait by actually running `sleep 60`. Never end the turn by saying "Waiting."** The Stop Hook pushes back against stopping, so waiting by ending the turn repeats "Waiting." → block → "Waiting." at 2–3 second intervals, consuming one model turn per round trip (measured: 10,000 round trips in one session, 10% of the transcript filled with hook text).

While waiting, the main thread does only `sleep` + `gh` / `jq` and does not "think", so context does not grow, and the Stop Hook watches the queue so it does not stop.

## Forbidden actions

**Do not restate what the body's procedure already says.** Only traps you can still step on while following the procedure are here.

**Branches**

- **Adopting the current HEAD or `develop` as the base branch by guessing** (the user decides the starting point)
- **Implementing in the main repository without creating a worktree** (the main cause of direct commits to the base branch. If creation fails, give up that batch)
- **Automatically fixing a state caught by the pre-guard with `git reset` / `git checkout -f` and continuing** (hand it back to a human)
- Changing the base branch midway

**Queue / merge**

- **Deleting the line from the queue before the PR merge completes** (most important — the root cause of forgotten merges)
- **Forgetting to merge after CI turns green / removing from in-flight without confirming merge completion** (the agent returns after PR creation, so unless the main thread observes, PRs get buried)
- **Closing only some Issues of a batch and removing it from the queue**
- **Appending attempt counts etc. to `queue.txt` lines** (deletion is exact-match `grep -vxF`, so they become undeletable)
- **Counting batch attempts only in the in-flight table (memory)** (re-establishing the session retries the same batch forever)

**Pipeline**

- **Trying to restart an agent inside a bash `while` loop** (bash cannot call the `Agent` tool. That is why state fetching and judgment are separated)
- **Creating the barrier implement → wait for all PRs' CI → implement again** (CI time becomes a gap with 0 implementation agents)
- **Stopping other in-flight items because one PR's CI failed / stopping the whole sweep because one batch failed** (give up only that one)
- **Continuing to wait without detecting CI failure** (cause of infinite waiting)
- **Assuming shell variables (`$base_branch` / `$int_branch` / counters) survive until the next Bash call** (every call is a new shell. Source the prelude and read counters from state.json)
- **Ending the turn to wait when there is nothing to do** (each push-back by the Stop Hook consumes one model turn. When waiting, put `sleep 60` inside a single bash command)

**Delegation to agents**

- **Launching a sub-skill (`/impl` etc.) directly in the main thread via the Skill tool** (root cause of context pollution. Always via `Agent`)
- **The main thread itself fixing code / committing / editing PRs** (the CTO does not touch implementation)
- **Taking anything other than the agent's reply JSON into the main context** (do not leave the agent's internal Plan/Develop logs in main)

**Termination**

- **Not confirming remaining queue = 0 and spinoff detection done before setting `phase=terminal`**
- **Skipping terminalization and report generation when aborting on failure** (leaving `phase=iterating` leaves no record at all)
- **Raising the default of `max_rounds` above 1 on your own judgment** (increase only when the user explicitly specifies)
- **Discarding spinoffs dropped by the importance filter (`spinoff_deferred`) without writing them in the report**
- **Stopping to ask the user for confirmation** ("Follow spinoffs too?", "Proceed to the next round?", "What parallelism?". Proceed with all defaults. The Stop Hook pushes back)

**single-pr mode**

- Proceeding with `--single-pr` without reading `../sweep-common-en/single-branch-mode.md` (do not guess the procedure from the difference table alone)
- **Launching `/refine-git-en` inside an agent** (in single-pr, polish happens once on the integration branch in S-2-0; running it per work unit would detect and fix the same findings as many times as there are units)

## Notifications (`.sweep/notify.url`)

`sweep_notify "<title>" "<msg>" "<emoji>"` is called in various places. **If `.sweep/notify.url` does not exist, notification is a complete no-op**, so if absent you may ignore every call site. Only when it exists, read `../sweep-common-en/notifications.md` and follow its function definition and notification timing table.

## Telemetry (`.sweep/metrics.jsonl`)

On completion / failure of each **batch**, **append one line of JSON** (batch = 1 PR). Aggregable later with `jq`.

**When to write:**
- Normal merge completion (right after the Issue close in 2-4)
- Agent failure (failure behavior in 2-7)
- CI give-up (when the respawn limit is reached)

**Schema:**

`issues` is all Issues of the batch, and `skills` is the corresponding skill names in the same order. When you need the first Issue, use `issues[0]` (previously a backward-compatible `issue` field was held redundantly). **Keep the agent reply's `skills` as the array as is** (collapsing to the first one breaks aggregation of batches mixing `bug-fix` and `impl`).

```json
{"ts":"<ISO8601>","issues":[42],"skills":["impl"],"duration_sec":423,"agent_attempts":1,"ci_respawns":0,"pr_number":127,"pr_url":"https://...","status":"merged"}
{"ts":"<ISO8601>","issues":[12,13,14],"skills":["impl","impl","bug-fix"],"duration_sec":2140,"agent_attempts":1,"ci_respawns":0,"pr_number":129,"pr_url":"https://...","status":"merged"}
{"ts":"<ISO8601>","issues":[51],"skills":["bug-fix"],"duration_sec":1820,"agent_attempts":3,"ci_respawns":2,"pr_number":131,"pr_url":"https://...","status":"ci_gave_up","failed_checks":"unit-tests,lint"}
{"ts":"<ISO8601>","issues":[53],"skills":[],"duration_sec":12,"agent_attempts":1,"ci_respawns":0,"pr_number":null,"pr_url":null,"status":"agent_failed","failure":"<理由>","failed_issue":53}
```

**status values:** `merged` / `ci_gave_up` / `agent_failed` / `aborted` / `manual_close` / `pr_lost` / `branch_guard`

**Implementation:** record `start_ts=$(date +%s)` in the in-flight table at launch in 2-2, and just before 2-4 / 2-7:

```bash
issues=$(printf '%s\n' $batch_issues | jq -sc 'map(tonumber)')   # all Issues of the batch
skills_json=$(echo "$agent_response" | jq -c '.skills // []')     # the agent reply's skills as is
jq -nc \
  --arg ts "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
  --argjson issues "$issues" \
  --argjson skills "$skills_json" \
  --argjson dur "$(( $(date +%s) - start_ts ))" \
  --argjson att "$agent_attempts" \
  --argjson resp "$respawn_count" \
  --argjson pr "$pr_number" \
  --arg url "$pr_url" \
  --arg status "$status" \
  '{ts:$ts,issues:$issues,skills:$skills,duration_sec:$dur,agent_attempts:$att,ci_respawns:$resp,pr_number:$pr,pr_url:$url,status:$status}' \
  >> "$SWEEP_DIR/metrics.jsonl"
```

Aggregation queries are in `references/metrics-queries.md` (used in phase 3-1). The file is `.gitignore`d.

## Phase 3: Completion report and spinoff following

### 3-0. Spinoff detection and re-sweep judgment

Findings made during implementation are filed **after queue construction** by `/spinoff-issue-en --batch` in phase 3 of `impl` / `bug-fix`, so pick them up again:

```bash
source "$SWEEP_DIR/prelude.sh"
# The reference time for spinoff detection is **the start time of the current round** (not the sweep's overall started_at).
# Do not carry it in a shell variable; read it from state.json
since=$(jq -r '.round_started_at' "$SWEEP_DIR/state.json")

# List of parent Issue numbers processed by this sweep (including child Issues expanded in phase 1)
PROCESSED_IDS=$(jq -r --arg since "$since" \
  'select(.ts >= $since and ((.source // "") | startswith("refine") | not))
   | .issues[]' \
  "$SWEEP_DIR/metrics.jsonl" | sort -u | tr '\n' ',' | sed 's/,$//')

# Get OPEN Issues created since the sweep started
new_issues=$(gh issue list --state open \
  --search "created:>=${since}" \
  --json number,title,body,labels --limit 200)

# Decide spinoff origin: use the `spinoff` label assigned by /spinoff-issue as the main signal,
# extract the parent number from the body "元: #N" (spinoff-issue template), "Source: #N" (spinoff-issue-en template) or "Parent: #N" (backward compat),
# and pick those matching PROCESSED_IDS
#   `high` = whether the importance is high enough to auto-run through re-sweep (full implementation cycle)
spinoff_json=$(echo "$new_issues" | jq -c --arg ids "$PROCESSED_IDS" '
  ($ids | split(",") | map(tonumber)) as $parents
  | [ .[]
      | select(([.labels[]?.name] | index("spinoff")) != null)
      | select(
          # scan with a capture returns [["3"]], so flatten before converting to a number
          ( [ .body // "" | scan("(?:元|Source|[Pp]arent):\\s*#?([0-9]+)") ] | flatten | .[0]? | tonumber? ) as $body_parent
          | $body_parent != null and ($parents | index($body_parent)) != null
        )
      | { number,
          high: ([.labels[]?.name]
                 | any(. == "severity:critical" or . == "severity:high" or . == "priority:high")) }
    ]')

# Read counts into an array before counting (using ${#...} on a newline-separated string returns the "character count")
mapfile -t spinoff_all < <(echo "$spinoff_json" | jq -r '.[].number')
# Re-sweep targets are only high-importance ones. With --follow-all-spinoffs, use spinoff_all as is
mapfile -t spinoff_ids      < <(echo "$spinoff_json" | jq -r '.[] | select(.high) | .number')
mapfile -t spinoff_deferred < <(echo "$spinoff_json" | jq -r '.[] | select(.high | not) | .number')
```

Judgment:
- `${#spinoff_all[@]}` is **0** → normal termination (3-1 onward)
- `${#spinoff_ids[@]}` is 1 or more, and `--no-follow-spinoffs` not specified, and `.round < .max_rounds` in state.json (**default 1**):
  - Notify `sweep_notify "spinoffs detected" "${#spinoff_ids[@]} 件を再 sweep" ":arrows_counterclockwise:"`
  - Write a new queue with `printf '%s\n' "${spinoff_ids[@]}" > "$SWEEP_DIR/queue.txt"` (also reset `attempts.json` to `{}`)
  - **Return to phase 2** (carry over lock / notify URL / metrics; advance only `round` and `round_started_at`):
    ```bash
    jq --arg now "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
       '.round = (.round + 1) | .round_started_at = $now | .updated_at = $now' \
       "$SWEEP_DIR/state.json" > "$SWEEP_DIR/state.json.tmp" && mv "$SWEEP_DIR/state.json.tmp" "$SWEEP_DIR/state.json"
    ```
- Limit reached (with the default, you always arrive here the moment you try to enter round 2) or `--no-follow-spinoffs` specified:
  - Add an "unprocessed spinoffs" section to the report and list `"${spinoff_all[@]}"`
  - Notify `sweep_notify "spinoffs left unprocessed" "${#spinoff_all[@]} 件、要手動 sweep" ":warning:"`
- If `${#spinoff_deferred[@]}` is 1 or more, regardless of whether a re-sweep happens, add and list a section **"Untracked spinoffs (excluded by importance filter)"** in the report (do not silently swallow them)

### 3-1. Completion report

1. Summarize the processed Issue numbers and PR URLs in a table (**cumulative across all rounds**)
2. **Aggregate duration and failure breakdown from this sweep's portion of `$SWEEP_DIR/metrics.jsonl` and show it to the user**
3. Confirm the queue file is empty (`wc -l < "$SWEEP_DIR/queue.txt"` is 0)
4. Remove all remaining worktrees with `git worktree prune`
4b. **Set state.json to terminal**:
   ```bash
   # If queue_remaining is not 0 at the time of reaching phase 3, treat as manual_intervention
   remaining=$(jq -r '.queue_remaining // 0' "$SWEEP_DIR/state.json")
   if [[ "$remaining" == "0" ]]; then
     reason="queue_empty"
   else
     reason="manual_intervention"
   fi
   jq --arg reason "$reason" --arg now "$(date -u +%Y-%m-%dT%H:%M:%SZ)" \
      '.phase = "terminal" | .termination_reason = $reason | .updated_at = $now' \
      "$SWEEP_DIR/state.json" > "$SWEEP_DIR/state.json.tmp" && mv "$SWEEP_DIR/state.json.tmp" "$SWEEP_DIR/state.json"
   ```
5. **Generate the Markdown report** — write it to `$SWEEP_DIR/report-sweep-<timestamp>.md`:

```bash
source "$SWEEP_DIR/prelude.sh"
ts=$(date -u +%Y%m%dT%H%M%SZ)
report="$SWEEP_DIR/report-sweep-${ts}.md"
# Counters do not remain in the shell. state.json is the only carrier
eval "$(jq -r '@sh "sweep_start_iso=\(.started_at) processed_count=\(.processed_count) merged_count=\(.merged_count) failed_count=\(.failed_count) mode=\(.mode) base_branch=\(.base_branch) parallel_n=\(.parallel) max_inflight=\(.max_inflight)"' "$SWEEP_DIR/state.json")"
total_dur=$(( $(date +%s) - $(date -d "$sweep_start_iso" +%s) ))
{
  echo "# issue-sweep report — $(date -u +%Y-%m-%dT%H:%M:%SZ)"
  echo
  echo "## Summary"
  echo "- Started: $sweep_start_iso"
  echo "- Processed: $processed_count"
  echo "- Merged: $merged_count"
  echo "- Failed: $failed_count"
  echo "- Elapsed: ${total_dur}s"
  echo "- Base branch: $base_branch"
  echo "- Parallel: $parallel_n (implement) / $max_inflight (in-flight)"
  echo
  echo "## Per-Issue"
  echo
  echo "| Issues | Skill | Duration | Status | PR | Respawns |"
  echo "|---|---|---|---|---|---|"
  jq -r --arg since "$sweep_start_iso" \
    'select(.ts >= $since and ((.source // "") | startswith("refine") | not)) |
     "| \(.issues | map("#\(.)") | join(", ")) | \((.skills // []) | unique | join(", ") | if . == "" then "-" else . end) | \(.duration_sec)s | \(.status) | \(.pr_url // "-") | \(.ci_respawns // 0) |"' \
    "$SWEEP_DIR/metrics.jsonl"
  echo
  echo "## Failures & Manual Intervention"
  jq -r --arg since "$sweep_start_iso" \
    'select(.ts >= $since and ((.source // "") | startswith("refine") | not) and .status != "merged") |
     "- **\(.issues | map("#\(.)") | join(", "))** (\(.status))\(if .failed_issue then " — 転んだのは #\(.failed_issue)" else "" end): \(.failure // .failed_checks // "-") — PR \(.pr_url // "n/a")"' \
    "$SWEEP_DIR/metrics.jsonl"
  if [[ -f "$SWEEP_DIR/refine-metrics.jsonl" ]]; then
    echo
    echo "## Recent refine runs（直近 24h）"
    cutoff=$(date -u -d '24 hours ago' +%Y-%m-%dT%H:%M:%SZ)
    jq -r --arg c "$cutoff" \
      'select(.ts >= $c and (.source | startswith("refine"))) |
       "- [\(.source)] PR #\(.pr_number) iter \(.iter): critical=\(.critical) major=\(.major) minor=\(.minor)"' \
      "$SWEEP_DIR/refine-metrics.jsonl"
  fi
} > "$report"
echo "Report: $report"
```

6. Release the lock with `rm -f "$SWEEP_DIR/lock"`
7. **Completion notification**: `sweep_notify "Sweep done" "${merged_count} merged, ${failed_count} failed (report: ${report})" ":checkered_flag:"`
8. Return the final summary and the **report path** to the user
