# spinoff-issue

`impl` などのスキルで作業中に「これは別 issue に切り出した方がよい」と判断した内容を、Claude 自身がそのまま issue 化するためのスキル。**ユーザー確認なしで作成し、URL を事後報告する**ことを前提とする（暴走防止のためのチェックは下記「自動作成のガード」を厳守）。

## 前提条件

- Claude Code 環境
- `gh` CLI（認証済み）

## 起動契機（impl 等の他スキルから呼ぶ場合）

以下を発見した時に呼び出す。**現スコープに混ぜると PR が肥大化する／要件と独立している作業**が対象。

- スコープ外の追加機能・改善（feat / chore）
- 現スコープと無関係に発見したバグ（bug）
- 現 PR に混ぜると肥大化するリファクタ提案（refactor）
- 仕様書・ドキュメントの矛盾／未記載項目（docs / spec）

呼ぶべきでない例:

- 現在のスコープに含まれる作業（→ 今の PR で対応する）
- 「あとで実装」「TODO」を理由にしたサブステップ省略の言い換え（→ 元スキルのフェーズに戻る）
- 単発の typo や軽微な疑問（→ 直接修正、または無視）

## 引数

Claude が任意の形で渡せる。複合可。

- **バッチ入力** (`--batch <path>`): `impl` / `impl-wt` が書き出した JSONL（1 行 = `{parent, type, title, files, why}`）。**他スキルから呼ばれる場合はこの形式を使う**。1 回の呼び出しで全件を処理し、gh への問い合わせを束ねる（フェーズ0）
- **テキスト**: 切り出したい内容の要約（例: `/spinoff-issue ログイン画面のリトライ処理が未実装`）
- **親 Issue 番号 / URL** (`--parent`): 現作業の元 Issue（例: `--parent #42`）。テキスト起動で親がある場合は必ず渡す
- **引数なし**: 親 Issue が無い独立コンテキストでのみ許容。直近の作業コンテキストから Claude が要約を抽出する

引数なしで impl 等から呼ばれた場合は、直前のレビュー指摘・実装中の発見事項・未解消 TODO 等から **要約・分類・親リンク候補を Claude が組み立てる**。ユーザーへのヒアリングはしない（事後報告方針のため）。**親 Issue が呼び出し元の文脈に存在するのに `--parent` が渡されていない場合は、Claude 自身が文脈から親 Issue 番号を補完してから作成する**。

## 自動作成のガード（必須）

ユーザー確認なしで作成するため、以下を厳守する。1 / 2 に該当した分は**その 1 件をスキップしてフェーズ5 で報告**（ユーザーに確認を取らない）。3 / 4 に該当した場合は **作成中止** し、ユーザーに確認を取る。

1. **重複チェック**: フェーズ0 で取得した既存 Issue 一覧（`--batch` 以外の起動では `gh issue list --state open --search "<要約>"`）と突合し、類似タイトル／本文のものがあれば**その 1 件をスキップ**してフェーズ5 の報告に「重複のため未起票」と載せる（バッチ全体は中止しない）
2. **件数ガード**: 1 回の呼び出しで作成する Issue は **最大 5 件**。超過分は起票せずフェーズ5 の報告に「上限超過のため未起票」として全件列挙する。カウンタは `.sweep/spinoff-count` に持ち、**サブエージェント跨ぎで通算する**（会話コンテキスト上のカウントは agent ごとにリセットされて機能しない）:

   ```bash
   mkdir -p .sweep; [ -f .sweep/spinoff-count ] || echo 0 > .sweep/spinoff-count
   created=$(cat .sweep/spinoff-count)   # 起票のたびに +1 して書き戻す
   ```
3. **スコープ判定の自己チェック**: 「これは現スコープに含まれるのではないか」を一度自問する。境界が曖昧な場合は中止 → ユーザー確認
4. **空内容ガード**: タイトル／本文に具体的な事実（ファイルパス・関数名・再現条件のいずれか）が無い場合は中止し、Claude 自身でコードを再調査して埋めてから作成

## フェーズ0: 入力の正規化と gh 問い合わせの集約（`--batch` 時）

draft を読み込み、**以降のフェーズで使う gh の問い合わせをここで 1 回ずつだけ実行する**（件数ぶん繰り返さない）:

```bash
drafts=$(jq -sc '.' "<batch path>")                                  # 全件を配列化
existing=$(gh issue list --state open --json number,title,labels --limit 300)  # 重複チェック用
labels=$(gh label list --limit 200 --json name -q '.[].name')        # ラベル存在チェック用
```

以降、フェーズ1〜3 を draft の要素ごとにループで処理する。`gh issue list --search` / `gh label list` を要素ごとに呼び直さないこと。

## フェーズ1: コンテキスト抽出と種別判定

1. 切り出し内容の要約を確定する（引数があればそれを起点に、無ければ直近の発見事項から抽出）
2. 関連コードを `Grep` / `Read` で確認し、ファイルパス・関数名を特定（空内容ガード対策）。**`--batch` 時は draft の `files` / `why` が具体的に埋まっていれば再調査しない**（呼び出し元が発見時点で記録済み）
3. 種別を判定する（複数該当時は主たる 1 つを選ぶ）:

   | 種別 | 用途 | type ラベル |
   |------|------|-----------|
   | bug | 動作不具合 | `type:bug` |
   | feat | 新規機能・改善要望 | `type:feat` |
   | chore | 環境構築・ツール整備 | `type:chore` |
   | refactor | 設計変更・技術的負債 | `type:refactor` |
   | docs | ドキュメント修正・仕様矛盾 | `type:docs` |

4. 親 Issue / 元 PR を特定する（impl 中なら `gh pr view --json url,number` または現ブランチに紐付く Issue を探す）

## フェーズ2: タイトル・ラベル・本文の生成

### タイトル形式

`<type>: <要約>` で固定する（CLAUDE.md の commit 規約と整合）。日本語可。

例:
- `feat: ログイン画面にリトライボタンを追加`
- `bug: 注文確認画面で合計金額が二重表示される`
- `refactor: AuthMiddleware を Strategy パターンに整理`
- `docs: API 仕様書の認証エラー表が未更新`

### ラベル（4〜5 種を必ず付与）

1. **`spinoff`** 固定 — 本スキル経由で作成されたものの目印
2. **`type:<種類>`** — フェーズ1 の判定に従う
3. **`area:<領域>`** — kebab-case 英小文字。コード調査で特定したモジュール／ディレクトリ名（例: `area:auth`, `area:checkout`）
4. **`severity:<level>`**（bug の場合のみ）または **`priority:<level>`**（その他）
   - bug の severity は `bug-report` スキルの基準と同一（critical/high/medium/low）
   - その他は priority: `priority:high` / `priority:medium` / `priority:low`
5. **`bug`**（`type:bug` の場合のみ追加） — `bug-report` で作成される bug issue と検索クエリ（`label:bug`）を揃えるため

### ラベル存在チェック（作成前に必ず実行）

`--batch` 時はフェーズ0 の `$labels` を使う。単発起動時のみここで取得する:

```bash
gh label list --limit 200 --json name -q '.[].name'
```

存在しないラベルは **`spinoff` ラベルだけは自動作成可**（無ければ `gh label create spinoff --color BFD4F2 --description "Spun off from another issue/PR"` で作る）。それ以外の不足ラベルは作成中止 → ユーザー承認後に作成。

### 本文

`templates/issue.md` のテンプレートに従う。最低限以下を埋める:

- **背景**: なぜ別 issue にしたか（元の作業 / PR / Issue へのリンクと、混ぜなかった理由）
- **やること**: 1〜3 行で具体的に
- **関連箇所**: ファイルパス（行番号付きが望ましい、例: `src/auth/middleware.ts:42`）
- **受け入れ条件**: 完了判定の箇条書き（feat/refactor）／再現手順と期待動作（bug）
- **親 Issue / 元 PR**: あれば `関連: #<番号>` で明記

## フェーズ3: Issue 作成

```bash
gh issue create \
  --title "<type>: <要約>" \
  --label spinoff \
  --label "type:<種類>" \
  --label "area:<領域>" \
  --label "severity:<level>" `# bug の場合` \
  --label bug              `# type:bug の場合のみ追加` \
  --body-file <一時ファイル>
# 非 bug の場合は --label "severity:<level>" の代わりに --label "priority:<level>"
# bug 以外では --label bug は付けない
```

作成成功後、URL を保持する。

## フェーズ4: 親 Issue / 元 PR への関連付け

該当する場合のみ実行する。

1. **親 Issue がある場合**: 親 Issue 本文末尾の `## 派生 issue` セクションに `- [ ] #<新番号> <タイトル>` を追記
   - 既存セクションがあれば末尾に追加。無ければ新設
   - `gh issue view <親番号> --json body -q .body` → 一時ファイルに書き出し → 編集 → `gh issue edit <親番号> --body-file <一時>` → 一時ファイル削除
   - **`--batch` 時は親番号ごとに 1 回にまとめる**（同じ親にぶら下がる子を全部集めてから read-modify-write を 1 回実行する。子ごとに親を編集し直さない）
2. **元 PR がある場合**: PR 本文末尾に `関連 spinoff: #<新番号>` を追記（`gh pr edit` を使用）
3. **新 Issue 側からも親へリンク**: 本文の「関連」欄に `元: #<親> / PR: #<PR番号>` を必ず含める（フェーズ2 の本文生成時に組み込み済みのはず）

## フェーズ5: 事後報告

ユーザーに以下を 1 度だけ報告する。確認は求めない（既に作成済み）:

```
spinoff issue を作成しました:
- #<番号> <タイトル>
- URL: <issue URL>
- ラベル: spinoff, type:<種類>, area:<領域>, ...
- 親: #<親番号>（リンク追加済み）／PR: #<PR番号>（リンク追加済み）
```

複数作成した場合はリストで一括報告。**重複・上限超過でスキップした分は「未起票」として理由付きで必ず列挙する**（黙って落とさない）:

```
未起票（重複 2 件 / 上限超過 3 件）:
- <タイトル> — 既存 #<番号> と重複
- <タイトル> — 1 回あたり 5 件の上限超過
```

元のスキル（impl 等）の作業フローには戻り、現スコープを継続する。

## ルール

- **ユーザー確認は原則取らない**。「自動作成のガード」に該当した時のみ `AskUserQuestion` で確認する
- 作成件数の上限は「自動作成のガード」2 に従う（`.sweep/spinoff-count` で通算 5 件）。超過分は**ユーザーに確認せず未起票として報告する**（確認待ちで止まるより、列挙して判断を委ねる方が安い）
- タイトル・ラベルは `bug-report` および CLAUDE.md commit 規約と整合させる
- 元の Issue／PR 本文を改変するのは「派生 issue」セクションの追記のみ
- コードは修正しない。成果物は Issue のみ
- 報告フォーマットは固定（呼び出し元スキルが結果を機械的に扱えるように）
