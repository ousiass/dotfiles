# impl-report（上長への実装後報告メッセージ生成）

**実装・PR を終えた後、上長/PM に共有・追認依頼すべきことを棚卸しし、送信用の報告メッセージを生成する。**
特に「仕様書・Issue に明記がなく自分で判断した点（＝認識がズレうる追認ポイント）」を取りこぼさず拾うことが主眼。

経緯を時系列で起こす `code-flow-hurikaeri` とは別物。本スキルは「上長が知るべき意思決定・追認ポイント」だけに絞り、送信用トーンに整える。

## 前提条件

- Claude Code 環境
- `git`, `gh` CLI（差分・PR・Issue の取得に使用。なくてもセッション文脈から作成可）

## 引数

- **引数なし**: 現在のブランチ/セッションの作業を対象
- **PR番号 / ブランチ**: その対象を解析（例: `/impl-report #234`）
- **テキスト**: 補足指示（宛先・強調したい点など）として扱う

## フェーズ1: 作業内容の解析

1. 現在のブランチ・PR・差分を把握する（`gh pr view`、`git log` / `git diff <base>...HEAD`）
2. このセッションの impl / review / doc-drift 等の結果と会話文脈から、実施した作業・判断・作成物を拾う
3. ベースブランチ・PR番号・関連 Issue 番号を控える（メッセージに焼き込む）

## フェーズ2: 報告事項の棚卸し

3カテゴリに分類する。**推測で項目を作らない。実際の差分・Issue・コミット・会話で裏付ける。**

| カテゴリ | 中身 | 優先度 |
|---|---|---|
| **追認ポイント** | 仕様書・Issue に明記がなく自分で判断した点。特に上長の認識とズレうるもの・解釈を広げたもの | 最優先（冒頭に置く） |
| **新規作成Issue** | このセッションで切り出した Issue（spinoff 含む）。番号・要約・親リンク | 中 |
| **保留した改善点** | 指摘したが未対応・別Issue化候補として残したもの | 低 |

- 各カテゴリで該当が無ければ「なし」と判断し、メッセージから省く（無理に埋めない）。
- 追認ポイントは「何を・なぜそう判断したか（仕様のどこに合わせたか）」を1行で添える。

## フェーズ3: 宛先・目的・範囲の確認

`AskUserQuestion` で確認する（テキストだけで聞かない）。最大4問:

1. **宛先**: 誰へ送るか（トーン決定。社内上長／社外・発注元 PM 等。宛先が不明なら必ず確認）
2. **目的**: 共有のみ ／ 共有＋一部追認依頼 ／ レビュー・承認依頼
3. **含める範囲**: 追認ポイントのみ ／ ＋新規Issue ／ 全カテゴリ
4. **長さ**: 標準（要確認＋参考＋Issue）／ 短縮（要確認だけ）／ 詳細（背景付き）

## フェーズ4: メッセージ生成

**箇条書き主体・一目で要点が伝わる形にする。** 前置きや経緯は書かない。

構成:

1. 冒頭1行: 何を実装し、どの PR にあげたか（PR / Issue 番号入り）。例:「○○（#NNN）を PR #MMM にあげました。」状態（緑化・マージ可否など）は書かない。
2. ラベル見出しでカテゴリを区切る。`【要確認】` は必須。`【新規Issue】` / `【保留】` は該当があれば付ける（無ければ出さない）:
   - `【要確認】` 追認ポイント。番号付き箇条書き。各行は **結論を先頭** に、**できるだけ短く1行**に収める。理由が要るときだけ括弧で短く1句。
   - `【新規Issue】` 切り出した Issue を1行ずつ（番号＋ごく短い要約）。
   - `【保留】` 未対応・別対応にした点を1行ずつ（ごく短く）。
   - `【参考】`（既存実装・仕様に準拠した判断）は **書かない**。報告価値が低く冗長になるため。
3. 締め1行: 「ご確認お願いします」等を簡潔に。確認してほしい番号があれば添える。

### 可読性ルール（必須・このスキルの肝）

- **各行はできるだけ短く。** 1行に収め、長ければ削る。
- **1行1論点。** 接続詞で複数の判断を1文に詰めない。
- **結論ファースト。** 背景・経緯・「〜という想定からの変更です」等のメタ説明は書かない（理由が要るなら結論の後に短く1句だけ）。
- **括弧の入れ子は禁止。** 括弧は1階層・1項目まで。
- 専門用語は宛先のレベルにかみ砕く。仕様番号（§x.x）は根拠として残してよい。

生成後、**さらに短い版・背景付きの詳細版も出せる**ことを一言添える。**送信はしない**（ドラフト提示のみ。送信はユーザーが行う）。

## フェーズ5: 日報ラフへの記録（Yes/No）

報告メッセージを提示した **後**、この作業を VeriCerts 日報ラフに記録するかを `AskUserQuestion` で確認する。**Yes / No の2択**（テキストで聞かない）。

- 質問例: 「この実装（#NNN → PR #MMM）を VeriCerts 日報ラフに記録しますか？」
- 記録の実体は **`veri-nippo-rough`（L0）に委譲する**（自前でラフに書かない）。impl-report は記録項目を整形して渡すだけ。

**Yes の場合:**

1. フェーズ1で把握した作業を、1〜数行の **事実** に整形する。Issue/PR 番号を必ず含める。
   - 例: 「#163 エラーハンドリングを改修し PR #234 を作成」
2. 整形した項目を `veri-nippo-rough` に渡し、当日ラフ（`02_日報/ラフ/YYYY-MM-DD.md`）の「稼働内容（下書き）」へ追記させる。
3. 脚色・解釈はしない。追認ポイントや感想は混ぜない（事実だけ）。
4. 追記したパスと内容を一言報告する（veri-nippo-rough の報告で足りる）。

**No の場合:** 記録せず終了。

- VeriCerts と無関係な案件で impl-report を使ったときは **No** を選べばよい（記録先は VeriCerts 専用フォルダに固定）。

## トーン規約

- **箇条書き主体で、一目で要点が伝わる形にする**（文章の作り込みはフェーズ4の可読性ルールに従う）。
- 丁寧めの汎用ビジネストーン（宛先が社外でも失礼にならない水準）。
- PR番号・Issue番号は必ず含める。
- 絵文字は控えめ（宛先がカジュアルな社内と確定した場合のみ可）。

## 模範例（構成・トーンの見本。内容は案件依存）

```
お疲れさまです。勤怠一覧のステータスフィルタ（#227）を PR #234 にあげました。

【要確認】仕様にない判断
1. 複数フィルタ同時ON = AND（全条件を満たす行のみ）
2. 「未ロックのみ」= 日次・月次とも未ロック（§7.6 準拠）

【新規Issue】#233 無関係なツール警告を切り出し

1・2 をご確認ください。
```

短縮版・承認依頼版・進捗共有版などのバリエーションは `references/examples.md` を参照。

## ルール

- セッションの会話文脈を最優先で参照する（直近の impl/review 結果に判断・Issue が含まれる）。
- 推測で「判断した」と書かない。差分・Issue・コミットで裏付ける。
- 追認ポイントを取りこぼさない（このスキルの最大の価値）。
- `AskUserQuestion` で宛先・目的を確認。宛先のトーンが不明なまま生成しない。
- 送信はしない。ドラフトを提示し、ユーザーが送る。
