# spec-refine

`spec-review` の3観点（整合性・コード乖離・品質）を観点ごとの並列サブエージェントでレビューし、「並列レビュー → 指摘を1件ずつ確認して修正 → 再レビュー」を有効な指摘が出なくなるまで繰り返す。1回で終わる `spec-review` に対し、収束するまで自動で周回し続けたい場合に使う。

## 対応関係

| スキル | ループ | レビューの実行者 | 修正の実行者 |
|---|---|---|---|
| `spec-review` | なし（1周のみ） | メインスレッド自身 | メインスレッド自身 |
| **spec-refine**（本スキル） | 指摘ゼロに収束するまで反復 | 観点ごとの並列サブエージェント（`review`） | メインスレッド（自動修正はask不要、内容矛盾/内容修正のみ `AskUserQuestion` で1件ずつ確認） |

## 前提条件

- Claude Code 環境
- spec-gen 形式の仕様書（docs/ または spec/ ディレクトリ）
- git

## 引数

- 引数なし: 自動検出した仕様書を対象に実行
- パス指定: 指定ディレクトリの仕様書を対象
- `--max-iter <N>`: 反復上限（デフォルト 8）
- `--scope <diff|full>`: 2周目以降のレビュー範囲。`diff`=差分のみ、`full`=毎回全体（未指定ならフェーズ1-3で選択式確認）

## フェーズ1: セットアップ

### 1-1. 仕様書の検出

`spec-review` フェーズ1-1 と同じ手順。引数でパスが指定されていればそのまま使用。指定がなければ以下のパターンで Glob 検索する:

```
**/spec/**/*.md
**/specs/**/*.md
**/docs/**/*.md
**/specifications/**/*.md
**/design/**/*.md
```

見つからなければ `AskUserQuestion` でパスを確認する。

### 1-2. 全仕様書の読み込み

検出した仕様書をすべて Read で読み込む。

### 1-3. スコープモード選択

引数で `--scope diff` / `--scope full` が指定されていなければ `AskUserQuestion` で確認:

```
質問: 2周目以降のレビュー範囲は？
選択肢:
1. 差分のみ — 変更したファイル・未解決指摘があるファイルのみ再レビュー（高速。他ファイルへの副作用は見落としうる）
2. 毎回全体 — 全仕様書を毎周レビュー（時間はかかるが見落としが少ない）
```

`scope_mode` = `"diff"` または `"full"`

### 1-4. 変数初期化

- `iter = 0`
- `max_iter` = 引数指定値、なければ 8
- `skip_list = []`（`{file, summary}` の配列。ユーザーが「スキップ」を選んだ指摘を記録し、以降の周でレビューエージェントに除外させる）
- `stall_count = 0`
- `prev_total = null`（前周の有効指摘件数）
- `review_scope` = 全仕様書（1周目は `scope_mode` に関わらず全体）

### 1-5. 進捗管理の初期化

`TaskCreate` で「レビュー反復」「完了レポート」の2フェーズを登録する。反復回数は事前に確定しないため、反復ごとに `TaskUpdate` で進捗を更新する。

## フェーズ2: レビュー→修正ループ

### 2-1. 並列レビュー起動（観点別）

`harness-model` に従い（`subagent_type: review`。`claude` は使わない）、3体を**同一メッセージで並列**起動する。各エージェントは `review_scope` の仕様書のみを読み、担当観点の指摘だけを検出して JSON で返す。プロンプトには `skip_list` を渡し「以下はユーザーが対応不要と判断済みなので再指摘しないこと」と明示する。

観点定義（`spec-review` と同一）:

| 観点 | 検証内容 |
|---|---|
| **整合性** | 機能要件↔API仕様、機能要件↔コンポーネント設計、ER図↔API仕様、ER図↔機能要件、アーキテクチャ↔非機能要件、コンポーネント↔API仕様のクロスリファレンス矛盾 |
| **コード乖離** | API仕様↔ルーティング/ハンドラ、ER図↔マイグレーション/モデル、コンポーネント設計↔実装コンポーネント、アーキテクチャ↔ディレクトリ構成のズレ（コードが無ければスキップしその旨を返す） |
| **品質** | Mermaid図の欠落/構文エラー、改訂履歴の未更新、記述の曖昧さ（「適宜」「必要に応じて」等）、テーブル/見出し構造の崩れ、ドキュメント間リンク切れ |

各指摘には `category`（`"auto"` / `"confirm"`）を付与させる（`spec-review` フェーズ3と同一基準）:

| 観点 | category の判定 |
|---|---|
| 整合性 | 常に `"confirm"`（仕様書間の実質的な矛盾は必ず判断が要るため） |
| コード乖離 | 常に `"confirm"`（実装に合わせた記述内容の変更は内容修正にあたるため） |
| 品質 | 見出し/箇条書き番号のズレ、テーブル罫線・インデント等の体裁崩れ、Mermaid構文エラー修正（意味を変えない）、改訂履歴の日付/バージョンの機械的更新、見出しレベルの一貫性 → `"auto"`。記述の曖昧さの解消・必須セクションの欠落・参照先変更を伴うリンク修正など意味が変わるもの → `"confirm"` |

```
Agent({
  description: "spec-refine iter <iter+1> — 整合性",
  subagent_type: "review",
  prompt: """
仕様書レビュー観点「整合性」を担当。対象: <review_scope のファイル一覧>
[上表の「整合性」検証内容をそのまま埋め込む]

以下はユーザーがスキップ済みなので再指摘しないこと:
<skip_list を file+summary で列挙>

指摘は JSON 1行で最終メッセージとして返す:
{"source":"整合性","findings":[{"file":"...","severity":"high|medium|low","category":"confirm","desc":"...","excerpt":"...","suggestion":"..."}]}
指摘が無ければ findings: [] を返す。「整合性」観点の category は常に "confirm" とする。
"""
})

Agent({ description: "spec-refine iter <iter+1> — コード乖離", subagent_type: "review", prompt: ... "source": "コード乖離", category は常に "confirm" で返す })
Agent({ description: "spec-refine iter <iter+1> — 品質", subagent_type: "review", prompt: ... "source": "品質" で返す。上表の振り分け基準に従い指摘ごとに category を "auto"/"confirm" で判定させる })
```

3体を同一メッセージで並列起動する。

### 2-2. 集約・分類

3エージェントの JSON をマージする。同一 `file` + 実質同一内容の指摘は1件に統合する。`skip_list` に一致するものは除外する。`category` で `auto_findings` と `confirm_findings` に分割する。振り分けに迷う指摘、またはメインスレッドが見て意味が変わると判断した指摘は `confirm_findings` 側に倒す。severity 高→低、ファイル単位でグルーピングして並べる。

### 2-3. 自動修正の適用（確認不要）

`auto_findings` をファイル単位でループし、確認なしで適用する（`spec-review` フェーズ4と同一手順）:

1. 対象ファイルの自動修正指摘をすべて Edit で適用
2. 同じファイルの改訂履歴を1回だけ更新（そのファイルで自動修正した件数・内容をまとめて記載）
3. `git add <対象ファイル>`
4. `git commit`（例: `docs: <対象ファイル> の体裁・表記ズレを自動修正`）

複数ファイルにまたがる場合はファイルごとに1〜4を繰り返す（1ファイル=1コミット）。適用後、同じファイルへの後続 Edit（2-5 での対話確認修正）の前には必ず再 Read してタグを取り直す。

`confirm_findings` の件数を `valid_total` とする（終了判定に `auto_findings` は含めない。この周ですでに自動修正済みのため）。

### 2-4. 終了判定

```
if valid_total == 0:
  → converged, フェーズ3 へ
if prev_total != null && valid_total > 0 && valid_total >= prev_total:
  stall_count += 1
  if stall_count >= 2:
    → no_progress, フェーズ3 へ（残指摘ありで終了）
else:
  stall_count = 0
if iter >= max_iter:
  → iter_limit, フェーズ3 へ（残指摘ありで終了）
otherwise:
  → 2-5 へ
```

`prev_total = valid_total` を更新してから 2-5 に進む。

### 2-5. 対話確認が必要な指摘の提示と修正（`spec-review` フェーズ5を流用）

`confirm_findings` を **1件ずつ** `AskUserQuestion` で提示する。提示形式・選択肢・修正適用・コミット手順は `spec-review` フェーズ5と同一:

```
質問: [観点名] 指摘 N/全M件 — [対象ファイル名]
[指摘内容の説明][該当箇所の引用（あれば）][修正案の概要]
選択肢:
1. 修正する — 提案どおりに修正を適用
2. 修正内容を変更する — 修正方針を指定してから適用
3. スキップ — この指摘は対応しない
4. 残りをすべて修正 — 以降の指摘をすべて提案どおりに修正
5. レビュー終了 — 残りの指摘を破棄して終了
```

- 「修正する」/「残りをすべて修正」: Edit で本文を修正 → 同じファイルの改訂履歴を更新 → `git add <対象ファイル>`（`-A`/`.` は使わない）→ `git commit`（1件ごと）
- 「修正内容を変更する」: `AskUserQuestion` の `allowFreeText: true` で修正方針を確認してから適用
- 「スキップ」: `skip_list` に `{file, summary}` を追加。コミットしない
- 「レビュー終了」: `user_stop` としてフェーズ3へ即抜ける

コミットメッセージは CLAUDE.md 規約 `<type>: <説明>` に従う:
- 仕様書の追記・記述改善: `docs: <対象> の <内容> を更新`
- 仕様書間の矛盾解消・コード乖離反映: `fix: <対象> の <内容> を修正`

### 2-6. 次周へのスコープ縮小

```
if scope_mode == "diff":
  review_scope = (この周に Edit したファイル: 自動修正 + 対話確認修正) ∪ (未解決の confirm_findings があるファイル)
else:  # full
  review_scope = 全仕様書（変更なし）
```

`scope_mode == "diff"` の場合のみ2周目以降を上記に絞る（全体再スキャンの無駄を避ける）。`scope_mode == "full"` の場合は毎周全仕様書を対象にする。`iter += 1` してフェーズ2-1 に戻る。

## フェーズ3: 完了レポート

以下を表示する:

- 終了状態（`converged` / `no_progress` / `iter_limit` / `user_stop`）
- 反復回数と、周ごとの観点別・有効指摘件数（`confirm_findings`）の推移
- 選択した `scope_mode`（差分のみ/毎回全体）
- 自動修正した件数・ファイル一覧（周ごと）
- 対話確認: 修正済み / スキップ / 変更修正 の内訳
- 修正したファイル一覧
- 作成したコミット一覧（`git log --oneline` の該当範囲）

`no_progress` / `iter_limit` で終了した場合は、残った `confirm_findings` 一覧も併記する。

## ルール

- 質問には必ず `AskUserQuestion` を使い選択式で提示する。テキストだけで質問しない
- 自由入力が必要な場合は `AskUserQuestion` の `allowFreeText: true` を使う
- レビュー検出（観点別3体）は必ずサブエージェント（`review`）に委ね、メインスレッドは分類・自動修正・対話確認・コミットに専念する
- 3観点（整合性/コード乖離/品質）は毎周すべて並列起動する。一部だけ回さない
- **スタイル/体裁のみで意味を変えない指摘（`category: "auto"`）は確認せず自動修正する。仕様書間の矛盾（整合性）・実装との乖離修正（コード乖離）・意味が変わる品質指摘（`category: "confirm"`）は必ず対話確認する**
- **対話確認の指摘は1件ごとにコミットする。自動修正はファイル単位でまとめて1コミットにする。** いずれもそれ以上まとめない
- 改訂履歴の日付は実行日を使用する
- `no_progress`（2周連続で有効指摘件数が減らない）・`max_iter` 到達を無視して回し続けない。逆にどちらにも到達していないのに恣意的にループを打ち切らない
- `scope_mode == "diff"` の場合のみ2周目以降を `review_scope` に絞る。`scope_mode == "full"` の場合は毎周全体を再スキャンする
- 既存ファイルの修正は Edit で行う。新規ファイルを作成しない
- `TaskCreate`/`TaskUpdate` で進捗を管理する
