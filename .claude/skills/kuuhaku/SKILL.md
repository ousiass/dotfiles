# kuuhaku（画面単位の仕様理解 × 穴の検出）

仕様書を読ませるのではなく、**1画面分の仕様を「読める形」に変換して渡す**。生成したHTMLに疑問を書き込み、CCと突き合わせて解消する。この往復が「教えてくれる存在」の実体になる。

- **要件定義書**: `_プロジェクト設定.md` の「要件定義書」に指定があれば参照する
- **成長の定義**: kuuhakuなしで**仕様書を読み、空白を見つけ、埋める文を書ける**ようになること（3層 = 読む / 見つける / 書く）。**このSkillの成功は、自分が不要になること。**

**パスの基準**: 断りなき限り `<出力ルート>` 直下。`<出力ルート>` と案件横断の保存先は `_プロジェクト設定.md` で指定する。リポジトリ内のパスは同ファイルのローカルパス基準。

## 鉄則

**最優先ルール。他の記述と衝突したらここが勝つ。**

1. **read-only を厳守する** — implが同じリポジトリを書き換える。書き込みは出力ルート配下のみ
2. **答えを先に出さない** — 材料を見せる前に予測させる（FR-14）
3. **推測で断定しない** — 読めるものは必ず読む。読めなかったものは「推測」タグを付ける
4. **1画面 = 1フォルダ** — 再訪しても新フォルダを作らない。版はファイルで管理

## read-only の境界

2026-07-21に共有メインworktreeが別プロセスに操作される事故が発生済み。

| してよい | してはいけない |
|---|---|
| ファイル読み込み・grep | リポジトリへの書き込み（コード・仕様書・mock） |
| `git log` `git rev-parse` `git status` `git diff` | `git fetch` `checkout` `commit` `push` |
| `gh issue list` `gh pr list`（検索） | `gh issue create` |
| mockをブラウザで開く・スクショ | 状態を変える操作（登録・承認・削除） |
| 出力ルート配下への書き込み | worktree（`*-wt-*`）への一切のアクセス |

frontmatter の `allowed-tools` が書き込み系コマンドを機構的に外している。境界表はその補完であって、代替ではない。

## 起動時：モードを判別する

**先にこれを決める。予測をやるかどうかがここで決まる。**

| モード | 条件 | 手順3の予測 | 使う画面 | 昇格の母数 |
|---|---|---|---|---|
| **新規生成** | 画面フォルダが無い | **やる** | 未学習 | **入る** |
| **再訪** | フォルダあり＋再生成の依頼 | やらない | 既生成 | 入らない |
| **疑問回答** | `疑問.md` に未回答あり、または「疑問に答えて」 | — | — | 入らない |
| **赤入れ** | **読むトラック R2 以降**で本人が穴候補・骨子を書いた | — | — | 入らない |
| **Skill整備** | Skill自体を直すテスト運用（テンプレート・記載ルールの変更後など） | **やらない** | **既生成のみ** | 入らない |

- **疑問回答がこのSkillの中核**（→ 専用セクション参照）
- **赤入れは検証だけ。書き直さない**
- **Skill整備で未学習の画面を使ってはいけない。** 答えを見た画面は予測の題材として二度と使えず、学習用の在庫が減る。テストは既生成の画面の再生成で行う
- **Skill整備での「次に進む」は、新しい画面の生成ではない。** Skill自体の検証と、要件定義書 §13 未確定事項の解消を指す

2026-07-31にこれを取り違えて P-051（未学習）をSkill整備で消費した。モードの区別が無かったのが原因。

## 手順（新規生成）

### 1. 設定を読む

`<出力ルート>/<PJ>/_プロジェクト設定.md` からリポジトリパス・mock対応・**3トラックの現在地と担当トラック**を取得。
無ければ `templates/` のテンプレート群からフォルダ一式を作る。

| コピー元 | コピー先 |
|---|---|
| `templates/project-config.md` | `<PJ>/_プロジェクト設定.md` |
| `templates/concept-index.md` | `<PJ>/_概念の住所録.md` |
| `templates/screen-doc.html` | `<画面フォルダ>/理解.html`（手順7で埋める） |
| `templates/questions.md` | `<画面フォルダ>/疑問.md`（疑問が出たら） |
| `templates/phase-order.md` | `<PJ>/着手順序.md` |
| `templates/issue-proposal.html` | 起票候補PDFを作るとき（→「起票候補PDFを作る」節） |

### 2. 鮮度を確認する

```bash
git -C <repo> rev-parse HEAD && git -C <repo> log -1 --format=%ci
git -C <repo> status --porcelain -- <画面の関連ファイル>
```

- HEADが**7日以上古い**→ 生成前に警告。pullは**implウィンドウ側で本人が行う**
- 未コミット変更あり → 「implが編集中の可能性」を警告し、続行するか確認

### 3. 予測させる（材料を見せる前）— 固定5問の有無二択

**新規生成モードのみ。再訪・Skill整備ではスキップする。**

**問いは毎画面まったく同じ5項目。発想させない。**（2026-08-14改訂・旧Q1〜Q3を廃止）

| # | 項目 | 答え |
|---|---|---|
| 1 | 誰が開けるか（権限・ロール）の規定は仕様書にあるか | ある / ない |
| 2 | 入力の必須・上限・弾く条件の規定はあるか | ある / ない |
| 3 | 成功後にどこへ行くかの規定はあるか | ある / ない |
| 4 | 失敗の種類と、そのとき出す文言の規定はあるか | ある / ない |
| 5 | 一覧・数字の母数と並び順の規定はあるか（該当する画面のみ） | ある / ない |

**中身は当てさせない。有無だけ。**

- **「ない」と答えたものには理由を一言添えさせる** — 勘か、他画面の経験からかを区別するため
- 二択なので**白紙にならない**。旧Q3で起きた「3問とも白紙」が構造的に消える
- 5項目は「画面の仕様書に必要な要素」そのもの。**反復して型として身につけるのが目的**

任意で1問足してよい（**昇格判定には使わない**）: この画面で利用者層のうち誰が一番困りそうか。

#### なぜ「穴がありそうな場所」を廃止したか

旧Q3は毎回ゼロから発想させる問いだった。当たっても外れても**何の能力が動いたのか分からず、蓄積しない**。「システムから、仕様書に入れ忘れられていそうな項目を思いつくゲーム」になり、仕様書を読む力・書く力とは別のスキルを測っていた（2026-08-14 本人の指摘）。

### 4. 利用者プロファイルを部分読みする

`_プロジェクト設定.md` の「利用者プロファイル」にパスがあれば読む。無ければこの手順を飛ばす。

**全文Readは禁止。**（プロファイルは肥大しやすい）3手順のみ:

1. `grep -n '^#' <path>` で見出し構造を掴む
2. 「学習特性」に相当する節を offset/limit で Read（毎回読む）
3. 今日のテーマ語で grep し、ヒット行だけ読む

既習概念は説明なしで使う。未習には噛み砕きを添える。

### 5. 材料を集める（遠征）

画面IDを横断キーに、`_プロジェクト設定.md` の「材料の取得元」表に従って集める。

### 6. 穴候補を検出する

**穴の定義**: 仕様書の空白のうち、放置すると**利用者層（作業者 / 管理者 / 発注元）のいずれかが困るもの**。層の定義は `_プロジェクト設定.md` に書く。困らない空白は穴ではない → 記録して捨てる。

空白の型は6種（規定なし / 例外・境界未定義 / 画面間の概念不整合 / mock乖離 / **数字の定義欠落** / 導線の欠落）。型5が最も価値が高い（画面上は正常に見えるため実データを見ないと分からない）。

**候補ごとに必ず2つを通す:**

- **横断チェック** — `_概念の住所録.md` を引く。他画面に定義があれば「穴」ではなく**役割分担**として記載
- **地雷チェック** — 既存issue/PR検索（`#<番号> in:title,body`）、`git log -S`、回帰テストの有無。**意図的な変更履歴が出たら候補から外さず「人に聞くべき」に分類**（意図的な変更を見落として誤って起票する事故を防ぐ）

確度は3段階（確度高 / 要確認 / 意図の可能性）。

### 7. HTMLを生成する

`templates/screen-doc.html` をコピーし、`{{プレースホルダ}}` を埋める。
**書き方は `templates/writing-rules.md` が正本**（文章スタイル・確度タグ・幅）。

理解.html は §1〜§12 の固定構成。**§2「前回からの変化」は初回では section ごと削除**する（再訪でのみ出力）。

mockスクショは `_assets/` にコピーして埋め込む。

**プレースホルダは全て固有名になっている**（`{{rows_s5_操作}}` 等）。同名のものを増やしてはいけない → 理由は次節。

### 7b. 生成したHTMLを開いて検証する（必須・省略不可）

**2026-08-14の事故**: `{{rows}}` が同名で6箇所あり、上から順に置換したため §5→§7→§8 で使い切り、**§9の中身が§10に流れ込んだ**。§10本来の中身（穴候補3件）はどこにも書き込まれず空欄のまま提出し、本人に発見された。

**「残プレースホルダ0」は完成の判定に使えない。** 中身が正しい場所に入ったかは別問題。**必ずブラウザで開いて中身を照合してから提出する。**

```python
# Playwright で開き、各項目を照合する
sections = 'document.querySelectorAll("section.kh").length'          # §の数
empty    = '[...document.querySelectorAll("td")].filter(e=>!e.textContent.trim()).length'  # 空セル
cols     = 'document.querySelectorAll("#s9 table")[0].querySelectorAll("tr")[0].children.length'  # 列数
overflow = 'document.documentElement.scrollWidth > window.innerWidth'  # 横スクロール
```

| 見るもの | 合格条件 | これで防げた事故 |
|---|---|---|
| 残プレースホルダ | 0 | — |
| **空セル** | **0**（意図的な空欄を除く） | §9のトレードオフ表が空だったのを検出できる |
| **表の列数** | 想定と一致（案A/Bなら3列、A/B/Cなら4列） | 別の表の中身が入り込んだのを検出できる |
| **セクションを跨いだ混入** | §10に「案A」等の§9用語が出てこない | 中身が流れ込んだのを検出できる |
| JSエラー | 0 | 疑問欄の自動保存が壊れていないか |
| 横スクロール | なし | 幅の崩れ |
| 画像 | `naturalWidth > 0` | 貼ったつもりで読めていないのを検出 |

**§9のトレードオフは「払ったもの」が空でないことを必ず見る**（記載ルール: 空欄の案は理解できていない証拠）。

検証を通したら、本人に渡すときに**何を確認したかを明記する**。「生成しました」だけでは、今回と同じものを提出しうる。

### 8. 予測と照合する — 1回で2つ測る

手順3の5項目を、仕様書の実際の記述と突き合わせる。**4分類で返す。**

| 予測 | 実際 | 意味 | 記録先 |
|---|---|---|---|
| ある | あった | 読めている | **読む ○** |
| ない | なかった | 読めている＋空白の検知 | **読む ○** ／ 穴候補へ |
| **ある** | **なかった** | 読み落とし（過大評価） | **読む ×** |
| **ない** | **あった** | 読み落とし（見落とし） | **読む ×** |

- **読み落ちには、それが仕様書のどこに書かれていたかを必ず示す**（`ファイル:行`）。次回の地図になる
- **「ない → なかった」だけを成果と数えない。** 読み落ちを見逃すと、検知だけが伸びて読解が0のまま進む
- 読み落ちた項目は、**他の実装者も読み落とす箇所**である。「どう書けば誤読されないか」の材料として `履歴.md` に残す

的中結果を `履歴.md` に記録し、`_プロジェクト設定.md` の**読むトラック**を更新する。

### 9. 記録する

保存は自動実行しない。**本人の確認後に行う。**

**画面ごと（毎回・4ファイル）**

| ファイル | 書くもの |
|---|---|
| `<画面フォルダ>/履歴.md` | 生成日・HEADハッシュ・**モード**・予測と照合・穴候補・横断/地雷チェックの記録・次回への申し送り |
| `_概念の住所録.md` | **理解.html §7「この画面の外にあるもの」**で特定した概念の定義元。既存エントリの更新も |
| `_プロジェクト設定.md` | 進捗表・**3トラックの現在地**（読む / 見つける / 書く）・mock対応表の確定 |
| `<PJ>/着手順序.md` | フェーズの完了数 |
| `<画面フォルダ>/送信文_YYYY-MM-DD.md` | **起票候補PDFを作った回のみ**。Slackへ貼る本文と、補足を入れた／入れなかった理由 |

履歴.md が次回の差分の起点になる（FR-11）。

**月末（振り返りへ転記）**

`_プロジェクト設定.md` で指定した振り返り先の「**3トラックの変化**」へ転記する。転記元は各PJの `_プロジェクト設定.md` と各画面の `履歴.md`。

| 振り返りの行 | どこから取るか |
|---|---|
| 予測した画面 | 進捗表のうち**新規生成モードのもの**（再訪・Skill整備は除く） |
| **読む**（5項目の正解数 / **読み落ち件数**） | 3トラック表の読む欄。読み落ちは項目名と出典まで |
| **見つける**（確度判定が相手の反応と一致したか） | 同・見つける欄 |
| **書く**（規定文案を添えた件数 / 通った件数） | 同・書く欄 |
| 段が動いたか（月初→月末） | 3トラック表。動いたなら理由も |
| 検出した穴候補（確度別） | 各履歴.md の穴候補表を集計 |
| うち起票不可で捨てた | 同（`<s>` 付きのもの） |
| 実物確認を済ませた画面 | 各履歴.md の「実物確認が未実施」でないもの（**確認はCCが実施し、本人は結果を読む**） |

**成果として数える「空白を見つけた」は、実物確認まで済んだ穴候補だけ。** 検出しただけは数えない（想像で止まっているものを成果に数えないため）。

**「見つけた」と「埋めた」の差が滞留。** 差が開き続けているなら検出をやめ、埋める側（起票・実装）に手を回す。

## 規定文案を添える（書くトラック W1・2026-08-14追加）

穴候補には**仕様書に入れる文**を1文添える。**指摘だけで終わらせない。**

| 項目 | 書くこと |
|---|---|
| 入れる場所 | ファイル名＋節（例: `03-screen-detail.md` §P-050 の表示仕様） |
| 文案 | 実装者とテスターが**同じ解釈をする1文**。主語・条件・値を入れる |
| 根拠 | **既存の類似規定を必ず1件引く**（同じ粒度・文体に合わせるため） |

| ✕ | ○ |
|---|---|
| 並び順を明記する | 一覧の既定の並び順は姓カナ→名カナ→社員IDの昇順とする。利用者が並び替えた状態は保存しない |
| パスワードの条件を仕様書に書く | パスワードは8文字以上128文字以下、半角英字と数字をそれぞれ1文字以上含む。条件を満たさない場合は「半角英字と数字を含む8文字以上で入力してください」を表示する |

**既存規定を引くのが必須。** 自分の文体で書くと粒度が合わず、通っても書き直される。

判定は相手の反応で4分類する（そのまま入った / 文言を直された / 判断が逆 / 決める必要なし）。→ 足場外しの「書く」トラック

## 実物確認はCCがやる

> 操作系でCCができることは全部CCがやる。本人はその結果をチェックして上長へ送る役割に絞る。

**「環境構築はCC／画面を触るのは本人（学習の本体）」で切る案は採らない。**

実物確認は3トラック（読む・見つける・書く）のどれにも入っていない。本Skillが「成果として数える『空白を見つけた』は実物確認まで済んだ穴候補だけ」と定めているとおり、**実物確認は成果の計上条件であって学習工程ではない**。CCがやっても学習設計と矛盾しない。

### 役割の切り分け

| やること | 誰が |
|---|---|
| 環境の起動・DBの初期化・疎通確認 | **CC** |
| **画面を操作して挙動を確かめる**（登録・編集・削除・エラーの再現） | **CC** |
| **API直叩き・SQLでの確認** | **CC** |
| **結果のスクリーンショット取得** | **CC** |
| 確認結果を読んで判断する／上長へ送る | **本人** |

**本人に渡すのは「確認しました。結果はこうです」の状態から。** 手順書を渡して終わりにしない。

### 触ってよい範囲（ここは変えない）

| ○ | ✕ |
|---|---|
| ローカルの docker compose 環境・ローカルDB（使い捨て） | **本番・staging・共有環境の状態を変える操作** |
| ローカルAPIへの直叩き | リポジトリへの書き込み・git操作・issue作成（鉄則1） |

**ローカルで壊れて困るものは無い。** 迷ったら消して立て直す。本番と共有環境にだけは触れない。

### 確認できないときは、できる範囲を先に済ませる

環境が完全でなくても止まらない。**読み取りだけの確認は先にやる。**

2026-08-18 の実例: api が起動せず（GCS鍵が無い）画面は触れなかったが、**postgres には入れたのでテーブル構造を確認**し、「契約履歴に価格の列が無い」ことを実測できた。穴候補が読解から実測へ上がった。

| できないこと | それでもできること |
|---|---|
| ログインが要る画面操作 | DBのテーブル構造・データの確認（`\d`・`SELECT`） |
| API直叩き（api停止時） | コードから文言・分岐の引用 |
| 実画面のスクリーンショット | 操作マニュアルPDFからの抜粋（出所を明記する） |

**できなかったものは「未確認」と書いて残す。** 済んだものと混ぜない。

### 「起動した」と言う前に必ず疎通確認する

**`docker compose ps` は信用できない。** `Started` と表示されていても、直後にプロセスが落ちていることがある（2026-08-14 に実際に起きた）。

```bash
# 1. フロントが応答するか
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000/<対象パス> --max-time 20

# 2. APIが応答するか（ログインが必要な画面では必須）
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8080/v1/health --max-time 10

# 3. 200 以外なら、落ちた理由をログで特定する
docker compose logs api --tail 20
```

2026-08-14 の実例: `docker compose ps` は `shabekuri-api Started` と表示したが、ログには
`CRITICAL failed to create storage client: open config/gcs-key.json: no such file or directory` → `Process Exit with Code: 1`。
**「起動して見えるのに死んでいる」状態**で、本人には「URLが分からない」ように見えていた。

### 渡し方

- 疎通が通った → **「`http://localhost:3000/...` で確認できます」と具体的なURLを書いて渡す**。トップページのURLだけ渡さない（LPが出て「検証できない」となる）
- ログインが必要な画面 → **ログイン用のアカウント（シードのメール）も併せて渡す**。初回ログイン時にパスワード変更画面を通ることも明記する
- 疎通が通らない → **URLを渡さず、落ちた理由と必要なもの（鍵ファイル等）を報告して止まる。** 本人の手を止めさせない

### 環境が立たないときは理由まで特定する

「動きません」で返さない。ログを読み、**何が足りないか**を名前で示す。

| 症状 | 見るところ | よくある原因 |
|---|---|---|
| APIが応答しない | `docker compose logs api` | 鍵ファイル・環境変数の不足 |
| DBが空 | `psql -c "\dt"` | マイグレーション未適用（`backend/scripts/setup-local-db.sh`） |
| 画面が404 | ルート定義 | パスの取り違え |
| ログインできない | APIのログ | APIが落ちている（表示上は起動して見える） |

**あわせてブランチを確認する。** 理解.html は特定のコミットを読んで書いている。検証時のチェックアウトが別ブランチだと内容が食い違う（実際に別ブランチで検証しかけた事例がある）。

## 起票候補PDFを作る（上長へ提案するとき）

穴候補が揃ったら、上長への提案用にPDFを作る。**デザインは固定。毎回考え直さない。**

2026-08-14に、前回のHTMLがscratchpadに残っていたおかげで再現できただけの状態が発覚した。テンプレートを `templates/` に置いて解決済み。

### 作り方

1. `templates/issue-proposal.html` をscratchpadにコピーする
2. `{{ }}` を埋める。**CSSは触らない**
3. Playwrightで PDF 化する（コマンドはテンプレート冒頭のコメントに記載。`margin 0` と `print_background=True` が必須）
4. **PDF化したらスクショで全ページを目視する。** レイアウト崩れ・はみ出しを確認してから配置する
5. `<出力ルート>/<PJ>/<画面フォルダ名>/起票候補_提案書_YYYY-MM-DD.pdf` に置く
6. **送信文も同じフォルダに作る**（→ 次節）。PDFだけ置いて終わりにしない

**PJ直下に置かない**（2026-08-14に直した）。直下に並べると画面名がファイル名だけの手がかりになり、27画面ぶんが横並びでどれがどれか分からなくなる。**画面フォルダが画面を示すので、ファイル名は種別＋日付だけ**にする。理解.html・疑問.md・履歴.md と同居させ、画面を開けば資料が揃う状態を保つ。

### 送信文をPDFとセットで作る（2026-08-18追加）

> 「いつも提案書は添付画像の通りの文章で送しているので、PDF作成と一緒にその文章の作成までタスクに入れて欲しい」

PDFを作ったら **`<画面フォルダ>/送信文_YYYY-MM-DD.md`** も作る。**そのままコピーできる形**で書く。宛先はSlack（社内）。

**型は固定。3行。**

```
【<プロダクト名>】
<画面名>画面の起票候補をまとめたPDFです！
OKが出たものを起票して潰していきたいと思います！
```

- 本人の実際の投稿文がこの形。**言い換えない**
- 相談の内容を本文に要約しない（PDFに書いてあるので二重になる）

**選択肢を出した項目は、本文で番号を名指しする**（2026-08-18の反省）。

PDFに複数案を書いても、カード内に埋まっていると「OK」だけが返ってきて選択が決まらない。実例: 7件出して案を並べたのは3件だったが、**専用の補足ページを付けた1件だけ選ばれ、カード内に収めた2件は「OK」で返ってきた**（結果、issue本文に両案を書いて実装者判断に回すことになった）。

```
判断が必要なのは3件です！
・1 → 案A/B/Cのどれで進めるか（P3に比較があります）
・2 → エラーコードを分けるか、文言を両対応にするか
・3 → タイプ変更は不可でよいか
他（4〜7）はOK/NGだけで大丈夫です！
```

**OK/NGで済む項目と、選択が必要な項目を分けて書く。** 相手は前者を読み飛ばして後者だけ考えられる。

**補足は「PDF内にあっても埋もれるもの」だけ足す。**

| 足すもの | 足さないもの |
|---|---|
| 依頼（鍵の共有・データ確認など）。**最終ページは読み飛ばされやすい** | 相談の内容の要約 |
| 前回の回答を受けての報告 | 表紙に書いてある確認状況 |
| | 別画面の未提案分（混ぜると論点が増える。送るなら別投稿） |
| | こちらの作業計画・次に読む画面（相手が行動できない） |

送信文の .md には、**何を足して何を足さなかったかの理由も書く**。次回の判断が速くなる。

### これは「相談書」である（2026-08-14 FBで確定）

読み手は上長・実装担当者。**相手から見れば全件が相談**。ここを取り違えると、内部メモをそのまま送る文書になる。

- **内部管理用の分類をPDFに書かない** — 「自分で判断可」「記録のみ」「起票不可」は本人の作業分類であって、相手には意味がない。それらは `履歴.md` 側に残す
- **タグは2種だけ** — 「要確認」＝意図を聞きたい／「修正のご提案」＝直し方まで提示できる（既存issue分は別枠の「既存issue」）
- 各項目に**「ご相談: 」または「ご提案: 」の1文**を必ず入れ、相手に何をしてほしいかを書く
- **確度をPDFに書かない**（2026-08-18）。確度（確度高／要確認／意図の可能性）は**そう言い切れるかというこちらの内部評価**であって、相手の判断を変えない。タグが既にその情報を持っており、「確度: 要確認」と タグ「要確認」は同じ語の重複になる。**代わりに `item-meta` へ置くのは次の2つ**:
  - **影響**: 何が損なわれるか（例: 顧客企業への請求金額／管理者が原因を取り違える）
  - **確認**: どこまで確かめたか（例: 実DBで確認済み／コード読解のみ／実画面で再現済み）— これは内部評価ではなく事実なので、相手が信頼度を判断する材料になる

### 構成

**ページ数は内容で決まる。空のページを型として持たない。**

| ページ | 中身 | 必須か |
|---|---|---|
| 表紙 | **対象画面**・リポジトリ・調査範囲・件数・本書の位置づけ・**確認状況**・調査の進め方 | 必須 |
| 相談一覧 | 1件1カード。**1ページ3件まで**。溢れたら「（続き）」ページへ | 必須 |
| 各相談の補足 | 案の比較・確認したいこと・コスト比較。1件が大きいときだけ | 任意 |
| 既存issue | 指摘済みのもの | 該当があれば |
| **お願いしたいこと** | 相談ではなく、**こちらから依頼すること**（鍵の共有・データの確認など） | 依頼があれば |

**作らないページ（2026-08-14 FB）**

| ✕ | 理由 |
|---|---|
| 「主な発見」 | 相談一覧と重複する |
| **「今後の進め方」** | **相談内容の言い換えになる。**各カードに「ご相談: 」を書いた以上、同じことを2回書くことになる |

### 相手が行動できることだけ書く

**混ぜてはいけない2つ**があった。「今後の進め方」は、相手が知りたいこと（自分が何をすればいいか）と、こちらの作業計画を同じ見出しに入れていた。

| 何を | どこに書くか |
|---|---|
| 相談・提案の内容 | **各カードの「ご相談: 」に1箇所だけ** |
| こちらから依頼すること | 「**お願いしたいこと**」として最後に短く |
| **こちらの作業計画・次の調査対象** | **書かない**（相手に無関係。`履歴.md` に残す） |

「次はフェーズ2に進みます」は相手にとって何の判断材料にもならない。**読み手が何もできない情報は落とす。**

### 選択肢を出すときは、比較表の前にサマリを置く（2026-08-14 FB）

比較表だけ渡すと「表がごちゃっとしていて見づらい」（本人の指摘）。**各案が何なのかを1行ずつ先に示す。**

```
案A  何もしない（現行）  同名の組織を制限なく登録できる状態を続けます
案B  禁止する           メールアドレスと同じように、既存の組織名と重なる登録を拒否します
案C  警告する           登録自体は通しますが、その前に確認を挟みます
```

そのうえで**比較表からは「内容」の行を削る**（サマリと重複するため）。表に残すのは**案によって答えが変わる観点だけ**にする。

| ✕ 表に入れる | ○ 表に入れる |
|---|---|
| 内容（＝各案の説明） | 同名の別法人を登録できるか |
| | うっかり2件目を防げるか |
| | 既存データへの影響 |

### 1件の情報量が多いときも、骨格を崩さない（2026-08-14 FB）

**構成を変えてはいけない。** 相談一覧はカード形式のまま、増えた情報は**補足ページに逃がす**。

2026-08-14 に、相談1の情報量（3案比較・確認事項2つ・識別手段）をカード1枚に詰めようとして諦め、**1件を複数ページに展開する形に構成ごと変えてしまった**。前回のPDFと並べると別物に見え、本人から「PDFの形式が違うのは仕方ないのか」と指摘された。

| ✕ 崩れた形 | ○ 正しい形 |
|---|---|
| P2「ご相談1／2」<br>P3「ご相談1の続き」<br>P4「ご相談2／2」 | P2「**ご相談したい2件**」（カード2枚）<br>P3「**ご相談1の補足**」<br>P4 今後の進め方 |

- カードには**要点と「ご相談: 」の1文まで**を入れ、末尾の `item-meta` に `詳細: 次ページ` と書く
- 詳細（案の比較表・確認事項・コスト比較）は**次ページに「〜の補足」として置く**
- 読み手は毎回**同じ骨格**（表紙 → カードで一覧 → 詳細 → 今後の進め方）で読める

**「読み手にとって毎回同じ形式であること」が、1件の情報量より優先する。**

### ページ溢れの照合（必須）

`.page` は `min-height` なので、詰めすぎると勝手に次ページへ溢れる。**PDF化したら必ず2つを照合する。**

```python
# 1) 各ページの高さ（A4縦 = 約1123px）
'''[...document.querySelectorAll('.page')].map((e,i)=>({p:i+1, h: Math.round(e.getBoundingClientRect().height)}))'''
# 1123px を超えていたら、そのページが溢れている

# 2) div.page の枚数 と PDFの実ページ数
len(re.findall(rb'/Type\s*/Page[^s]', open('out.pdf','rb').read()))
```

**枚数が一致しなければ提出しない。** 数十pxの超過なら見出しの `margin` を詰める（24px→16px）。それでも収まらなければページを分ける。

### タイトルは、それだけ読んで何の話か分かる文にする

技術用語を先頭に置かない。**「何が起きるか」を平易な日本語で言い切る。**

| ✕ | ○ |
|---|---|
| パスワード更新時、既定で「変更済み」として扱われる | 呼び出し方によっては、パスワード再発行後も強制変更画面を通らずに済んでしまう |
| セッション無効化つきパスワード変更が、定義のみで使われていない | 他端末のログインを切るパスワード変更処理が、実装されているが使われていない |

### 事実だけで止めない。何の期待を裏切るかまで書く（2026-08-18追加）

タイトルが「何が起きるか」を満たしていても、**読み手が「それの何がいけないの？」と感じることがある**。事実は伝わっても、それがまずい理由が伝わっていない。

**指摘は3点で1組にする。**

> **事実** → それが**壊す前提** → **誰がどう困るか**

| 何を | どこに書くか |
|---|---|
| 事実 | タイトル |
| 壊す前提 | 本文の**1文目** |
| 困り方 | 本文の続き（影響を受ける対象を名指しする） |

2026-08-18 の実例。タイトルは正確だったのに「一見『何がいけないの？』と感じる」と指摘を受けた。

| ✕ 事実だけ | ○ 前提から書く |
|---|---|
| プランの月額料金を変更すると、契約中の組織のその月の請求額も変わります | **契約には開始日があるのに、プラン自体の価格には開始日がありません。**料金を編集した時点で、過去にさかのぼって「その価格だったこと」になります。影響は請求金額と画面表示の2つに出ます |

**検算**: 書いた指摘に「だから何？」と自分で聞いてみる。答えられないなら、壊す前提を書き落としている。

### 状態の記述には、困る場面を1つ添える（2026-08-18追加）

「〜できません」「〜が効きません」は**状態**であって影響ではない。読み手は状態だけでは優先度を決められない。**誰が・何をしようとして・どこで詰まるかを1文で書く。**

| ✕ 状態だけ | ○ 場面を添える |
|---|---|
| プランタイプを変更しても保存されません | 「基本プランとして作ったがオプションにすべきだった」と気づいた管理者が選び直して保存し、成功表示を見て組織に割り当てようとして、そこで初めて弾かれます |

**検算**: その指摘で実際に困る人の1シーンを1文で書けるか。書けないなら、影響がまだ分かっていない。分からないまま出さず、調べるか「影響の範囲は未確認」と書く。

### 一覧は「読み手が次に取る行動」でまとめる（2026-08-18追加）

項目が5件を超えたら、**読み手の行動が同じものを固めて、グループ名を見出しに出す。** 行動が違うものを混ぜて並べると、読み手は毎項目で「これは自分が何をする話か」を判定させられる。

分ける軸は内容で決まる。例:

| 軸 | グループ |
|---|---|
| 何を直すか | コードを直す ／ 文書を直す |
| 誰が決めるか | 自分たちで決められる ／ 顧客・上位者に確認が要る |
| いつやるか | 今すぐ ／ 次のリリースで |

**分けたらページとラベルの両方に出す。** 見出しだけだと、ページをめくった読み手が現在地を見失う（`sec-label` に「― 実装について」「― 仕様書について」のように付ける）。

2026-08-18 の実例: 7件を1つの並びに置いたところ「4-6は仕様書への変更依頼なのでそれは一瞬で理解できる形式にしておきたい。いきなり7で実装側の起票候補になるのは認知負荷が無駄に高い」と指摘を受けた。

### 画面写真を入れる（2026-08-18追加）

**文章だけの指摘は、読み手にとって画面が想像できない。** 該当する画面を貼ると、説明の何行分かが消える。

| 状況 | 何を貼るか |
|---|---|
| 実画面を操作できる | **実画面のスクリーンショット**（第一選択。→「実物確認はCCがやる」） |
| 環境が動かない | **操作マニュアルPDFからの抜粋**。表紙に「掲載写真はマニュアル抜粋で実画面ではない」と明記する |
| どちらも無い | 貼らない。**作り物のスクリーンショットを実物のように見せない** |

**貼らない判断も明示的にする。** 2026-08-18 の実例: エラーモーダルの文言が問題という指摘に対し、入力欄の写真を貼っても文言の食い違いは伝わらないため貼らず、「操作 → 出る文言」の対応表で代替した。

**画面写真を探す作業そのものが調査になる。** 同日、マニュアルp16 のプランタブを探した過程で「契約履歴の月額表示がプランの現在値を引いている」ことに気づき、穴候補の根拠が1つ増えた。コードを読むだけでは出なかった。

抜き出しの手順:

```bash
# 1. 該当ページを特定する
pdftotext -layout <manual>.pdf - | awk 'BEGIN{p=1} {if(/\f/) p++; if(/<探す語>/) print "p"p": "$0}'
# 2. 150dpi で画像化
pdftoppm -f <p> -l <p> -r 150 -png <manual>.pdf out
# 3. 必要な箇所だけ切り出す（小さい文字は2倍に拡大してから埋め込む）
python3 -c "from PIL import Image; im=Image.open('out-<p>.png'); im.crop((x1,y1,x2,y2)).save('_assets/shot_xxx.png')"
```

**切り出したら必ず開いて読めるか確認する。** 2026-08-18 に赤字の警告が潰れて読めない状態で1度出した。範囲を絞って2倍に拡大し直した。

### どの画面の話かを全ページに出す

表紙タイトル・`cover-meta` の「対象画面」・各ページの `sec-label`・`footer` の**4箇所**。

### 書くときの注意

- **実物確認が未実施なら表紙に明記する。** 読解だけの指摘を確定事実として出さない
- 指摘だけで終わらせず、**何をすれば閉じるか**まで書く
- 「要確認」には**誰に何を聞くか**まで書く
- **ページ溢れを必ず照合する** — `.page` は `min-height` なので詰めすぎると勝手に次ページへ溢れる。`div.page` の枚数とPDFのページ数が一致することを確認する
- **高さの照合と目視は別物**（2026-08-18）。置換を重ねると同じ文が2回出るなどの不具合が起きるが、高さは合ったままになる。**全ページを画像化して読む**

## 手順（再訪）

**予測はやらない。的中率の母数に入れない。**

1. `履歴.md` から**前回のHEADハッシュ**と申し送りを読む
2. 差分を取る

```bash

```

差分が空なら再生成しない。「変化なし」を履歴.md に書いて終える。

## 疑問に答える（疑問回答モード） — FR-7

**このSkillの中核。** 生成は材料を渡すだけで、往復が「教えてくれる存在」の実体になる。

### 起動条件

`<画面フォルダ>/疑問.md` の「未回答」に何か貼られている、または「疑問に答えて」と言われたとき。

`疑問.md` が無ければ `templates/questions.md` の本体をコピーして作る。

### 手順

1. **疑問.md の「未回答」を読む**
2. **1件ずつ answer する。まとめて長文を返さない**（1メッセージ＝1件が原則。利用者プロファイルの簡潔さ要求）
3. **答えを探す順序**: 仕様書 → 実装 → テスト → git log → 既存issue。**読めるものは必ず読む**（推測で埋めない）
4. **3つに仕分ける**（下記）
5. **回答済みへ移し、状態を付ける**
6. 穴候補へ昇格したものは **理解.html §10「穴候補」の表に追記**する

### 仕分け — 疑問から穴が見つかる

| 行き先 | 条件 | やること |
|---|---|---|
| **解決** | 仕様書・コードに答えがあった | 出典（`ファイル:行`）を付けて回答する |
| **穴候補へ昇格** | **答えが仕様のどこにも無かった** | 横断チェック＋地雷チェックを通し、確度を付けて **§10に追記**。住所録にも「仕様に定義なし」で登録 |
| **人に聞く** | 過去の判断理由が絡む／複数案のどれも成立する | 誰に何を聞くかの**文案**まで作る |

**「自分が分からなかった」と「仕様に書かれていない」は別。** 回答の過程で必ずどちらかを判定する。前者なら教える、後者なら穴として記録する。

### 回答の書き方

**必ず本人の疑問を引用してから始める（2026-08-14 本人の要求）。**

> 「次から僕がどんなふうに疑問を持ったのかについて最初に提示してから解説して欲しいな。どんな疑問を持って今解説してくれているのかが明確になるとUXが向上する」

疑問を書いてから時間が経っていたり、複数を順に答えていると、**本人はどの疑問への回答か分からなくなる**。回答の頭に引用を置けば、読む前に対象が確定する。

```markdown
> IDが表示されない。IDだけでは普通にうっかりがあり得そうなので…

（ここから回答）
```

- 引用は**本人が書いた言葉のまま**。要約して言い換えない（何を聞いたか本人が照合できなくなる）
- 長い疑問は**冒頭1〜2文だけ引用**して残りを省略してよい
- 疑問が複数あるときは、**最初に仕分け表を1枚出す**（どれが穴に昇格したか・どれが解決かを先に見せる）。そのうえで1件ずつ引用して答える

**指導側が出した比喩を本人の解釈として帰属しない。**「あなたが〜で例えた」と書かない（利用者から是正を要求された事例がある）。英語の専門語・固有名にはカタカナ読みを添える。

### 1つの疑問に複数の論点が含まれていたら、分けて1つずつ短く答える

**2026-08-14 に「もう少し簡単に説明してほしい。一つずつ、なぜ追加はあるのか、編集がないのか、削除がないのか」と要求された。**

そのとき私は「変える・消すが無いのは良いことか」に対して、理由・比較・背景を1つの回答に混ぜて返した。**論点が3つ（追加／編集／削除）あるのに、まとめて説明したため長くなった。**

| ✕ まとめて説明 | ○ 1つずつ |
|---|---|
| 一覧に置かない理由 → 同名で区別できない話 → 論理削除の話 → ぶら下がるデータの話…（1つの塊） | **追加が一覧にある理由**: まだ詳細画面が存在しないので、ここしかない<br>**編集が一覧に無い理由**: 項目が多くて一覧に収まらない<br>**削除がどこにも無い理由**: 消すと請求履歴も消える |

**書き方**

1. 疑問に含まれる論点を数える（「変える」「消す」→ 2つ。文脈上「追加」も対比に必要なら3つ）
2. **1論点＝2〜3行**で答える。理由を1つだけ書く
3. 最後に**一覧表で並べる**（横に比較できると関係が見える）
4. 「ここまでで引っかかるところはありますか」で締める

**背景・比較・トレードオフは、聞かれてから足す。** 最初から全部載せると、論点の区別が消える。

利用者プロファイルに簡潔さの要求があれば従う（例: 「要点のみ」「1メッセージ＝1アイデア＋1確認まで」）。**こちらの"短い"はまだ長い**と考えて削る。

確度タグは下の表に従う。「実装のみ」が出たら**穴候補への昇格を検討する**。「確認できず」は推測で埋めずにそう書く。

既習概念は説明なしで使う（利用者プロファイルで判定）。未習には噛み砕きを添える。

## 書き方の要点（詳細は記載ルール.md）

### 文章スタイル

**品詞の数量を最小化する。** 前置き・修飾語・抽象語・接続語・言い換えの重複を削る。結論・理由・必要な例だけ書く。

**強度は副詞で足さず、内容で出す。** 確度タグが「推測」と言っているので、文中に「おそらく」を書かない（二重表現）。

### 確度タグ

理解.html と疑問.md で共通。

| タグ | 使う場面 | 文体 |
|---|---|---|
| 明記 | 仕様書に書いてある | 断定してよい。出典必須 |
| 実装のみ | コードにあるが仕様に無い | 「実装ではこうなっている」 |
| 推測 | 一般則からの補完 | 「〜と読める」＋「根拠:」（副詞は使わない） |
| **トレードオフ** | 設計判断 | **断定文を使わない**。対比表（案A/案B＋各代償） |
| 穴候補 | 確認が必要 | 「確認が必要」＋担保状況を併記 |
| 確認できず | 探したが見つからなかった | そう書く。推測で埋めない |

全セクションに `出典: ファイル:行` を付ける。

### 幅

**コンテナは1本。セクションごとに切り替えない**（左端が動くと基準線が崩れる）。行長は `max-width` ではなく背景ブロックの右内側余白で作る。

## 「自分で決められる／人に聞くべき」の仕分け

疑問と穴候補の両方に付ける。

| 分類 | 条件 |
|---|---|
| 自分で決められる | 一般則で判断できる / 仕様書内で完結 / 実物で確認できる |
| **人に聞くべき** | 過去の判断理由が絡む / git logに意図的変更 / 仕様の意図が読み取れない / 複数案のどれも成立する |

「人に聞くべき」には**誰に何を聞くかの文案**を付ける。

## 足場外し（2026-08-14 全面改訂）

### 3トラック並走。積み上げない

能力は3層あり、進む速さが違う。1本の階段にすると**「読む＝未達なのに、見つける＝達成済み」で判定が壊れる**（下位段が未達なのに上位段相当の行動が出る形）。

現在地は `_プロジェクト設定.md` に**3トラック分**記録する。

| トラック | 段 | 通過条件 |
|---|---|---|
| **読む** | R1 有無を当てる | 手順3の5項目が **5/5正解を2画面連続** |
| | R2 中身を当てる | 有無が合った項目の**中身**を 3/5以上を2画面連続 |
| | R3 出典を当てる | どのファイル・どの節に書かれるかを 3/5以上 |
| **見つける** | F1 空白を挙げる | 確度高の候補が1件以上出る |
| | F2 確度を当てる | 確度判定が相手の反応と **2回一致** |
| | F3 反応を当てる | 聞く前に「採用されるか」を宣言して 2回一致 |
| **書く** | W1 規定文案を添える | 起票に**仕様書へ入れる規定文案**を1文つける |
| | W2 文言修正で通る | 修正入りで仕様書に入る 1件 |
| | W3 無修正で通る | 無修正で仕様書に入る 2件 |

### 生成量は「読む」トラックだけに連動させる

生成を減らして重くなるのは読む負荷だから。見つける・書くが先に進んでいても矛盾しない。

| 読む段 | kuuhakuがやること | 本人がやること |
|---|---|---|
| **R1** | 全セクションを生成 | 読む・5項目を答える・疑問を書く |
| **R2** | 穴候補セクションを**空欄**で生成 | 自分で穴候補を書く → CCが検証 |
| **R3** | 赤入れのみ | 理解.htmlの骨子を自分で書く |
| **卒業** | 相談相手のみ | 仕様書を直接読み、自力で穴を見つける |

- 新規プロジェクトは R1 / F1 / W1 から始める
- 降格は**読み落ちが3項目以上出たら1段**。戻ることは失敗ではない
- **画面を消費するのは読むトラックだけ。** 見つける・書くは同じ画面で何度でも測れる

### 複数PJ並行のとき、担当トラックは仕様書の構造で決める

仕様書の構造はPJごとに違う。**別カウントで分割するのではなく、層で分担する。**

| 仕様書の状態 | 担当トラック | 理由 |
|---|---|---|
| 画面単位で揃っている | **読む** | 5項目の照合が成立する |
| 機能別に分散 | **見つける** | 横断の不整合が出やすい |
| 画面仕様書が存在しない | **書く** | 自分の文が事実上の画面仕様書になる |

**画面仕様書が無いPJで読むトラックは測れない**（読む対象が無い）。そこで5項目の照合をやっても「ない → なかった」しか出ず、読み落ちが検出できない。

各PJの担当トラックは `_プロジェクト設定.md` に記録する。

### 昇格を空白の件数で決めない

旧条件（Q3を2画面連続で当てたら昇格）は廃止した。空白の件数で決めると**読み落ちが見逃され、検知だけ伸びて読解が0のまま進む**。実際に、検知は F2 到達・読むは未測定・書くは0という状態になった。

## 着手順序

`templates/phase-order.md` に**データ依存順**でフェーズを並べ、それに従う。依存元から先に読む。

> 例: 土台 → マスタ → トランザクション → 集計 → 出力 → 監査

フェーズの粒度と数はPJごとに決める。依存元が未学習の画面を指定されたら、それに従いつつ**一言添える**。

## 生成物の取り扱い

生成物には案件の仕様が含まれる。**着手前に案件の秘密保持条項を確認し、該当条項を `_プロジェクト設定.md` に書き写す。**

- 自分の管理下での保管は可（本人であり第三者ではない）
- **社外に出さない**（記事・SNS・ポートフォリオ・他案件）
- **契約終了時は出力ルート配下を廃棄する**
- 汎用ナレッジへは**抽象化した型だけ**保存する（固有名・コード断片を持ち込まない）

## アンチパターン

- ❌ **リポジトリに書き込む** — implと衝突する。read-onlyが最優先
- ❌ **材料を見せてから予測させる** — 答えを見てから当てても検索練習にならない
- ❌ **1画面だけ見て穴と断定する** — 別画面で担保されている可能性を必ず検証する
- ❌ **git logの意図的変更を無視して起票候補にする** — 意図的な変更を見落とした事実誤認の起票事故
- ❌ **利用者プロファイルを全文Readする** — 肥大しやすい。部分読みする
- ❌ **確度タグがあるのにヘッジ副詞を書く** — 二重表現
- ❌ **設計判断を単一の正解として書く** — 制約で答えが変わる。トレードオフで示す
- ❌ **セクションごとに幅を変える** — 左端が動いて読みの基準線が崩れる
- ❌ **穴を見つけたら即issue化** — ゴールは相談メモまで。起票は本人がimpl側で
- ❌ **確認を本人に投げる** — 環境の起動・**画面操作・API直叩き・SQL・スクショ取得まで全部CCがやる**。本人に渡すのは「確認しました。結果はこうです」の状態から（2026-08-18 改訂 → 「実物確認はCCがやる」節）
- ❌ **環境が完全でないことを理由に確認を丸ごと諦める** — 読み取りだけの確認は先に済ませる。できなかったものは「未確認」と書いて分ける
- ❌ **確度をPDFに書く** — こちらの内部評価であって相手の判断を変えない。タグと重複する。代わりに「影響」と「確認」を出す
- ❌ **事実だけ書いて「なぜ困るか」を書かない** — 読み手が「それの何がいけないの？」と感じる。事実 → 壊す前提 → 困り方の3点で1組
- ❌ **状態の記述で止める** — 「〜できません」は状態。困る人の1シーンを1文で添える
- ❌ **行動の違う項目を1つの並びに混ぜる** — 読み手が毎項目で「自分が何をする話か」を判定させられる。5件を超えたら行動でグループ化する
- ❌ **`docker compose ps` の表示だけで「起動した」と言う** — `Started` と出ていても直後に落ちていることがある。**疎通確認まで通す**
- ❌ **「残プレースホルダ0」で完成と判断する** — 中身が正しい場所に入ったかは別問題。開いて検証する（→ 手順7b）
- ❌ **同名のプレースホルダを複数置く** — 上から順に置換して中身がずれる。2026-08-14に §9→§10 で発生
- ❌ **複数の論点をまとめて1つの回答にする** — 論点ごとに分けて2〜3行ずつ。最後に一覧表で並べる（→ 「1つの疑問に複数の論点が…」）
- ❌ **本人の疑問を引用せずに回答を始める** — どの疑問への回答か分からなくなる（→ 「回答の書き方」）
- ❌ **PDFで1件が大きいからといって構成を変える** — 骨格は固定。詳細は補足ページへ逃がす
- ❌ **モードを判別せずに始める** — 予測をやるか飛ばすかが決まらない。未学習の画面をSkill整備で焼く事故が起きる
- ❌ **再訪で旧版を上書きする** — `_archive/` へ退避してから生成する
- ❌ **昇格を空白の件数で決める** — 読み落ちが見逃され、検知だけ伸びて読解が0のまま進む
- ❌ **「ない → なかった」だけを成果に数える** — 手順8の4分類のうち2つは読み落ち。そこを飛ばすと読むトラックが動かない
- ❌ **予測で穴を発想させる** — 固定5項目の有無二択に統一した。思いつきゲームは蓄積しない
- ❌ **PDFだけ作って送信文を作らない** — 本人が毎回文面を書き起こすことになる。型は固定なので一緒に作る（→ 「送信文をPDFとセットで作る」）
- ❌ **見つけたまま出口へ渡さない** — 2026-08時点で穴候補40件超に対し起票2件。**検出を止めて起票に手を回す判断を、月末ではなく都度行う**
