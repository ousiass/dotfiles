# 記載ルール（正本）

kuuhaku が生成するHTMLの書き分け規則。**生成のたびに表現がバラつくのを防ぐための固定ルール。**
迷ったらここに戻る。変更するときはこのファイルを直し、[生成テンプレート.html](生成テンプレート.html) に反映する。

## 大原則 — 文章もデザインも引き算

**数量を最小化する。足す理由を立証できた要素だけ残す。**

文章で削るもの（前置き・修飾語・抽象語・接続語・言い換えの重複）には、デザインの対応物がある。

| 文章で削るもの | デザインで削るもの |
|---|---|
| 前置き | 飾りの導入要素・意味のない罫線 |
| 修飾語 | 多重の枠線・影・グラデーション |
| 抽象語 | 意味を持たない色分け |
| 接続語 | 区切り線の乱用（余白で区切る） |
| 言い換えの重複 | 同じ情報をタグと枠の両方で言うこと |

**二重表現の実例**（2026-07-31に両方直した）

- 文章: 「推測」タグがあるのに文中で「おそらく」→ タグが確度を担うので副詞は不要
- デザイン: 「推測」タグがあるのに四辺を枠で囲う → タグが確度を担うので左罫だけでよい

**空間は削る対象ではなく、作る対象。** 余白トークン `--kh-section-y: 96px` はそのために存在する。

## 前提を先に渡す — 解説から始めない

**過去に発覚した最大の欠陥。** 何の話をしているかを言う前に中身の説明を始めていた。

読み手に起きること:

- §4「数字はどう計算されるか」→ **その"数字"が何を指すか分からないまま本文が始まる**
- 「型5」「数字の定義欠落」→ 型1〜6を知らない読み手に初出で使っている
- 「判定」→ 何の何を判定するのか書いていない

### 全セクションの冒頭に3点を置く

1〜2行でよい。**前置きを足すのではなく、読む目的を先に渡す。** 迷いが消えるぶん全体は短くなる。

| # | 置くもの | §4の例 |
|---|---|---|
| 1 | **何を見るか** | この画面が表示する情報と、その元になる計算の条件 |
| 2 | **なぜ見るか**（穴の発見にどう効くか） | 条件が仕様に書かれていなければ、そこが穴 |
| 3 | **語の定義**（初出の独自語だけ） | ここでいう「数字」＝画面に出る件数・日数 |

### 目的との接続を切らさない

このHTMLの目的は**仕様書の穴を見つけること**。読み手が「今読んでいるセクションが、その目的にどう効くのか」を見失ってはいけない。

§8ロール差を読んでいるときに「これは穴の発見にどう役立つのか」が分からないなら、②が書けていない。

### Skill独自語は初出で必ず定義する

| 語 | 定義 |
|---|---|
| **穴** | 仕様書の空白のうち、放置すると利用者層のいずれかが困るもの |
| **型1〜型6** | 空白の6分類（規定なし / 例外・境界未定義 / 画面間の概念不整合 / mock乖離 / 数字の定義欠落 / 導線の欠落） |
| **確度** | その穴候補をどこまで確認できたか（確度高 / 要確認 / 意図の可能性） |
| **利用者層** | 作業者 / 管理者 / 発注元（呼び名は `_プロジェクト設定.md` で定義する） |

型番号を単独で使わない。**「型5（数字の定義欠落）」のように必ず名前を添える。**

### 語を同じ解釈で使う

同じ語が別の意味で出てきたら、どちらかを言い換える。曖昧な語（判定・処理・対応・条件）は、**何の何かを補う**。

- ✕ 「判定の条件」→ ○ 「ログインを**拒否する**条件」
- ✕ 「数字の定義」→ ○ 「画面に出る**件数の集計条件**」

## 情報の出どころを見た目で区別する

読み手が「どこまで信じていいか」を、文章を読まずに判断できる状態にする。

## ジャンル × 確度のマトリクス

| ジャンル | 取りうる確度 | CSSクラス | 見た目 | 文体 |
|---|---|---|---|---|
| **事実**（構成・表示・操作） | 明記 | `kh-meiki` | 青の左罫＋淡い青地 | 断定してよい |
| | 実装のみ | `kh-jisso` | 実線枠 | 「実装ではこうなっている」 |
| **数字の定義**（集計・計算） | 明記 | `kh-meiki` | 同上 | 断定してよい |
| | 実装のみ | `kh-jisso` | 同上 | 「実装ではこう数えている」 |
| | **未定義** | `kh-ana` | **警告色** | 「定義が書かれていない」→ 穴候補型5へ |
| **挙動・遷移**（操作の結果） | 明記 / 実装のみ | 上に同じ | | |
| | 推測 | `kh-suisoku` | **点線枠**・文字薄め | 「〜と読める」「おそらく」 |
| **設計判断**（なぜこの形か） | **常にトレードオフ** | `kh-tag--trade` ＋対比表 | 案A/案Bの表 | **断定文を使わない** |
| **穴候補** | 確度高 / 要確認 / 意図の可能性 | `kh-ana` ＋ `kh-tag--kakudo` | 警告色＋確度ピル | 「確認が必要」 |

## 設計判断を断定しない理由

制約（規模・チーム・運用・納期）で答えが変わる。断定すると「正解を暗記する」学習になり、**判断力に繋がらない**。

対比表には必ず3行を入れる。

| | 案A | 案B |
|---|---|---|
| やったこと | | |
| 得たもの | | |
| **払ったもの** | | |

「払ったもの」が空欄の案は、まだ理解できていない証拠。埋まるまで書かない。

## 穴候補の確度3段階＋処置1つ

| ピル表示 | CSSクラス | 条件 |
|---|---|---|
| **確度高** | `kh-tag--k-high` | 他画面にも無く、git logに意図的変更なし、既存issueなし |
| **要確認** | `kh-tag--k-mid` | 他画面での担保が未確認、または仕様の意図が読み取れない |
| **意図の可能性** | `kh-tag--k-low` | git logに意図的変更あり、または回帰テストで固定されている |
| **起票不可** | `kh-tag--k-low` | **既存issueが同じものを扱っている**、または仕様にあって実装に無い（穴の逆方向） |

**「意図の可能性」は候補から外さない。**「人に聞くべき」に分類して残す（意図を見落とした誤起票を防ぐため）。

### 「起票不可」を4つ目として足した理由

確度3段階は「その空白がどこまで確認できたか」の軸。**既存issueとの重複は確度ではなく処置**なので、どの段階にも当てはまらなかった。

5候補のうち2件が既存issueと重複した回がある（重複の型は2つ。同一指摘の再掲と、仕様にあって実装に無い側）。**確度を上書きせず、処置として別に示す。**

- 表からは消さない。`<s>` で取り消し線を引き、担保状況の列に**issue番号と重複の根拠**を書く
- 「捨てた」ことも記録する（成果の測り方「捨てた件数」に加算する）
- 仕様にあって実装に無いものは**穴ではない**（仕様の空白ではないため）。実装バグとして別枠で記載する

## 出典の付け方

全セクションに必須。

```html
<span class="src">出典: spec/content/docs/spec/07-shift.md:159</span>
```

- `ファイル:行` 形式。現物に飛べる粒度で書く
- 複数根拠があるときは `/` で並べる
- **推測には「根拠:」を書く**（何から読み取ったか）。出典がないのに断定枠を使わない

## 文章スタイル

**品詞の数量を最小化する。** 以下を削る。

- 前置き
- 修飾語
- 抽象語
- 接続語
- 言い換えの重複

結論、理由、必要な例だけを書く。意味がすぐ届く文を優先する。**強度は「かなり」「おそらく」などの副詞で足さず、内容で出す。**

### 確度タグがあるので、ヘッジ副詞は書かない

**このHTMLでは特に重要。** 確度はタグと枠線が既に示している。文中で重ねると二重表現になる。

| | ✕ | ○ |
|---|---|---|
| 推測 | 「使われ方はおそらく〜画面」 | 「出社した管理者が朝一番に開く画面」（点線枠＋「推測」タグが確度を担う） |
| 実装のみ | 「実装ではこうなっている可能性が高い」 | 「実装ではこう数えている」 |
| 穴候補 | 「〜かもしれないので確認したほうがよさそう」 | 「〜が書かれていない。確認が必要」 |

不確かさは**タグ・枠線・`<span class="src">根拠:</span>`** の3つで表現する。文体で薄めない。

### 削る対象の実例

| 直す前 | 直した後 | 削ったもの |
|---|---|---|
| 使われ方は**おそらく**「〜」画面 | 出社した管理者が朝一番に開く画面 | ヘッジ副詞・前置き |
| 実装との乖離**の可能性が常にある**（〜6件検出した**実績あり**） | 実装と乖離する（〜6件検出） | 抽象語・冗長 |
| **この画面の本体は**サマリカード | 本体はサマリカード | 前置き |
| 改訂履歴で追える教材**になっている** | 改訂履歴で追える教材 | 補助動詞 |
| 完結していると**思うと**誤る | 完結していると**読むと**誤る | 曖昧な動詞 |

### その他

- 一文一義。読点4つ／3行を超えたら分割
- 結論を先頭に置く
- 用語は1概念=1語で固定
- 禁止句: 「〜することが重要です」「さまざまな」「以下に示します」「〜と言えるでしょう」「総じて」、根拠なき誇張副詞（劇的に・大幅に）

## 利用者プロファイル連動

既習概念は説明なしで使う。未習概念には必ず噛み砕きを添える。判定は利用者プロファイル。

- 英字の識別子は**英単語に分解して意味を示す**（`advisory lock` = advisory 助言的 + lock 錠 →「DBが強制する錠ではなく、アプリ同士の申し合わせでかける錠」）
- 暗記させない。「覚えなくていい、忘れたらまた読めばいい」

## 幅の決め方 — コンテナは1本。行長は内側の余白で作る

**セクションごとに幅を切り替えない。** 幅が変わると左端が動き、読み進めるたびに視線の基準線が左右にずれる。

**行長の制限は `max-width` ではなく、背景ブロックの右内側余白で作る。**

```css
padding-right: max(32px, calc(100% - var(--kh-measure) - 32px));
```

| 画面 | 挙動 |
|---|---|
| 広い | 右余白が伸びて、行長は50文字で頭打ち |
| 狭い | `max()` が32pxを選び、行長が自然に縮む |

背景が途中で切れないので、右側は「死んだ空白」ではなく**ブロックの内側の余白**になる。

### 行長の値

`--kh-measure: 50em`。本文0.9rem基準で全角50文字ぶん（720px）。日本語の適正行長（40〜50文字）の上限。

- 狭いと改行が増えて文字が詰まる
- 広いと行を追う目の移動が大きくなる

`px` ではなく `em` で持つ。根拠が「文字数」なので、font-size を変えても文字数が保たれる。

### 表・画像・コード

幅を制限しない。中身が画面に応じて伸縮する。

### 実測

| 画面幅 | 見出し左端 | 背景幅 | テキスト幅 | 行長 |
|---|---|---|---|---|
| 1585 | 233 | 1120 | 720 | 50文字 |
| 1265 | 73 | 1120 | 720 | 50文字 |
| 1009 | 24 | 961 | 720 | 50文字 |
| 845 | 24 | 797 | 720 | 50文字 |
| 685 | 24 | 637 | 597 | 41文字 |
| 485 | 24 | 437 | 397 | 28文字 |

全幅で見出し左端が1本に揃い、横スクロールも発生しない。

### やってはいけない

- **要素ごとに `max-width` を掛ける** → 背景が途中で切れ、右に空白の帯ができる（2026-07-31に実際に起きた）
- **セクション種別で幅を切り替える** → 左端が動いて基準線が崩れる（同日、これも起きた）
- セクションごとに数値をその場で決める → 再現性が失われ、生成のたびにバラつく

### レスポンシブ

| 画面 | `--kh-section-y` | その他 |
|---|---|---|
| 〜900px | 72px | ブロックpadding縮小 |
| 〜768px | **64px** | 見出し縮小、`kh-deflist`縦積み、表は横スクロール、キャラ62px |

表はモバイルで縦積みにしない。**どの列の値か読めなくなる**ため、横スクロールで守る（セルは `min-width: 8em`）。

## UIの扱い

- キャラ（右下）はドラッグで移動可。位置はlocalStorageに保存
- **`transform` を使わない**（矩形計算が狂いドラッグが壊れる）
- `KH_PREFIX` は画面IDごとに必ず変える（localStorageの衝突防止）
- 印刷時はUI一式を非表示（`@media print`）

## セクション別の書き方

学習者が実際に詰まった3箇所。**表の作りが誤読を生んでいた**のが共通の原因。

### §5 — 「無い操作」を表の行にしない

| | |
|---|---|
| 起きたこと | 「『あとで変更する』をスキップする」を操作の行として立てたら、実装済みの機能だと読まれた |
| 原因 | 表の左端に操作名が並ぶと、存在する操作に見える。「結果」列に「操作が無い」と書いても届かない |
| 直し方 | **探して無かったものは表から外し、表の下に1文で書く** |

> スキップも、ログイン画面へ戻るリンクも無い。この画面に来たら送信以外の出口が無い。

あわせて**操作名を二重に修飾しない**。「『あとで変更する』をスキップする」は「あとで変更する」ボタンのことだが、動詞が二重で意味が壊れた。**ボタンの表示名をそのまま書く。**

### §7 — 3列にする。「どこ」をファイルパスで書かない

| | |
|---|---|
| 起きたこと | 「§7自体が理解しづらい」と指摘された |
| 原因 | 2列目が `backend/internal/infra/password/hash.go:22-31` のようなパスだった。**パスは場所の説明になっていない** |
| 直し方 | 3列にする |

| この画面で見える概念 | どこが決めているか | どう決まっているか |
|---|---|---|
| パスワードの長さ | バックエンドの共通処理（画面ではない） | 8〜128文字。文字種は見ない |
| この画面へ来る条件 | **ログイン画面** | `passwordChanged` が false なら送られる |

中央は**人間が指させる場所**（画面名・システム領域）、右は**決定の中身**。ファイルパスは出典として下に落とす。

### §11 — コマンドの前に「何が起きるか」を書く

| | |
|---|---|
| 起きたこと | 「毎回このパートは何をすればいいのか分からない」と申告され、3画面連続で放置されていた |
| 原因 | shellコマンドだけが並び、**打つと何が起きるかが書かれていなかった** |
| 直し方 | **手順 → 何が起きるか → なぜやるか** の順で書く |

- **手順**: 起動コマンドを1行だけ先頭に置く
- **何が起きるか**: 自分のPCの中で何が動くか・所要時間・開くURL・止め方・**本番に繋がらないこと**
- **なぜやるか**: 候補は読解で止まっている。実物で再現して初めて事実になる
- そのうえで「この画面で確認できること」を3列の表（何を／どうやって／分かること）で出す

利用者プロファイルの「具体的な手順 → なぜ の順を厳守」に沿わせている。

## プレースホルダは固有名にする（2026-08-14 の事故から）

| | |
|---|---|
| 起きたこと | §9のトレードオフ表が空欄のまま提出され、§10には§9の中身が入っていた。**§10本来の中身（穴候補3件）はどこにも書き込まれていなかった** |
| 原因 | `{{rows}}` が同名で6箇所あり、`replace(..., 1)` を上から順に消費したため §5→§7→§8 で使い切り、§9以降がずれた |
| 直し方 | **セクション名を含む固有名にする**（`{{rows_s5_操作}}` `{{rows_s10_穴候補}}` 等）。同名を増やさない |

**同じ値が入るものは同名でよい**（`{{画面ID}}` `{{画面名}}` `{{YYYY-MM-DD}}` など一括置換で正しく動く）。
**別の中身が入るのに同名だと事故る**（`{{論点}}` は §9のトレードオフと §10の相談文案で別物だったため分離した）。

トレードオフが2本以上必要なら `{{s9_2本目_...}}` のように連番を付けて足す。

## 生成物は開いて検証してから提出する

**「残プレースホルダ0」は完成の判定に使えない。** 上の事故は、プレースホルダが全部埋まった状態で起きた。

| 見るもの | 合格条件 |
|---|---|
| 空セル | 0（意図的な空欄を除く） |
| 表の列数 | 想定と一致（案A/Bなら3列、A/B/Cなら4列） |
| セクションを跨いだ混入 | §10に「案A」等の§9用語が出てこない |
| JSエラー | 0 |
| 横スクロール | なし |
| 画像 | `naturalWidth > 0` |

**§9は「払ったもの」が空でないことを必ず見る。** 空欄の案は理解できていない証拠なので、そのまま出してはいけない。
