# visual-review

Playwright で画面を実際にレンダリングしてスクリーンショットを撮影し、**見た目そのもの**を対象に次の3点をレビューする。

1. **デザイン品質**: 表示崩れ、レスポンシブ破綻、コントラスト、視覚的一貫性
2. **モック乖離**: モック（HTML / 画像カンプ / Markdown）と実描画の見た目の差
3. **仕様乖離**: 仕様書・Storybook・ルーティング定義と実装の差

責務の境界:
- `design-review`: コードの静的解析（トークン準拠、Props 設計）
- `mock-drift`: モック↔実装の**コード**比較（DOM 構造・クラス名）
- **`visual-review`（本スキル）: ブラウザで実際にどう見えるかの比較**

## 前提条件

- Claude Code 環境
- Node.js もしくは Bun（Playwright 実行用）
- 開発サーバーを起動できること（または静的ビルド / デプロイ済み URL）
- `gh` CLI（GitHub Issue 出力時）

## 引数

- **引数なし**: 撮影対象を自動収集し、`AskUserQuestion` で確認してから実行
- **URL / パス指定** (例: `/visual-review http://localhost:3000/settings`): その画面のみ
- **設定ファイルパス**: その設定で撮影

**フラグ:**

- `--setup`: `.claude/visual-review.json` の生成（または更新）のみ行って終了
- `--capture-only`: 撮影して manifest を出力するまで。レビューはしない
- `--review-only`: 既存の `<outDir>/shots/` をレビューする（再撮影しない）
- `--full`: 撮影マトリクス全件を読み込んでレビューする（フェーズ4の段階的読み込みを無効化。**画像トークンを大量消費するため明示指定時のみ**）
- `--auto`: 自律実行モード。`AskUserQuestion` を使わず既定値で進め、採用した前提をレポートの「## 前提」に列挙する

## フェーズ1: 環境準備

1. 設定ファイルを探す: `.claude/visual-review.json` → 無ければ後続フェーズで生成する
2. Playwright の有無を確認する
   - `node_modules/playwright` またはグローバルの有無をチェック
   - 未導入なら `AskUserQuestion` で導入可否を確認し、承諾されたら導入する（詳細は `references/setup.md`）
3. 開発サーバーの状態を確認する
   - `baseUrl` に到達可能かチェック（`curl -sS -o /dev/null -w '%{http_code}'`）
   - 到達不可なら `package.json` の scripts から dev サーバー起動コマンドを推定し、**ユーザーに起動を依頼するか、バックグラウンドで起動する**
4. **フロントエンドのビルド成果物が最新か確認する（ビルドが必要な構成では必須）**
   - CSS / JS をビルドして配信する構成（Tailwind CLI + esbuild、Vite の本番ビルド、HALT の `static/dist/` 等）では、**ビルドが古いと実描画がソースと食い違い、レビュー結果が嘘になる**
   - ソース（`static/src/`, `assets/` 等）とビルド成果物（`dist/`）の mtime を比較し、成果物が古ければビルドを実行する
   - templ のように**テンプレートからコード生成する構成では生成物の再生成も確認する**（`templ generate`）
5. デザイン基盤ファイルを検出し、レビューの判断基準として読み込む
   - CSS フレームワーク設定（`tailwind.config.*`, `uno.config.*`）
   - デザイントークン / テーマ定義（`theme.ts`, `tokens.*`, `variables.css`）
   - グローバルスタイル（`global.css`, `base.css`, `app.css`）

## フェーズ2: 撮影対象の収集と突き合わせ

**6つの収集元をすべて探索する。** 単に対象を集めるだけでなく、**収集元どうしの差分がそのまま乖離の検出結果になる。**

| 優先 | 収集元 | 探索対象 |
|-----|-------|---------|
| 1 | 設定ファイル | `.claude/visual-review.json` の `targets` |
| 2 | Storybook | `.storybook/`、`storybook-static/index.json`、`**/*.stories.{ts,tsx,js,jsx,svelte,vue}` |
| 3 | クライアントルーティング | Next.js `app/`・`pages/`、Nuxt `pages/`、SvelteKit `src/routes/`、Astro `src/pages/`、React Router / Vue Router のルート定義 |
| 4 | サーバーサイドルーティング | Go（Gin / Echo / chi）の `router/`・ハンドラ登録、Rails `config/routes.rb`、Laravel `routes/`、Django `urls.py`、PHP / ERB / Blade / Templ のテンプレート配置 |
| 5 | 仕様書の画面一覧 | `docs/design/screens.md`、`docs/**/*.md` の画面一覧・画面遷移図 |
| 6 | モック | `mocks/`, `mock/`, `docs/mocks/`, `design/mocks/`, `.mocks/`（`__mocks__/` はテスト用途のためスキップ） |

**サーバーサイドルーティングから対象を採る際の除外基準:**

- **GET のページルートのみを対象にする**
- API ルート（JSON を返す。例: `/api/v1/...`、Huma / OpenAPI 登録分）は視覚レビュー対象外
- **POST / PUT / DELETE のアクションルートは撮影しない**（副作用があるため。データを壊す）
- 認証・権限で分岐するルートは `auth` 設定で撮影する

### 2.1 対象の確定

1. 各収集元から「画面 / コンポーネント状態」の一覧を作る
2. Storybook が存在する場合は **stories を優先採用する**。ローディング / エラー / 空状態やバリアントは URL では到達できないため、カバレッジが最も高い
3. **Storybook が無いサーバーサイドレンダリング構成（HALT 等）では、フラグメント撮影を使う**
   - HTMX が部分更新で返す HTML を単体で描画して撮影できる（`targets[].fragment: true`）
   - `HX-Request: true` を付けて GET し、返った部分 HTML をラッパー（`fragmentWrapper`）に埋め込んで撮影する
   - **フルページとフラグメントの両方を撮ることに意味がある**。HATEOAS 設計では「部分だけ差し替わったときに崩れる」のが実際のバグ源になる
   - 対象はページルート（GET）のみ。アクションルートは副作用があるため撮影しない
   - 詳細は `references/setup.md` の HALT 節を参照
4. 動的セグメント（`[id]`, `:slug`）は設定ファイルの値を使う。未設定ならユーザーに確認する（`--auto` 時はシード値を推定し前提として記録）
5. 認証が必要な画面は `auth` 設定を使う（`references/setup.md` 参照）
6. 各対象の収集元を `origin` に記録する（`config` / `storybook` / `route` / `fragment` / `spec` / `mock`）
7. 確定した対象で `.claude/visual-review.json` を生成・更新する（テンプレート: `templates/visual-review.json`）

### 2.2 モックと画面の対応付け

1. モックファイル名・見出しから対応する画面 / コンポーネントを推定し、`targets[].mock` に設定する
2. 対応先が曖昧な場合は `AskUserQuestion` で確認する（`--auto` 時は最も近いものを採用し前提に記録）
3. モックの種別ごとに扱いが変わる（`scripts/capture.mjs` が自動判定する）

| 種別 | 例 | 扱い |
|-----|---|-----|
| HTML / CSS モック | `mocks/home.html` | **実装と同じビューポートで撮影し、画像同士を並べて比較** |
| 画像カンプ | `mocks/home.png`, `.jpg` | 撮影せず、レビュー時に実装スクショと並べて読み込む |
| Markdown モック | `mocks/home.md` | 画像化せず本文を読み、記述された要素・文言と実描画を照合する |
| URL モック | Figma プレビュー等の公開 URL | HTML モックと同様に撮影 |

### 2.3 収集元の突き合わせ（乖離候補の抽出）

以下の差分をすべて記録する。これはフェーズ5のレポートに載せる:

- **未実装**: 仕様書 / モックにあるが、対応するルートが存在しない
- **仕様未記載**: ルートが存在するが、仕様書の画面一覧に無い
- **モック未整備**: 実装された画面に対応するモックが無い
- **モック取り残し**: モックがあるが対応実装が無い（または削除済み画面のモックが残っている）
- **story 欠落**: 仕様書に定義された状態（ローディング・エラー・空・バリアント）に対応する story が無い
- **到達不能**: 仕様書に記載があり実装もあるが、導線が無く URL 直打ち以外で到達できない

## フェーズ3: 撮影

`scripts/capture.mjs` を使う。**撮影は全マトリクスを一括で行う**（撮影自体はトークンを消費しない）。

```bash
# 全ターゲット + モックを撮影
node .claude/skills/visual-review/scripts/capture.mjs .claude/visual-review.json

# 認証済み状態を先に作る（auth.login 設定時、初回のみ）
node .claude/skills/visual-review/scripts/capture.mjs .claude/visual-review.json --auth

# 一部だけ撮り直す
node .claude/skills/visual-review/scripts/capture.mjs .claude/visual-review.json --only home,settings
```

- Bun がある場合は `bun` で実行してよい
- 既定マトリクス: **desktop / tablet / mobile × light / dark**（1 画面あたり最大 6 枚）
- HTML モックは各ビューポートで 1 回撮影される（テーマ非依存）
- 縦長ページはビューポート単位に自動スライスされる（1 枚が巨大画像にならないようにするため）
- 出力: `<outDir>/shots/` と `<outDir>/manifest.json`
- 撮影失敗は manifest の `failures` に記録され、処理は継続する。**失敗した画面は「撮影不可」としてレポートに必ず載せる**（多くの場合それ自体が不具合）

## フェーズ4: レビュー（段階的読み込み・必須）

**画像 1 枚あたり約 1.5k トークンを消費する。** 全件を無条件に読み込んではならない。`--full` 指定時を除き、次の順で進める。

1. `manifest.json` を読み、撮影結果の全体像（画面数・枚数・モック有無・失敗）を把握する
2. `TaskCreate` で画面単位のタスクを作る
3. **第1パス（デザイン品質）**: 全画面の `desktop × light` のみを読み込む（1 バッチ最大 8 枚）。バッチごとに所見を `<outDir>/findings.md` へ追記してから次のバッチへ進む
4. **第2パス（モック照合）**: モックがある画面のみ、**実装と対応モックを同一バッチで並べて読み込む**（1 バッチ最大 4 ペア）。Markdown モックは本文を読んで照合する
5. **第3パス（レスポンシブ）**: 第1・2パスで問題が出た画面 + レイアウトが複雑な代表画面について `mobile` を読み込む
6. **第4パス（ダークテーマ）**: ダークテーマ実装がある場合、色の指摘があった画面 + 主要画面の `dark` を読み込む
7. `tablet` は第1・3パスでレスポンシブの破綻が疑われた画面のみ
8. 各パスで打ち切る場合は、レポートに**未確認の範囲を明記する**

チェック観点の詳細は `references/check-criteria.md` を参照。

主要カテゴリ:
- **表示崩れ**: オーバーフロー、要素の重なり、はみ出し、意図しない改行・文字切れ
- **レスポンシブ**: 横スクロール発生、タップターゲット、折り返し後のレイアウト
- **視覚的一貫性**: 実描画された色・字形・余白がデザイン基盤と一致しているか
- **アクセシビリティ**: 実際の描画色でのコントラスト比、フォーカスリングの視認性
- **状態表現**: ローディング / エラー / 空状態が意図どおり描画されているか
- **モック照合**: レイアウト構造・要素の有無と配置・色と余白・文言の一致
- **仕様照合**: 仕様書に記述された画面構成・要素・文言と実描画の一致
- **部分更新の整合**（HTMX 等）: フラグメント単体で崩れないか、スワップ後に周辺と揃うか
- **Web Components の描画**（Lit 等）: カスタム要素が空のまま / フォールバック表示のまま描画されていないか

## フェーズ5: レポート生成

1. `AskUserQuestion` で出力先を確認する（`--auto` 時は GitHub Issue）
   - **GitHub Issue**（推奨）: タイトル `visual-review: 実描画レビュー(<ブランチ名>, <YYYY-MM-DD>)`
   - **ローカル MD ファイル**: `visual-review-report.md`
   - **コンソール出力**: 会話に直接出力
2. レポート形式は `templates/report.md` を参照
3. 指摘には**該当スクリーンショットのパスを必ず添える**。モック乖離は実装側とモック側の両方のパスを示す
4. 要約と、レビュー対象外にした範囲をユーザーに報告する

## 重大度の基準

| 重大度 | 基準 |
|-------|------|
| 🔴 重大 | 実描画で操作不能・情報が読めない、要素の重なりによる隠蔽、撮影不可（描画エラー）、WCAG A 不適合のコントラスト、モックの主要要素が実描画に存在しない |
| 🟠 重要 | レスポンシブ破綻（横スクロール・はみ出し）、モック / 仕様書との明確な不一致、状態表現の欠如、ダークテーマでの視認性不足 |
| 🟡 提案 | 余白リズムの不整合、トークンから外れた実描画値、モックとの軽微なズレ、インタラクション強化 |
| 🟢 軽微 | 微細なスタイルズレ、文言の表記ゆれ |

## ルール

- **推測で指摘しない。** 指摘は必ず実際のスクリーンショットで確認した内容に基づき、画像パスを根拠として示す
- スクリーンショットで見えない事柄（コード上のトークン違反など）は本スキルの対象外。`design-review` / `mock-drift` に委ねる
- モック乖離は**モックを「あるべき姿」の参照とする**。ただしモックが古く実装側の変更が妥当な場合は「モックを更新」を推奨として明記する
- モックと実装のピクセル一致は求めない。レイアウト構造・要素の有無・配置関係・デザイン値の一致を見る。フォントレンダリングや 1〜2px の差は指摘しない
- 撮影の非決定性に注意する。アニメーション・カルーセル・日時表示・ランダム表示は `hide` / `actions` で安定化させ、それでも不安定なら指摘せず「要目視確認」として記録する
- デザイン基盤が未検出の場合は、モック側の値、次に一般的な UI/UX ベストプラクティスを基準とする
- 🔴🟠 は必ずレポートに含める。🟡🟢 は明確なメリットがある場合のみ
- 撮影成果物（`<outDir>`）は `.gitignore` に追加する。未追加なら追加を提案する
- **ビルドが必要な構成でビルドが古い状態のまま撮影しない。** 実描画がソースと食い違い、レビュー結果が無効になる
- **Web Components が空で描画された場合、デザインの問題として指摘する前に原因を切り分ける。** バンドル未ビルド・JS エラー・カスタム要素の未定義が原因なら実装またはビルドの問題として報告する
- shadow DOM 内部は外側の CSS が届かない。`hide` は shadowRoot にも注入されるが、`::part` を持たない内部要素の細かな制御はできない。安定化できない場合は「要目視確認」として記録する
- `TaskCreate` / `TaskUpdate` で進捗を管理する
