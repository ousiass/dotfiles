# visual-review チェック観点

スクリーンショット（実描画）から判定できる観点のみを扱う。コードを読まないと分からない事柄は `design-review` の担当。

## 1. 表示崩れ

- テキストがコンテナからはみ出している / 見切れている
- 要素同士が重なって内容が隠れている
- 長い文字列（メールアドレス、URL、日本語の連続文）で折り返しが破綻している
- 意図しない位置での改行、1 文字だけの行送り
- ellipsis（`…`）が意図せず発生し情報が失われている
- 画像のアスペクト比が崩れている / 引き伸ばされている
- 画像・アイコンが読み込めず alt テキストや破損アイコンが出ている
- Web フォントが適用されずフォールバックで描画されている（字形・字幅が他画面と異なる）
- ボタンやカードの高さが揃っていない（グリッド内で不整合）
- z-index の破綻（モーダル / ドロップダウン / ヘッダーの重なり順）

## 2. レスポンシブ

- 横スクロールが発生している（**mobile で最優先に確認**）
- 固定幅要素がビューポートを超えている（テーブル、コードブロック、埋め込み）
- タップターゲットが小さすぎる（目安 44×44px 未満）
- 要素間の間隔が近すぎて誤タップしやすい
- 折り返し後にラベルと入力欄の対応が読み取れなくなっている
- ナビゲーションがモバイルで崩れている / メニューが開けない状態で描画されている
- 中間ブレークポイント（tablet）でだけ余白が極端に空く / 詰まる

## 3. 視覚的一貫性

- 実描画された色がデザイン基盤（トークン / テーマ定義）の値と一致しているか
- 同一の意味を持つ要素（プライマリボタン等）が画面間で同じ見た目か
- 余白のリズムがスペーシングスケールに沿っているか（目視で不規則な余白）
- 角丸・シャドウ・境界線の太さが画面間で揃っているか
- タイポグラフィの階層（見出しサイズの差、行間）が一貫しているか
- 画面間で同じ役割の要素の配置が揃っているか（ヘッダー位置、アクションボタンの並び）

## 4. アクセシビリティ（実描画で判定できる範囲）

- テキストと背景の**実際の描画色**でのコントラスト比（本文 4.5:1、大きな文字 3:1）
- プレースホルダー・補助テキスト・disabled 状態の文字が薄すぎて読めない
- 色のみで状態を区別している（エラー / 成功が色だけ）
- フォーカスリングが描画されない / 背景に埋もれて見えない
- ダークテーマでのコントラスト不足（**ライトテーマで通ってもダークで落ちることが多い**）
- 画像内テキストに情報が閉じ込められている

## 5. 状態表現

Storybook がある場合は stories 単位で確認する。URL のみの場合は到達可能な状態に限定し、未確認を明記する。

- ローディング状態（スケルトン / スピナー）が描画されるか
- エラー状態のメッセージが表示され、復帰手段（再試行ボタン等）があるか
- 空状態（データ 0 件）が説明文付きで描画されるか（空白のままになっていないか）
- disabled 状態が視覚的に区別できるか
- 入力バリデーションエラーが該当項目の近くに表示されるか

## 6. モック照合

**モックを「あるべき姿」の参照とする。ピクセル一致は求めない。**

判定する:
- レイアウト構造（セクションの並び順、カラム構成、グリッドの列数）
- 要素の有無（モックにある要素が実描画に存在するか / モックに無い要素が追加されていないか）
- 配置関係（左右・上下の位置関係、揃え、階層）
- デザイン値（色・font-size・余白・角丸が目視で明確に異なるか）
- 文言（見出し・ラベル・ボタン文字・placeholder・空状態メッセージ）
- ナビゲーション / メニュー（項目の網羅・順序・階層・アクティブ状態）
- 状態表現（モックに描かれた disabled / loading / error / empty が実装にあるか）

指摘しない:
- 1〜2px の差、フォントレンダリングの差
- ダミーテキスト / ダミー画像の内容差
- モック側が明らかに古く、仕様変更が反映されている箇所（この場合は「モックを更新」として記録する）

Markdown モックの場合は、記述された要素・Props・状態・文言が実描画に存在するかを照合する。

## 7. 仕様照合

- 仕様書に記述された画面の構成要素が実描画に存在するか
- 仕様書の文言（見出し・ラベル・エラーメッセージ）と実描画が一致するか
- 画面遷移図どおりの導線（リンク・ボタン）が描画されているか
- 仕様書に定義された状態が実描画で確認できるか
- 仕様書に無い要素が追加されていないか（仕様未記載として記録）

## 8. 部分更新 / Web Components（HTMX + Lit などのサーバー内蔵構成）

### フラグメント単体（`fragment: true` で撮影した画像）

- フラグメント単体で見たときにレイアウトが破綻していないか（親のグリッド / flex 前提のスタイルが単体では崩れる）
- フラグメント内で完結すべき情報（見出し・件数・空状態）が欠けていないか
- フルページ版とフラグメント版で見た目が食い違っていないか（同じ URL の2枚を比較する）
- フラグメントに `<html>` / `<head>` が混入していないか（フルページを返してしまっている＝分岐の実装ミス）

### スワップ後の状態（`actions` で操作してから撮影した画像）

- 差し替わった領域と周辺の余白・境界線・角丸が揃っているか
- OOB スワップの対象（件数バッジ等）が更新後の値と整合しているか
- 差し替え後に重複要素が生まれていないか（`hx-swap` の指定ミス）
- ローディングインジケータが出たまま残っていないか

### Web Components

- カスタム要素が**空のまま描画されていない**か（バンドル未ビルド / JS エラー / 未定義が原因。デザインではなく実装・ビルドの問題として切り分ける）
- フォールバック表示（スロットの初期内容）のまま止まっていないか
- shadow DOM 内部のスタイルが外側のデザイントークンと揃っているか（トークンが shadow 境界を越えるには CSS カスタムプロパティが必要）
- コンポーネント境界で余白が二重になっていないか
- 親（サーバー描画側）の枠と子（Web Component 側）の高さが噛み合っているか

## 撮影が失敗した場合の扱い

manifest の `failures` は必ずレポートに載せる。原因ごとに扱いが変わる:

| 失敗内容 | 判定 |
|---------|-----|
| ページが 4xx / 5xx を返す | 🔴 実装またはルート定義の不具合 |
| `waitFor` セレクタがタイムアウト | 🔴 想定要素が描画されていない可能性 |
| ナビゲーションタイムアウト | 🟠 パフォーマンス問題の可能性（`web-perf` を推奨） |
| JS エラーで白画面 | 🔴 実装の不具合 |
| モックファイルが見つからない | 🟠 モック未整備 / 設定の誤り |
| 認証切れ（ログイン画面にリダイレクト） | 設定の問題。`--auth` を再実行して撮り直す |
| フラグメント取得が 4xx / 5xx | 🔴 ページルートの `HX-Request` 分岐の不具合、またはルートが存在しない |
| カスタム要素が空で撮影された | ビルド未実行 / JS エラー / 未定義。🔴 実装またはビルドの問題 |
