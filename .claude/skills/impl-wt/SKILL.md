# impl-wt

## 前提条件

- Claude Code 環境
- `git`, `gh` CLI
- `jq`

## 引数

- **Issue 番号** (例: `/impl-wt #123`): GitHub Issue から要件を取得
- **Issue URL** (例: `/impl-wt https://github.com/owner/repo/issues/123`): 同上
- **テキスト** (例: `/impl-wt ユーザー認証機能を追加`): テキストを要件として扱う
- **引数なし**: ユーザーに要件をヒアリング

## 禁止行動（最重要）

以下に該当した場合はそのフェーズをやり直す。コンテキスト節約や軽微変更を理由にした省略は認めない。

- 「あとで実装」「TODO で残す」「別 PR で対応」を理由にサブステップ（2-1〜2-7）を省く
- ユーザーへの宣言なしにフェーズ・サブステップを飛ばす（サイレントスキップ）
- テストを未実装・ダミー（`expect(true).toBe(true)` 等）のままコミットする
- `review` エージェントを呼ばずに自己レビューで済ませる
- **2-6 の検証ゲートを実行せずコミットする / FAIL のままコミットする**（LLM の自己判断でゲートを代替しない。「明らかに直っているので不要」は禁止）
- **ゲートを通すために検証対象そのものを緩める**（テストの削除・アサーションの弱体化・`verify-scope: allow` の乱用・lint ルールの無効化）。直すべきは実装であってゲートではない
- lint/format を試行せずスキップする（実行 → 該当設定なしを確認した場合のみスキップ可）
- **スコープ外発見を「あとで報告」「PR 本文に列挙」「最終サマリで言及」だけで済ませる**（その場で `.sweep/spinoff-draft.jsonl` に append していない時点で違反。PR 本文や最終報告に「発見したが未 issue 化」と書くこと自体を禁止する）
- **発見のたびに `/spinoff-issue` を個別に呼ぶ**（起票はフェーズ3 の `--batch` 1 回に集約する）

スコープを縮小したい場合は、フェーズの省略ではなくフェーズ1のスコープ分割からやり直し、ユーザーに確認する。

実装中に**現スコープと独立した発見**（無関係なバグ・スコープ外の改善・別途必要なリファクタ等）があれば、**発見した瞬間に** worktree ディレクトリ内の `.sweep/spinoff-draft.jsonl` へ 1 行 append する:

```bash
mkdir -p .sweep
jq -nc --arg parent "<親Issue番号>" --arg type "<bug|feat|chore|refactor|docs>" \
       --arg title "<要約>" --arg files "<file:line>" --arg why "<現スコープに混ぜない理由>" \
       '{parent:$parent, type:$type, title:$title, files:$files, why:$why}' >> .sweep/spinoff-draft.jsonl
```

**ここでは Issue を作らない**（`/spinoff-issue` を呼ばない）。起票はフェーズ3 で 1 回だけまとめて行う。「記憶から落ちる／PR 本文の列挙で代替する」事故はファイルに残すことで防げるので、その場で起票する必要はない。**append 自体を後回しにするのは従来どおり禁止**（サブステップ末尾・スコープ末尾で思い出してまとめて書くのは不可）。フェーズ1で取得した親 Issue 番号は必ず `parent` に入れ、親なし（テキスト起動）の場合のみ空文字にする。`.sweep/` は作業ファイル置き場なのでコミットに含めない。

## フェーズ1: 要件分析とスコープ分割

1. 引数から要件を取得する
   - Issue: `gh issue view` で本文・コメントを読み取る
     - 取得結果の `assignees` を確認する。**自分以外の assignee が既にいる場合は、そのユーザー名を明示してユーザーに「他の担当者が既に assign されているが着手して良いか」を確認する。** 承認が得られたら次に進み、承認されない場合はここで作業を中断する
     - 上記の確認をクリアしたら `gh issue edit <Issue番号> --add-assignee @me` で自分を assignee に追加する（着手宣言。既存 assignee は保持され、自分が既に含まれていれば no-op）
   - テキスト: そのまま要件として扱う
   - 引数なし: ユーザーにヒアリング
2. **repo プロファイルを取得する**（仕様は `impl` の `references/repo-profile.md`）
   - `~/.claude/skills/impl/scripts/verify-scope.sh --profile-path` でパスを得る
   - 存在し、かつ破棄条件（同 reference 参照）に当たらなければ**そのまま使い、探索を一切行わない**
   - 無い / 古い場合のみ生成する（test / lint / format コマンド、仕様書パス、テスト配置規約、パッケージマネージャ）
   - **プロファイルのキーは git common dir なので、同一リポジトリの worktree はすべて同じものを共有する。** worktree を作るたびに探索し直さない
3. 仕様書を確認する
   - プロファイルの `spec_paths` を読む。Issue 本文にリンクされたドキュメントがあれば併せて読む
   - 見つかった仕様書の内容を要件と照合し、実装の入力とする
   - 仕様書が見つからない場合はそのまま進める
4. 現在のブランチをベースブランチとして記録する（PR のマージ先）
   - `git branch --show-current` を実行し、結果をユーザーに「ベースブランチ: <ブランチ名>」と明示的に表示する
   - このブランチ名をフェーズ3のPR作成時まで保持する
5. 作業ブランチ名を決定する（命名規則は `references/branch-naming.md` を参照）
6. **git worktree を作成する**（手順は `references/worktree-setup.md` を参照）
7. **コンテキストパックを作成する**（仕様は `impl` の `references/context-pack.md`）
   - **worktree ディレクトリ内で**、**サブエージェントは立てずに** Grep / Glob / Read で「類似実装 / この層の規約 / 触るファイル / テストの作法」を集め、見出し固定・60 行以内にまとめる
   - このパックはフェーズ2 の 2-1 / 2-2 / 2-3 すべてのプロンプトに埋め込む
8. 要件を「独立して実装・テストできる単位」に分割し、**各スコープに type（`fix` / `feat` / `refactor` / `docs` / `test` / `chore`）を付ける**
   - type は 2-6 の検証ゲートに渡す。**バグの修正を含むスコープは `fix`**（回帰テストの有無が機械的に検査される）
9. 依存関係を整理し実装順を決定
10. TaskCreate でタスクを作成

- コードベースの探索・理解を行い要件を正確に把握する
- 不確定な仕様はユーザーに確認する
- 破壊的変更がある場合は下位互換性についてユーザーに確認する

## フェーズ2: 実装サイクル（各スコープで繰り返し）

**重要: フェーズ2のすべてのサブエージェント呼び出しで worktree パスを作業ディレクトリとして指定すること。**

**各スコープ開始時に `TaskUpdate` で該当タスクを `in_progress` にする。**

#### 2-1: Plan
- `Plan` エージェントで実装計画を立てる
- 変更箇所、影響範囲、テスト要件を明確にする
- プロンプトに worktree パスとコンテキストパックを含める

#### 2-2: Develop
- `develop` エージェントで実装（テスト含む）
- 最小限の変更で要件を満たす
- プロンプトに worktree パスとコンテキストパックを含める
- **`fix` 型スコープでは fail-first を守る**: 先に不具合を再現するテストを書いて**落ちることを確認**し、その後に修正して緑にする。テストが最初から通ってしまう場合は再現できていないので、テストを書き直す
- **本番動作するコードを書くこと。以下は実装完了とみなさない：**
  - モック・スタブ・ダミーだけのテスト（実コードなし）
  - `TODO`, `NotImplementedError`, `pass`, `throw new Error("not implemented")` で埋めた関数
  - インターフェース・型定義だけで中身がない実装

#### 2-3: Review
- `review` エージェントでコードレビュー（プロンプトは `impl` の `templates/review-prompt.md` の形で渡す）
- 要件適合、コード品質、テスト十分性を評価
- プロンプトに worktree パスを含める
- **未実装チェック**: モック/スタブのみ、TODO/NotImplementedError、空の関数本体がないか確認

#### 2-4: 改善サイクル
- レビュー指摘あり → `develop` で修正 → `review` で再レビュー → 指摘なしまで繰り返す
- **2 周目以降は `impl` の `templates/review-prompt.md` の「前回の指摘と対応結果」を必ず付ける**（付けないと同じ指摘と同じ直し方を往復する）

#### 2-5: Format & Lint
- プロジェクト設定（プロファイルの `format_cmd`）に従い変更ファイルに format/lint を実行
- **worktree ディレクトリ内で** format/lint コマンドを実行する
- 設定が見つからない場合はスキップ

#### 2-6: 検証ゲート（必須）
- **コミット前に必ず実行する。スキップ不可。**
- **worktree ディレクトリ内で**実行する（スクリプトは実行ディレクトリのリポジトリルートを対象にする）

```bash
~/.claude/skills/impl/scripts/verify-scope.sh --type <このスコープの type>
```

- 検査するのは 4 点: 追加行の未実装パターン / `fix` 型の回帰テスト有無 / テスト exit code / lint exit code
- **exit 0 になるまでコミットしない。** FAIL が出た場合:
  1. FAIL の内容（テスト出力・該当 file:line）を**そのまま** `develop` に渡して修正させる
  2. 再度ゲートを実行する。**緑になるまで上限なしで繰り返す**
  3. **同じ FAIL が 2 回続いたら、同じ直し方を繰り返さない。** 3 回目の `develop` 起動時は「前回試した修正とそれが効かなかった事実」をプロンプトに明記し、別のアプローチを取らせる。それでも同じ FAIL が続く場合は、原因の切り分け（テスト自体の誤り / 環境依存 / 要件の矛盾）を先に行ってから再開する
- FAIL がテスト自体の誤りに起因すると判断した場合のみテストを直してよい。**ゲートを通す目的でテストを削除・弱体化するのは禁止**（禁止行動の節を参照）
- WARN（スキップされたテスト等）はコミットを妨げないが、内容を 1 行で報告する

#### 2-7: Commit（必須）
- **各スコープ完了時に必ずコミットする。スキップ不可。**
- **2-6 が exit 0 で終わっていることが前提**
- **worktree ディレクトリ内で** `git add` / `git commit` を実行する
- コミットメッセージは CLAUDE.md の規約に従う
- **コミット後に `TaskUpdate` で該当タスクを `completed` にする**

## フェーズ3: 完了確認とPR作成

1. 全スコープの実装完了を確認
2. **worktree ディレクトリ内で** 全体テストを実行
3. **スコープ外発見の一括 issue 化**: `.sweep/spinoff-draft.jsonl` が存在し空でなければ `/spinoff-issue --batch .sweep/spinoff-draft.jsonl` を **1 回だけ** 呼んで一括起票し、完了後に draft を削除する。加えて draft に未記載の発見が残っていないかを明示的に確認・宣言する（残っていれば append してから起票する）。PR 本文や最終報告に「発見だが未 issue 化」を書くのは禁止
4. **worktree ディレクトリ内で** `git push -u origin <作業ブランチ>` を実行
5. `gh pr create --base <ベースブランチ>` でPRを作成
   - **ベースブランチはフェーズ1で記録した開始時のブランチを指定する。`main` や `master` にフォールバックしないこと。**
   - 不明な場合は `git log --oneline --graph HEAD...main` 等で分岐元を確認する
   - Issue 指定時: タイトルに Issue 番号を含め、PR作成後に `gh pr edit <PR番号> --add-issue <Issue URL>` でリンクする（Closes は使わない）
   - PR本文: 変更サマリー + 手動チェックリスト（`templates/pr-checklist.md` を参照）
6. 実装サマリーと **worktree パス** をユーザーに報告する

報告例:
```
## 完了
- PR: <URL>
- Worktree: <パス>（確認後 `git worktree remove <パス>` で削除可能）
```

## ルール

- 各スコープは独立して実装・テスト可能な単位にする
- **各スコープ完了時に必ずコミットする。** コミットせずに次へ進まない
- レビュー指摘はすべての重大度（🔴🟠🟡🟢）で修正する
- TaskCreate/TaskUpdate で進捗を管理する
- **フェーズ宣言**: 各サブステップ（2-1〜2-7）の開始時に `▶ 2-X 開始: <名称>`、完了時に `✓ 2-X 完了` を1行表示する。これによりサイレントスキップを防ぐ
- 2-6 は結果も 1 行で表示する（`✓ 2-6 完了: FAIL 0 / WARN 1`）
- **セルフチェック**: 各フェーズ完了前に本 SKILL.md の該当セクションを再読し、未実施手順がないか確認してから次フェーズへ進む
- コンパクト（コンテキスト圧縮）発生時は `TaskList` で現在の進捗を確認してから作業を再開する
- **すべての git / ファイル操作は worktree ディレクトリ内で行う。メインの作業ツリーを変更しない。**
