# slide-gen

既存の仕様書・提案書・報告ドキュメントを入力に、`slide/` で Slidev のプレゼン資料を作る。
対話でアウトラインを固めてから、パート単位で執筆とレビューを繰り返す。

`theme: default` + 独自 `visual.css` デザインシステム（`v-*` クラス群）で組み、
図解は画像化せず CSS で組み、キービジュアルだけ nano-banana で生成する。

## 前提条件

- Bun（`bun --version`）。npm / yarn / pnpm は使わない
- PDF / PNG エクスポートに Chromium（`bunx playwright install chromium`）
- キービジュアル生成に `mcp__nano-banana__*`（無くても資料は作れる → `references/images.md`）

## 引数

- **パス指定**（例: `/slide-gen docs/`）: そのドキュメントを入力にする
- **引数なし**: `spec/` `docs/` `README.md` を探索する
- 既存の `slide/` がある場合は、新規作成ではなく追記・改訂として扱う

## 禁止行動（最重要）

以下に該当した場合はそのフェーズをやり直す。コンテキスト節約を理由にした省略は認めない。

- **アウトラインの合意（1-3）を飛ばして執筆を始める**
- **パートを書き終えたのにレビュー（2-3）せず次のパートへ進む**（崩れが蓄積して手戻りが増える）
- **はみ出し検査を実行せずに「収まっているはず」と判断する**
- 入力ドキュメントを要約だけ読んで済ませる（構成を組み替える判断に本文が要る）
- 裏の取れない数値を推測で書く（README の「未確定事項」へ逃がす）
- `visual.css` に無い見た目を、既存パターンを検討せずに新しいクラスで作る
- 図解を画像で作る / 画像内に文字を入れる
- ページが収まらないときに文字サイズを縮める（削るかページを分ける）
- トンマナ（1-1）を執筆開始後に変更する

## フェーズ1: 現状把握と方針決定

### 1-0: 入力ドキュメントの探索（必須・最初に実行）

引数でパスが指定されていればそれを使う。無ければ Glob で探す。

```
**/spec/**/*.md
**/docs/**/*.md
README.md
```

**見つけたドキュメントは必ず全文を Read で読む。** 要約で済ませない。

`slide/` が既にある場合は `slide/README.md` の構成表と `slide/visual.css` の既存クラスを読み、
そのデッキの規約に合わせる（新しいトンマナを持ち込まない）。

### 1-1: 要点とトンマナのヒアリング

`AskUserQuestion` で以下を1回にまとめて聞く。ドキュメントから一意に読み取れる項目は聞かない。
**執筆開始後の変更は全ページの手直しになるため、ここで確定させる。**

1. **用途** — 技術説明・設計共有 / 提案・営業プレゼン / 進捗・成果報告
2. **想定読者と場面** — 対面プレゼン / PDF 送付 / 両方（情報密度が決まる）
3. **本編のページ数目安** — 20p前後 / 30p前後 / Appendix 厚め
4. **配色プリセット** — `references/tone.md` の A 紺×インディゴ / B 墨×一色差し / C 深緑×琥珀 /
   ブランドカラー指定。各選択肢の説明に想定場面と見え方を書く

**固有名詞で聞かない。** 特定プロジェクトを引き合いに出さず、上の一般名で提示する。

文体（常体 / 敬体）とラベル言語（英語 / 日本語）は用途と読者から自分で決め、作業メモに書いて一言伝える。
プロダクト名・会社名がドキュメントに無ければ個別に確認する。

### 1-2: プロジェクト初期化

```bash
mkdir -p slide/pages slide/public/img/visual
cp <skill>/templates/{visual.css,style.css,global-bottom.vue,package.json,wrangler.toml} slide/
cp <skill>/templates/gitignore slide/.gitignore
cp <skill>/templates/slides.md.tmpl slide/slides.md
cp <skill>/templates/appendix.md.tmpl slide/pages/appendix.md
cp <skill>/templates/README.md.tmpl slide/README.md
cd slide && bun install
```

プレースホルダを置換する。

| プレースホルダ | 値 |
| --- | --- |
| `{{PROJECT_SLUG}}` | 英小文字ケバブケース（Workers 名・PDF 名に使う） |
| `{{PRODUCT_NAME}}` / `{{DECK_TITLE}}` / `{{DECK_SUMMARY}}` | 1-1 と入力ドキュメントから |
| `{{ORG_NAME}}` | 会社名（フッターと表紙） |
| `{{KICKER}}` / `{{COVER_SUB}}` / `{{COVER_ALT}}` / `{{END_ALT}}` | 表紙・締めのコピー |
| `{{TODAY}}` / `{{TODAY_DOT}}` | `2026-08-26` / `2026.08.26` |
| `{{PALETTE}}` / `{{PALETTE_REASON}}` | 選んだ配色プリセット名と理由1文 |
| `{{TONE_STYLE}}` / `{{LABEL_LANG}}` | 文体とラベル言語 |
| `{{APPENDIX_1_LABEL}}` / `{{APPENDIX_1_TITLE}}` / `{{PREFIX_1}}` | Appendix 1章目のラベル・章題・番号接頭辞 |
| `{{APPENDIX_2_LABEL}}` / `{{APPENDIX_2_TITLE}}` | 2章目を使う場合のみ |
| `{{MAIN_PAGES}}` / `{{APPENDIX_PAGES}}` | 完成後に確定 |

配色は `references/tone.md` のプリセットを `:root` ブロックごと差し替える。**他の箇所に色を直書きしない。**
ブランドカラー指定の場合は tone.md の導出手順に従い、コントラスト比を実測してから確定する。

### 1-3: アウトライン設計と合意

`references/structure.md` を読み、用途に対応するテンプレートに入力ドキュメントを割り付ける。
**目次をそのまま写さない。** 1ページ1主張になるまで分割・統合する。

`slide/OUTLINE.md` に作業メモとして次の表を書く。**これが仕様であり、以降の作業の基準になる。**

```markdown
| # | Part | h2（そのページの主張文） | パターン | 出典 | 状態 |
|---|------|------------------------|---------|------|------|
| 1 | 表紙 | — | v-cover | — | |
| 2 | Part 1 | 申請の種類ごとにばらばらな手続きを、1つの基盤にまとめる | v-audience | docs/overview.md | |
```

本編と同時に **Appendix の割り付けも決める**。本編は判断に要る分だけにし、
根拠の詳細・算出過程・API 一覧・体制・契約条件は Appendix へ回す。

表が埋まったら `references/structure.md` の「アウトラインの検証」5項目を通し、
**ユーザーに提示して合意を取る。** ここで直すのが最も安い。

合意できたら **Part 単位でスコープを分け、`TaskCreate` でタスク化する**（1スコープ 4〜8ページ）。
表紙と締めは隣接する Part に含める。Appendix は章ごとに1スコープ。

## フェーズ2: 作成サイクル（各パートで繰り返し）

**各スコープ開始時に `TaskUpdate` で該当タスクを `in_progress` にする。**

### 2-1: Plan

- そのパートの各ページについて、使うパターンを `references/components.md` から確定する
- 情報の型とパターンが合っているか確認する（3つの並列 → `v-audience`、
  段階 → `v-flow-detail`、対比 → `v-duo`、数値 → `v-metrics`、一覧 → `v-data-table`）
- 同じパターンが3ページ続く場合は、どちらかを別の型に変える

### 2-2: 執筆

**初回のスコープに入る前に `references/example-deck.md` を読む**（文章の粒度とパターンの使い方の基準）。
あわせて `references/structure.md` の「わかりやすさの規律」に従う。

- h2 は主張文。見出し語（「機能一覧」「課題」）で終わらせない
- カード本文は結論を先に書き、2〜3文で止める
- 強調は1ページ1箇所。`.accent` は1枚だけ
- 各ページに `<!-- ... -->` で presenter note を1〜2文
- 数値には出典と年を添える。裏が取れないものは README の「未確定事項」へ

### 2-3: レビュー

```bash
cd slide && bun run build:site
bun <skill>/scripts/check-overflow.mjs
```

はみ出しがあれば、ページ番号・はみ出し量・要素名つきで報告される（終了コード 1）。
続けて該当ページを PNG で目視する。

```bash
bun run export:png   # public/<slug>/ に1ページ1枚
```

- 密度がトンマナの設定どおりか
- 強調が1ページ1箇所に収まっているか
- dark ページで文字が沈んでいないか（`v-note-dark` の付け忘れ）
- 図と本文が同じことを言っていないか
- ページ番号が出ているか（表紙のみ非表示が正しい）

### 2-4: 改善サイクル

- 指摘あり → 修正 → **2-3 をやり直す**（文言を削るとレイアウトが動き、別のページが崩れる）
- 指摘なしになるまで繰り返す。**上限 3 周。**
  3 周して残る場合は残指摘を `OUTLINE.md` の「残課題」に書き、次のスコープへ進む

### 2-5: ビルド確認

`bun run build:site` が通ること。`OUTLINE.md` の状態列を更新する。

### 2-6: Commit（必須）

- **各スコープ完了時に必ずコミットする。スキップ不可**
- メッセージは CLAUDE.md の規約に従う（例: `docs: 提案資料の Part 2 を追加`）
- **コミット後に `TaskUpdate` で該当タスクを `completed` にする**

## フェーズ3: 仕上げと通し確認

### 3-1: キービジュアル

`references/images.md` に従い、表紙・体験・クロージング用に 4〜7 点だけ生成する。
配置したら表紙・締めの `class` から `v-dark` を外し、`v-cover` / `v-end` を有効化する。
**存在しない画像パスを参照するとビルドが失敗する。**

### 3-2: 通し読みレビュー

全ページの PNG を並べ、次を確認する。ここで初めて資料全体を1本として見る。

1. h2 だけを縦に読んで話が通るか
2. 用途ごとのゴールに到達しているか（`references/structure.md`）
3. `v-dark` が2枚続いていないか
4. 同じパターンが3ページ続いていないか
5. 同じことを2回言っていないか

直したら **2-3 のはみ出し検査に戻る**。最後は必ず検査が緑で終わる状態にする。

### 3-3: 完成物の確認と案内

- `slide/README.md` の「資料の構成」表を実際のページ構成で埋め、未確定事項を列挙する
- `bun run build` が通ることを確認する
- `OUTLINE.md` の残課題をユーザーに報告する

```
■ 確認        cd slide && bun run dev  → http://localhost:3030
■ PDF         bun run export           → public/<slug>.pdf
■ デプロイ    bunx wrangler deploy     （Cloudflare Workers Static Assets）
■ ページ追加  slides.md に --- 区切りで追記。パターンは visual.css から選ぶ
■ 再レビュー  /slide-review  → はみ出し・デザイン・わかりやすさ・構成・規約の5観点
```

改訂を重ねたあとや、他の人が書き足したあとは `/slide-review` を回す。
このスキルのフェーズ2〜3のレビューを、既存デッキに対して独立して実行できる。

## 参照ファイル

| ファイル | 読むタイミング |
| --- | --- |
| `references/tone.md` | 1-1（質問の選択肢作成）、1-2（`:root` 差し替え） |
| `references/structure.md` | 1-3（アウトライン設計）、2-2（わかりやすさの規律）、3-2（通し確認） |
| `references/example-deck.md` | 2-2 の初回（文章とパターンの基準） |
| `references/components.md` | 2-1（パターン選定）、2-2（執筆）、2-3（崩れ修正） |
| `references/images.md` | 3-1（画像生成） |
| `scripts/check-overflow.mjs` | 2-3 / 3-2（はみ出しの機械検査） |

## 守ること

- **図解を画像にしない。** 構成図・フロー・比較・数値は CSS で組む（差分レビューと文言修正のため）
- **画像内に文字を入れない。** ラベルは必ず HTML 側
- **背景は情報の役割で決める。** ページ順で交互にしない
- **1ページ1主張。** 入りきらない情報はページを増やすのではなく、書かないことを決める
- **強調は1ページ1箇所。** 色だけで情報を区別しない
- **ページ番号は必須。** `global-bottom.vue` が全ページに `現在 / 総数` を出す（表紙のみ非表示）。
  このファイルを削らない。Appendix も本編からの通し番号で、章ごとに振り直さない
- **レビューは1周で終わらせない。** 修正のたびにレイアウトが変わる。最後は必ずはみ出し検査を緑で終える
