# slide-gen

既存の仕様書・提案書・報告ドキュメントを入力に、`slide/` で Slidev のプレゼン資料を作る。
対話でアウトラインを固めてから、パート単位で執筆とレビューを繰り返す。

`theme: default` + 独自 `visual.css` デザインシステム（`v-*` クラス群）で組み、
図解は画像化せず CSS で組み、キービジュアルだけ nano-banana で生成する。

## 前提条件

- Bun（`bun --version`）。npm / yarn / pnpm は使わない
- PDF / PNG エクスポートに Chromium（`bunx playwright install chromium`）
- キービジュアル生成に `mcp__nano-banana__*`（無くても資料は作れる → `references/images.md`）

## 引数

入力は探索だけでなく、**呼び出し側から直接渡せる**。優先順位は上から。

| 引数 | 例 | 扱い |
| --- | --- | --- |
| **テキスト** | `/slide-gen 以下を提案資料にする: <本文>` | 渡された本文をそのまま入力にする。探索しない |
| **パス**（複数可） | `/slide-gen docs/overview.md docs/architecture/` | 指定されたファイル・ディレクトリだけを読む |
| **Issue 番号 / URL** | `/slide-gen #123` | `gh issue view --comments` で本文とコメントを取得して入力にする |
| **引数なし** | `/slide-gen` | `spec/` `docs/` `README.md` を探索する |

**会話の中で既に共有された内容があれば、それを入力として扱い探索しない。**
ユーザーがメッセージに貼り付けた仕様、直前のスキル（`spec-gen` など）が作ったドキュメント、
このセッションで既に読んだファイルがこれにあたる。**同じものを読み直さない。**

複数の入力ソースが同時に与えられた場合は**すべてを入力にする**（テキスト + パス、パス + Issue など）。
どれを主にするか迷う場合のみ 1-1 のヒアリングで確認する。

既存の `slide/` がある場合は、新規作成ではなく追記・改訂として扱う。

**フラグ:**

- `--auto`: **自律実行モード**。他のスキルから呼ばれる場合は必ず付ける。挙動は「--auto モード」節を参照
- `--append`: 既存の `slide/` へ追記する（フェーズ1-2 の初期化を飛ばす）

## --auto モード（自律実行）

`--auto` 指定時は**ユーザーが応答できない前提**で動く。人に聞いて止まらない。

| 通常 | `--auto` |
|---|---|
| 1-1 でトンマナを `AskUserQuestion` | 入力から用途を推定し、配色は A（紺×インディゴ）、密度は標準、文体は常体、ラベルは英語を採用する |
| 1-3 でアウトラインの合意を取る | 合意を取らず `OUTLINE.md` に記録して進む。採用した前提を最終報告に列挙する |
| 2-4 で指摘の扱いを確認 | 🔴 🟠 相当は自分で修正し、🟡 🟢 は `OUTLINE.md` の残課題に積む |
| 3-3 で完成物を案内 | 案内に加え、推定した用途・トンマナ・残課題を呼び出し元へ返す |

**省略禁止**: 2-3 のレビュー（はみ出し・装飾・配色の3検査）と 2-6 の Commit は `--auto` でも必ず実行する。
人の目が入らないぶん、機械検査が唯一の品質担保になる。

## 禁止行動（最重要）

以下に該当した場合はそのフェーズをやり直す。コンテキスト節約を理由にした省略は認めない。

- **アウトラインの合意（1-3）を飛ばして執筆を始める**
- **パートを書き終えたのにレビュー（2-3）せず次のパートへ進む**（崩れが蓄積して手戻りが増える）
- **はみ出し検査を実行せずに「収まっているはず」と判断する**
- 入力を要約だけ読んで済ませる（構成を組み替える判断に本文が要る）
- **テキストや会話で内容が渡されているのに、ドキュメントを探索しに行く**（渡されたものを使う）
- **同じセッションで既に読んだファイルを読み直す**
- 裏の取れない数値を推測で書く（README の「未確定事項」へ逃がす）
- `visual.css` に無い見た目を、既存パターンを検討せずに新しいクラスで作る
- 図解を画像で作る / 画像内に文字を入れる
- **グラデーション・光彩・すりガラス・絵文字アイコンで装飾する**（→ `references/structure.md`「使わない表現」）
- ページが収まらないときに文字サイズを縮める（削るかページを分ける）
- トンマナ（1-1）を執筆開始後に変更する

## フェーズ1: 現状把握と方針決定

### 1-0: 入力の取得（必須・最初に実行）

「引数」節の優先順位で入力を確定する。**探索は最後の手段**であり、
テキストで渡された・会話で共有された・パスで指定された内容があるならそれを使う。

| 入力ソース | 取得方法 |
| --- | --- |
| 渡されたテキスト | そのまま入力にする。ファイルを探しに行かない |
| 会話で既に共有された内容 | このセッションで読んだ内容を再利用する。**同じファイルを読み直さない** |
| 指定されたパス | そのファイル・ディレクトリを Read する |
| Issue 番号 / URL | `gh issue view <番号> --comments` で本文とコメントを取得する |
| なし（探索） | Glob で `**/spec/**/*.md` `**/docs/**/*.md` `README.md` を探す |

**入力は必ず全文を読む。** 要約で済ませない（構成を組み替える判断に本文が要る）。

入力が薄い場合（テキスト数行だけ、Issue のタイトルだけ など）は、
足りない情報を 1-1 のヒアリングで補う。**推測で埋めない。**

`slide/` が既にある場合は `slide/README.md` の構成表と `slide/visual.css` の既存クラスを読み、
そのデッキの規約に合わせる（新しいトンマナを持ち込まない）。

### 1-1: 要点とトンマナのヒアリング

`AskUserQuestion` で以下を1回にまとめて聞く。ドキュメントから一意に読み取れる項目は聞かない。
**執筆開始後の変更は全ページの手直しになるため、ここで確定させる。**

1. **用途** — 技術説明・設計共有 / 提案・営業プレゼン / 進捗・成果報告
2. **想定読者と場面** — 対面プレゼン / PDF 送付 / 両方（情報密度が決まる）
3. **スタイル** — `references/tone.md` の A Editorial（角ゼロ・色帯・硬め） /
   B Soft（角丸・影・やわらかい） / C Minimal（罫線と余白だけ・静か）
4. **配色** — A 紺×インディゴ / B 墨×一色差し / C 深緑×琥珀 / ブランドカラー指定

**スタイルは必ず聞く。** ここを既定のままにすると、どのデッキも同じ顔になる。
スタイルと配色は独立しているので、組み合わせで見た目が決まる。

**固有名詞で聞かない。** 特定プロジェクトを引き合いに出さず、上の一般名で提示する。
各選択肢の説明には、そのスタイル・配色が合う場面と見え方を書く。

本編のページ数、文体（常体 / 敬体）、ラベル言語（英語 / 日本語）は
入力量・用途・読者から自分で決め、作業メモに書いて一言伝える。
プロダクト名・会社名がドキュメントに無ければ個別に確認する。

### 1-1b: 配色とロゴの詰め

1-1 の回答を受けて、必要なものだけ追加で聞く。**質問は必ず `AskUserQuestion` を使う。**

#### 配色で「ブランドカラー指定」が選ばれた場合

1. **プライマリカラーを聞く。** 選択肢はコーポレートカラー / プロダクトカラー / 既存資料に合わせる
   などを挙げ、**HEX は自由入力**で受け取る。ロゴ画像やサイトがあれば拾った色を候補に出す
2. 強調色（資料全体で1〜2箇所だけ使う色）を使うか聞く。指定がなければ自動生成する
3. 導出してコントラストを検証する

```bash
bun <skill>/scripts/derive-palette.mjs "#2b6cb0"                  # 人が読む形式
bun <skill>/scripts/derive-palette.mjs "#2b6cb0" --accent "#d6339b"
bun <skill>/scripts/derive-palette.mjs "#2b6cb0" --json           # 機械処理する場合
```

出力された `:root` を `visual.css` の `:root` と差し替える。終了コード 0 = 全基準を満たす。
**満たさない項目が出たら、そのままにせずユーザーに伝えて明度の調整を確認する。**

指定色が明るい場合は `--v-accent` が自動で暗く調整される。その旨も伝える。

#### ロゴ

先にプロジェクト内を探す。

```
**/logo.{svg,png}  **/*logo*.{svg,png}  public/img/**  assets/**  docs/**
```

見つかったかどうかで聞き方を変える。

- **見つかった** — 「表紙とフッターに使う / 表紙のみ / フッターのみ / 使わない」
- **見つからない** — 「会社名テキストのみ（既定） / パスを指定する / 置き場所だけ用意して後で差し込む」

**表紙・章扉・締めは dark 背景**になる。濃色のロゴは沈むため、
白抜き版があるか、どちらの背景でも成立する単色ロゴかを必ず確認する。
無い場合は「フッターのみ（light 背景）に置く」を勧める。

決まったら `public/img/` に配置し、`global-bottom.vue` と `slides.md` 表紙の
コメントアウトされたロゴ行を有効化する（→ `references/tone.md`「ロゴ」）。

### 1-2: プロジェクト初期化

**`--append` 指定時、または既存の `slide/` がある場合はこのステップを飛ばし、1-3 へ進む。**
既存デッキの `visual.css` と README の規約に合わせ、新しいトンマナを持ち込まない。

```bash
mkdir -p slide/pages slide/public/img/visual
cp <skill>/templates/{visual.css,style.css,global-bottom.vue,package.json,wrangler.toml,Makefile} slide/
cp <skill>/templates/gitignore slide/.gitignore
cp <skill>/templates/slides.md.tmpl slide/slides.md
cp <skill>/templates/appendix.md.tmpl slide/pages/appendix.md
cp <skill>/templates/README.md.tmpl slide/README.md
cd slide && bun install
```

プレースホルダを置換する。

| プレースホルダ | 値 |
| --- | --- |
| `{{PROJECT_SLUG}}` | 英小文字ケバブケース（Workers 名・PDF 名に使う） |
| `{{PRODUCT_NAME}}` / `{{DECK_TITLE}}` / `{{DECK_SUMMARY}}` | 1-1 と入力ドキュメントから |
| `{{ORG_NAME}}` | 会社名（表紙） |
| `___ORG_NAME___` | 会社名（`global-bottom.vue` のみ。Vue の `{{ }}` と衝突するため別形式）。**置換し忘れると Vue が式として評価してフッターが空になる** |
| `{{KICKER}}` / `{{COVER_SUB}}` / `{{COVER_ALT}}` / `{{END_ALT}}` | 表紙・締めのコピー |
| `{{TODAY}}` / `{{TODAY_DOT}}` | `2026-08-26` / `2026.08.26` |
| `{{STYLE}}` / `{{PALETTE}}` / `{{PALETTE_REASON}}` | 選んだスタイル名・配色プリセット名・理由1文 |
| `{{TONE_STYLE}}` / `{{LABEL_LANG}}` | 文体とラベル言語 |
| `{{APPENDIX_1_LABEL}}` / `{{APPENDIX_1_TITLE}}` / `{{PREFIX_1}}` | Appendix 1章目のラベル・章題・番号接頭辞 |
| `{{APPENDIX_2_LABEL}}` / `{{APPENDIX_2_TITLE}}` | 2章目を使う場合のみ |
| `{{MAIN_PAGES}}` / `{{APPENDIX_PAGES}}` | 完成後に確定 |

配色は `references/tone.md` のプリセットを `:root` ブロックごと差し替える。**他の箇所に色を直書きしない。**
ブランドカラー指定の場合は tone.md の導出手順に従い、コントラスト比を実測してから確定する。

### 1-3: アウトライン設計と合意

`references/structure.md` を読み、用途に対応するテンプレートに入力ドキュメントを割り付ける。
**目次をそのまま写さない。** 1ページ1主張になるまで分割・統合する。

`slide/OUTLINE.md` に作業メモとして次の表を書く。**これが仕様であり、以降の作業の基準になる。**

```markdown
| # | Part | h2（タイトル） | 主張（h2 には書かない） | パターン | 出典 | 状態 |
|---|------|--------------|----------------------|---------|------|------|
| 1 | 表紙 | — | — | v-cover | — | |
| 2 | Part 1 | 申請手続きを1つの基盤に | 種類ごとの手続きを1つにまとめる | v-audience | docs/overview.md | |
```

本編と同時に **Appendix の割り付けも決める**。本編は判断に要る分だけにし、
根拠の詳細・算出過程・API 一覧・体制・契約条件は Appendix へ回す。

**h2 はタイトル（10〜20字）、主張は別列に書く。** 主張は h2 ではなくカード・図・結論バナーが担うが、
どのページで何を言うかはこの表で管理する。

表が埋まったら `references/structure.md` の「アウトラインの検証」5項目を通し、
**ユーザーに提示して合意を取る。** ここで直すのが最も安い。

合意できたら **Part 単位でスコープを分け、`TaskCreate` でタスク化する**（1スコープ 4〜8ページ）。
表紙と締めは隣接する Part に含める。Appendix は章ごとに1スコープ。

## フェーズ2: 作成サイクル（各パートで繰り返し）

**各スコープ開始時に `TaskUpdate` で該当タスクを `in_progress` にする。**

### 2-1: Plan

- そのパートの各ページについて、使うパターンを `references/components.md` から確定する
- 情報の型とパターンが合っているか確認する（3つの並列 → `v-audience`、
  段階 → `v-flow-detail`、対比 → `v-duo`、数値 → `v-metrics`、一覧 → `v-data-table`）
- 同じパターンが3ページ続く場合は、どちらかを別の型に変える

### 2-2: 執筆

**初回のスコープに入る前に `references/example-deck.md` を読む**（文章の粒度とパターンの使い方の基準）。
あわせて `references/structure.md` の「わかりやすさの規律」に従う。

- **h2 はタイトル**。10〜20字で「何のページか」を示す。主張文を h2 に入れない
- **主張はカード・図が語る。** 足りないページだけ `v-formula-banner` を最下部に置く
- **`v-lead`（リード文）は既定では置かない。** 図より先に前提が要る場合だけ
- `v-formula-banner` と `v-note` を同じページに両方置かない
- カード本文は結論を先に書き、2〜3文で止める
- 強調は意味があるときだけ。`.accent` は既定で使わず、使うなら1枚だけ
- 各ページに `<!-- ... -->` で presenter note を1〜2文
- 数値には出典と年を添える。裏が取れないものは README の「未確定事項」へ

### 2-3: レビュー

```bash
cd slide && make check                          # はみ出し（全ページ実寸）
make style SKILL_DIR=<skill>                    # 装飾に逃げた表現
make contrast SKILL_DIR=<skill>                 # 配色のコントラスト（初回とトンマナ変更時）
```

`make check` はビルドしてから `scripts/check-overflow.mjs` を実行する。
スキルを既定と違う場所に置いている場合は `make check SKILL_DIR=<skill>`。

はみ出しがあれば、ページ番号・はみ出し量・要素名つきで報告される（終了コード 1）。
続けて該当ページを PNG で目視する。

```bash
make png   # public/<slug>/ に1ページ1枚
```

- 密度がトンマナの設定どおりか
- 強調が1ページ1箇所に収まっているか
- dark ページで文字が沈んでいないか（`v-note-dark` の付け忘れ）
- 図と本文が同じことを言っていないか
- ページ番号が出ているか（表紙のみ非表示が正しい）

### 2-4: 改善サイクル

- 指摘あり → 修正 → **2-3 をやり直す**（文言を削るとレイアウトが動き、別のページが崩れる）
- 指摘なしになるまで繰り返す。**上限 3 周。**
  3 周して残る場合は残指摘を `OUTLINE.md` の「残課題」に書き、次のスコープへ進む

### 2-5: ビルド確認

`make build` が通ること。`OUTLINE.md` の状態列を更新する。

### 2-6: Commit（必須）

- **各スコープ完了時に必ずコミットする。スキップ不可**
- メッセージは CLAUDE.md の規約に従う（例: `docs: 提案資料の Part 2 を追加`）
- **コミット後に `TaskUpdate` で該当タスクを `completed` にする**

## フェーズ3: 仕上げと通し確認

### 3-1: キービジュアル

`references/images.md` に従い、表紙・体験・クロージング用に 4〜7 点だけ生成する。
配置したら表紙・締めの `class` から `v-dark` を外し、`v-cover` / `v-end` を有効化する。
**存在しない画像パスを参照すると `make build` が失敗する。**

### 3-2: 通し読みレビュー

全ページの PNG を並べ、次を確認する。ここで初めて資料全体を1本として見る。

1. `OUTLINE.md` の「主張」列を縦に読んで話が通るか。h2（タイトル）の列で章立てが読み取れるか
2. 用途ごとのゴールに到達しているか（`references/structure.md`）
3. `v-dark` が2枚続いていないか
4. 同じパターンが3ページ続いていないか
5. 同じことを2回言っていないか

直したら **2-3 のはみ出し検査に戻る**。最後は必ず検査が緑で終わる状態にする。

### 3-3: 完成物の確認と案内

- `slide/README.md` の「資料の構成」表を実際のページ構成で埋め、未確定事項を列挙する
- `make build`（Web 配信用）と `make pdf`（配布用 PDF）が両方通ることを確認する
- `OUTLINE.md` の残課題をユーザーに報告する

```
■ 確認        cd slide && make dev   → http://localhost:3030
■ ビルド      make build             → dist/（Web 配信用。PDF は含まない）
■ PDF         make pdf               → public/<slug>.pdf
■ デプロイ    make deploy            （Cloudflare Workers Static Assets）
■ ページ追加  slides.md に --- 区切りで追記。パターンは visual.css から選ぶ
■ 再レビュー  /slide-review  → はみ出し・デザイン・わかりやすさ・構成・規約の5観点
```

改訂を重ねたあとや、他の人が書き足したあとは `/slide-review` を回す。
このスキルのフェーズ2〜3のレビューを、既存デッキに対して独立して実行できる。

## 守ること

- **図解を画像にしない。** 構成図・フロー・比較・数値は CSS で組む（差分レビューと文言修正のため）
- **画像内に文字を入れない。** ラベルは必ず HTML 側
- **背景は情報の役割で決める。** ページ順で交互にしない
- **1ページ1主張。** 入りきらない情報はページを増やすのではなく、書かないことを決める
- **装飾で情報を足そうとしない。** グラデーション塗り・光彩・すりガラス・文字の影・
  絵文字アイコン・ページ内アニメーションは使わない
- **意味のない強調をしない。** `.accent` は既定で使わない。付ける理由を presenter note に
  書けないなら外す。カードの色は区切りの構造であって、情報ではない
- **強調するときは1ページ1箇所。** 色だけで情報を区別しない
- **ページ番号は必須。** `global-bottom.vue` が全ページに `現在 / 総数` を出す（表紙のみ非表示）。
  このファイルを削らない。Appendix も本編からの通し番号で、章ごとに振り直さない
- **レビューは1周で終わらせない。** 修正のたびにレイアウトが変わる。最後は必ずはみ出し検査を緑で終える
