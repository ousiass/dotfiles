# 構成テンプレート

用途ごとの本編アウトライン。**ドキュメントの目次をそのまま写さない。**
仕様書の1章が0ページになることも、1章が5ページに分かれることもある。

## 共通ルール

- **1ページ1主張。** h2 がそのページの結論。
- **Part 構成にする。** 本編は 4 パート前後、各パート 4〜8 ページ。パートの切り替わりに `v-dark` の章扉を挟む。
- **`v-dark` は資料全体の句読点。** 連続させない。章扉・結論・1つの数値を見せるページだけ。
- **各ページに presenter note を付ける。** `<!-- ... -->` で「このページで固定したい1点」を書く。
- **数値には出典と年を添える。** 裏が取れない数値は載せず、README の「未確定事項」へ。
- **ページ番号を必ず出す。** `global-bottom.vue` が担保する。消さない（詳細は SKILL.md）。

## わかりやすさの規律

構成が正しくてもページが読めなければ意味がない。全ページで守る。

### 視線の順序

上から `v-kicker` → `h2` → 図 / カード → 結論バナー → `v-note` の順に重要度が下がる。
**この順に読めば理解できる状態にする。** 下にあるものを読まないと上が理解できない構成にしない。

### 強調は1ページ1箇所

- カード列で `.accent` を付けるのは**1枚だけ**。2枚以上あると、どちらが主役か読めない
- `--v-magenta` 系は**資料全体で1〜2箇所**。ここぞという1ページのために取っておく
- 太字は1ページ2〜3語まで。段落まるごと太字にしない

### 色だけで区別しない

`.accent` のカードには必ず `index` / `ordinal` / 見出しの語でも差が付くようにする。
色覚特性や白黒印刷でも情報が落ちない状態にする。比較表の `●` `—` も同様（色ではなく記号で区別する）。

### 図と本文で同じことを言わない

図で示した関係を、下の `v-note` で文章化しない。図が読めていない前提の説明を足すくらいなら、図を直す。
`v-formula-banner` は図の要約ではなく、**図から導かれる結論**を書く場所。

### 文字量の上限

密度プリセット（`references/tone.md`）に従う。標準なら:

| 要素 | 上限 |
| --- | --- |
| h2 | 30字・2行まで |
| カード内の本文 | 60字 |
| 箇条書き | 5行、1行30字 |
| `v-note` | 80字・2行まで |
| 1ページの総文字数 | 400字 |

超えたら、書き足すのではなく**削るかページを分ける**。

### 読める文字サイズ

`visual.css` の最小は `v-note` の 0.68rem 相当。**これより小さいサイズを新規に作らない。**
投影時に後方の席から読めなくなる。表が入らない場合は文字を縮めず、列を減らすか Appendix へ回す。

### 用語

- 専門用語・略語は初出のページで1度だけ定義する（`v-note` に1行で足りる）
- 同じ概念を別の語で言い換えない。資料内で語を1つに固定する
- 読み手の業界で通じない社内用語は、通じる語に置き換える

### 数値

- 単位は `<span class="unit">` に分け、数字本体を大きく見せる
- 桁区切りを入れる（`1,233`）。同じページ内で桁表記を混ぜない
- 比較する数値は単位と基準年を揃える。揃わないなら並べない

## h2 の書き方

h2 は見出しではなく**主張文**。読み手が h2 だけを縦に読んで話が通ることが完成条件。

| 良い | 悪い | 理由 |
| --- | --- | --- |
| 会費を上げられないのは、上げる材料がないから | 課金モデルの課題 | 何が問題かが読み取れない |
| 配信 PC 不要のクラウド配信 | インフラ構成について | 主張がない |
| いまファンは、5つのアプリを使い分けている | 現状分析 | 具体がない |
| 1機能から始めて、必要になった順に足せる | 導入方式 | 相手の得が見えない |

体言止めは、主語と述語の関係が読み取れる場合だけ許す（「配信 PC 不要のクラウド配信」は可、「インフラ構成」は不可）。

## アウトラインの検証

本文を書く前に「# / セクション / h2 の文 / 使うパターン / 出典」の表を作る。
書き始める前に次を確認する。

1. **h2 だけを縦に読む。** 接続が飛ぶ箇所があれば、そこにページが足りないか順序が違う
2. **同じことを2回言っていないか。** 言っていたら片方を Appendix へ
3. **ゴールに向かっているか。** 用途ごとのゴール（下記）に到達しないページは削る
4. **`v-dark` が2枚続いていないか**
5. **パターンが3ページ連続で同じでないか。** 同じ形が続くと読み手の集中が切れる

## A. 技術説明・設計共有

**ゴール:** 読み手が「この設計で作ってよい」と判断できる。

| # | セクション | 内容 | パターン |
| --- | --- | --- | --- |
| 1 | 表紙 | プロダクト名と一文の定義 | `v-cover` |
| 2 | 課題（dark） | 現状の何が重いのか | `v-statement` |
| 3 | 現状の分解 | 自作・既存構成だと何工程あるか | `v-pipeline` / `v-fragment` |
| 4 | Part 1 何を作るか | 提供対象 / 提供内容 / 新しさ | `v-audience` |
| 5-7 | 主要機能 | 機能を3〜5枚で並べる | `v-detail-grid` |
| 8 | 全体像 | レイヤー構成図と提供範囲 | `v-arch` |
| 9 | 処理の流れ | リクエストからレスポンスまで | `v-flow-detail` |
| 10 | 連携 | 既存システムとの接続 | `v-bridge` / `v-hub` |
| 11 | Part 2 なぜこの設計か | 技術選定の対比 | `v-duo` / `v-usecase-grid` |
| 12 | 比較 | 他手段との機能マトリクス | `v-matrix` |
| 13 | 非機能 | 性能・可用性・セキュリティ | `v-detail-columns` |
| 14 | Part 3 導入 | 導入ステップ | `v-process` |
| 15 | ロードマップ | フェーズごとの範囲 | `v-phase-grid` |
| 16 | 結論（dark） | 一文で言い切る | `v-statement` |

h2 の連なり（実例）:

```
運用が重い → 自作では5つの処理を個別に構築 → 3つの想定ユーザーとそれぞれの課題
→ コメント取得から映像配信までを自動化 → 利用者は設定、システムは配信運用を担当
→ 配信PC不要のクラウド配信 → 用途で選べる2つの配信モード → 導入から開始までの4ステップ
```

Mermaid は状態遷移・シーケンスなど CSS で組むのが不合理な図に限る。
構成図・レイヤー図・フロー図は `v-arch` / `v-flow-detail` の方が資料に馴染む。

**ゴール:** 読み手が「話を先に進める」と判断できる。

| # | セクション | 内容 | パターン |
| --- | --- | --- | --- |

h2 の連なり（実例）:

```
丸ごと作れて1機能だけでも足せる基盤 → 1つのアプリで聴く・観る・買う
→ いま利用者は5つのアプリを使い分けている → 高品質に届ける手段がどこにもない
→ 会費を上げられないのは上げる材料がないから → 判定と配信を1つの基盤でつなぐ
→ [dark] 関係そのものがサービスごとに分断されている → 立場ごとに別の困りごとが起きている
→ 既存の選択肢との違い → いま参入する理由 → 同じ基盤で小規模から大規模まで
→ 4フェーズで広げる → [dark] 運営会社ではなく取引が流れるインフラへ
```

金額・料率を確定できない場合は「個別提示」と書き、資料には載せない。

## Appendix

本編は「読み手が判断するのに要る分」だけにし、残りは Appendix に置く。
Appendix があることで本編を削れる。**本編を短くするための場所であって、余り物置きではない。**

### 何を落とすか

| 本編に残す | Appendix へ |
| --- | --- |
| 判断に要る結論と根拠1点 | 根拠の詳細、算出過程、前提条件 |
| 主要な数値3点 | 内訳、時系列、感度分析 |
| 全体構成図 | サブシステムごとの構成、API 一覧、データモデル |
| 比較の結論 | 競合ごとの詳細評価 |
| フェーズの見出し | フェーズごとのタスク一覧、体制、KPI |
| — | 会社概要、体制、契約条件、セキュリティ論点 |

質問されたときに開くページが Appendix にある状態を目指す。

### 章分けと番号

10ページを超えるなら章に分ける。章ごとに `v-appendix-cover`（`v-dark`）の扉を置く。

| 用途 | 章の分け方 | 番号 |
| --- | --- | --- |
| 技術説明 | 設計詳細 / 運用 | `D-1…` `O-1…` |
| 提案 | ビジネス / テクニカル | `B-1…` `T-1…` |
| 報告 | 数値詳細 / 実施ログ | `M-1…` `L-1…` |

各ページの kicker に番号と英語ラベルを入れる。口頭で「Appendix B-7 を見てください」と言える状態にする。

```html
<div class="v-kicker">Appendix B-7 / Revenue streams</div>

## 9つの収益源
```

### 配置

`pages/appendix.md` に置き、`slides.md` 末尾の `---\nsrc: ./pages/appendix.md\n---` で読み込む。
章が増えたら `pages/appendix-business.md` `pages/appendix-technical.md` に分け、`src:` を並べる。
ページ番号は本編から通しで振られる（Appendix 側で番号を振り直さない）。

Appendix のページも本編と同じパターン・同じデザインルールで組む。
密度は上げてよい（`v-data-table-dense` / `v-grid-compact`）が、1ページ1主張は崩さない。

## 収まらないときの対処

| 症状 | 対処 |
| --- | --- |
| カードが3行以上で溢れる | `v-grid-compact` を併用、または項目を減らしてページを分ける |
| 表の行が多い | `v-data-table-dense`。それでも溢れるなら Appendix へ |
| 本文が長い | 文を削る。ページを分けるより、書かないことを決める |
| 図が複雑 | 1ページ1関係に分解する。1枚に2つの関係を描かない |
| 本編が 35 ページを超える | 判断に要らないページを Appendix へ移す |
