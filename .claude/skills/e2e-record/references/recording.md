# 録画の実行手順

## 録画先の選び方

| | ローカル | 開発 / ステージング |
|---|---|---|
| テスターの準備 | bun + `bunx playwright install chromium` + アプリ起動 | ブラウザだけ（codegen 経路なら bun も必要） |
| 録画できる機能 | 未マージ・作りかけのものも録画できる | **デプロイ済みのものだけ** |
| データ | 壊しても平気。好きに作れる | **実データに近い。削除操作は要注意** |
| 前提データの用意 | Factory で先に作っておける | テスターが手で用意するか、既存を探す |
| CI との一致 | 高い（同じコードで動く） | ズレうる（環境のコードが古い / 新しい） |
| HAR の中身 | テストデータ | **本物の個人情報が入りうる。より厳重に扱う** |

**迷ったらローカル。** テスターの手元が用意できない、または作りかけでない機能を淡々と積むならステージング。

`playwright codegen` は URL を渡すだけなので、**ステージング録画でもアプリのローカル起動は不要**。必要なのは bun とブラウザのダウンロードだけ。

## 経路A: playwright codegen

### 起動（ローカル）

```bash
bunx playwright codegen \
  --test-id-attribute=data-testid \
  --load-storage=.auth/<role>-0.json \
  --save-har=e2e/_recordings/<name>.har \
  --output=e2e/_recordings/<name>.raw.ts \
  http://localhost:4173
```

`--load-storage` でログイン済みの状態から始まるので、テスターにログイン操作をさせない。

### 起動（開発 / ステージング）

```bash
bunx playwright codegen \
  --test-id-attribute=data-testid \
  --save-har=e2e/_recordings/<name>.har \
  --output=e2e/_recordings/<name>.raw.ts \
  https://staging.example.com
```

`--load-storage` は付けない。**テスターに普通にログインしてもらい、ログイン操作は変換時に捨てる**（実行時は storageState を使うため）。`.auth/` の説明をテスターにしなくて済む。

### 共通オプションの意味

- `--test-id-attribute=data-testid`: 画面の目印を優先して記録させる。変換精度が段違いに上がる
- `--save-har`: 通信の記録。Law #7 の待機を自動で埋めるのに使う
- `run_in_background: true` で起動し、ブラウザが閉じられて終了通知が来るまで待つ

### テスターへの声かけ（このまま伝える）

> ブラウザが開きます。**確認したい操作をいつも通りやってみてください。**
>
> - ゆっくりで大丈夫です。待ち時間も記録されます
> - 途中で操作を間違えたら、そのままやり直して構いません（あとでこちらで整えます）
> - 別のウィンドウ（記録用の小さい画面）が一緒に出ますが、触らなくて大丈夫です
> - **操作が終わったら、ブラウザを閉じてください。** それで録画が終わります

ステージング録画のときは先頭に足す:

> はじめにログイン画面が出ます。いつものアカウントでログインしてください。

### 終了後

`e2e/_recordings/<name>.raw.ts` と `.har` ができていることを確認する。
`.raw.ts` が空、または `goto` だけの場合は録画が成立していない。テスターを責めず「うまく記録できなかったので、もう一度お願いできますか」と伝えて再実行する。

## 経路B: Chrome DevTools Recorder

テスターの手元に bun を入れられない場合。**ブラウザだけで完結する。**

### テスターへの声かけ（このまま伝える）

> 1. Chrome で対象の画面を開き、ログインしておいてください
> 2. `F12`（または右クリック →「検証」）で開発者ツールを開きます
> 3. 上部のタブの `>>` から **「Recorder」** を選びます
> 4. **「Create a new recording」** を押し、名前を付けて **「Start recording」**
> 5. **確認したい操作をいつも通りやってみてください**
> 6. 終わったら **「End recording」** を押します
> 7. 右上のダウンロードアイコンから **「Export as a JSON file」** を選び、保存します
>
> つづけて、通信の記録も保存してください。
>
> 8. 開発者ツールの **「Network」** タブを開きます
> 9. 右上の **ダウンロードアイコン（Export HAR）** を押して保存します
> 10. 保存した2つのファイルの場所を教えてください

受け取ったファイルを `e2e/_recordings/<name>.json` と `<name>.har` に配置する。

**HAR は Network タブから出せる**ので、経路B でも Law #7 の待機は自動で埋められる。ただし録画開始前に Network タブを開いていないと記録が欠けるため、手順9で HAR が空だった場合は「通信の記録が取れていなかったので、もう一度お願いできますか」と伝えて録り直す（テストは HAR 無しでも作れるが、待機の精度が落ちる）。

### 経路B の制約

- 目印（`data-testid`）が無い要素は CSS セレクタや XPath で記録される。変換時にアプリ側へ目印を付与する
- 録画の粒度が codegen より粗い（入力途中の状態などが落ちる）

## 録画データの取り扱い

**`e2e/_recordings/` は絶対にコミットしない。**

HAR には以下がそのまま入る。

- 認証トークン・セッション Cookie
- API のリクエスト／レスポンス本文（実データ・個人情報を含みうる）

**ステージング／開発環境で録った HAR は特に危険**（本物の顧客データが入りうる）。変換が終わったら即削除する。

`.gitignore` に以下を必ず入れる。

```gitignore
e2e/_recordings/
.auth/
```

変換とテストの green を確認したら、`e2e/_recordings/` は削除する。デバッグのために残したくなるが、残さない。必要なら録画し直すほうが安全。

## 複数の録画をまとめて処理する場合

テスターが先に何本か録りためているケースもある。`e2e/_recordings/` 内の未変換ファイルを列挙し、**1本ずつ**フェーズ2〜4を回す。まとめて変換して最後にテストすると、どれが落ちたか切り分けられなくなる。
