# e2e-record

プログラミングに詳しくないテスターが画面を操作して録画するだけで、Iron Law 準拠の E2E テストが1本増える状態を作る。`e2e-turbo` で作った基盤に、テストを継ぎ足していくためのスキル。

## 前提条件

- `e2e-turbo` の基盤が導入済み（`playwright.config.ts` と `e2e/features/` がある）
- ローカルでアプリが起動できること
- 基盤が無い場合は「先に `/e2e-turbo` を実行してください」と案内して終了する

## 相手はテスターである

**このスキルの実行中、以下を厳守する。**

- **コードを見せない。** 生成したコードの断片を会話に出さない。「テストを1本作りました」で十分
- **専門用語を使わない。** locator / fixture / POM / assert / DOM / testid を会話に出さない。「画面の目印」「準備するデータ」等に言い換える
- **質問は必ず `AskUserQuestion` の選択式。** 自由記述を求めない。選択肢は録画の実データから作る
- **エラーをそのまま貼らない。** 「◯◯の画面が出てこなかったようです。もう一度録画しますか？」のように翻訳する
- **失敗しても原因をテスターに問わない。** 調査はこちらでやる
- 1回の質問は4問以内。テンポを落とさない

## フェーズ0: 準備と初回ヒアリング

### 0-1: 環境確認（テスターには見せない）

- `playwright.config.ts` / `e2e/features/` の存在と、既存 feature の一覧
- `.auth/` に storageState があるか（無ければ `bunx playwright test --list` 等で globalSetup を一度走らせる）
- アプリが起動しているか。していなければ起動する
- `.gitignore` に `e2e/_recordings/` と `.auth/` があるか。無ければ追加する

### 0-2: ヒアリング

`AskUserQuestion` で一度に聞く。**選択肢はすべて平易な日本語で書く。**

1. **どの機能のテストですか**
   → 既存 feature 一覧を選択肢にする。「新しい機能」も選択肢に入れる
2. **どの立場でログインした状態で操作しますか**
   → `.auth/` にあるロール（管理者・承認者・編集者・閲覧者）を選択肢にする
3. **録画のしかた**
   → 「ブラウザが自動で開くので操作する（おすすめ）」/「Chrome の録画機能を自分で使う」
4. **できたテストの取り込み方**
   → 「PR を作ってエンジニアに確認してもらう（おすすめ）」/「そのままコミットする」

## フェーズ1: 録画

`references/recording.md` の手順に従う。テスターへの声かけ文言もそこにある。

録画データは `e2e/_recordings/` に置く。**このディレクトリは絶対にコミットしない**（HAR に認証トークンや個人情報が入る）。変換が終わったら削除する。

## フェーズ2: 確認したいことのヒアリング

**ここが一番大事。** 録画から取れるのは「操作」だけで、「何が確認できれば合格か」は取れない。

録画データから画面上の文言・状態表示を抽出し、それを選択肢にして聞く。

1. **操作が終わったあと、画面がどうなっていれば成功ですか**
   → 抽出した文言を選択肢に（例: 「ステータスが『承認済み』になる」「完了メッセージが出る」）
2. **逆に、出てはいけないものはありますか**
   → 例: 「編集ボタンが消えている」「エラーが出ない」
3. **このテストを始める前に、あらかじめ用意しておくものはありますか**
   → 例: 「承認待ちの文書が1件」「何も要らない」
4. **このテストは時間がかかるほうですか**（30秒以上 / 大量データを扱う → `@heavy`）

## フェーズ3: 変換

`references/convert.md` に従い、Iron Law 準拠のコードに翻訳する。

1. 録画から画面の目印（`data-testid`）を抽出 → `selectors.ts`
2. 目印が無い箇所を検出 → **アプリ側に `data-testid` を付与**する（PR で明示する）
3. 操作を意味のまとまりで切って `pages/` の Page Object メソッドに
4. HAR から通信を抽出 → 再取得を伴う操作に `runAndWaitForRpc` を適用（Law #7）
5. フェーズ2 の回答を assert に翻訳（Law #4 / #5 を守る）
6. 前提データが必要なら `factories/` に生成 + teardown を追加
7. `specs/` に spec を配置。`@heavy` なら タグを付ける

**`_recordings/` の生ファイルを `specs/` にそのまま置かない。** codegen の出力は spec に生の locator が並ぶ Law #3 違反の形をしている。

変換後、`references/iron-law.md`（`e2e-turbo` 側）のセルフチェックを通す。

## フェーズ4: 検証

1. 追加した spec を単体実行 → green
2. `--repeat-each=3` で3回連続実行し、flaky が無いことを確認
3. 落ちた場合は Iron Law に照らして原因を直す。**テスターに聞かず、こちらで直す**
4. どうしても再現しない場合のみ「もう一度録画をお願いできますか」と依頼する
5. lint / format / `bunx linterly check e2e/`（設定があれば）

テスターへの報告は結果だけ伝える。「3回続けて成功しました。安定しています」

## フェーズ5: Git に取り込む

1. `e2e/_recordings/` を削除する（録画データは残さない）
2. ブランチを作る（`test/e2e-<feature>-<内容>`）
3. コミット（`test: <機能>の<内容>のE2Eテストを追加`）
4. PR を作る。**本文はテスターの回答をそのまま日本語で書く**

```markdown
## このテストで確認すること
<フェーズ2 の回答をそのまま>

## 操作の流れ
1. <POM メソッド名を日本語で>

## 前提データ
<factories で用意するもの>

## 実装メモ（エンジニア向け）
- data-testid を追加したファイル: <一覧>
- 実行時間: <秒> / project: light-<feature>
```

5. テスターには PR の URL を伝えて終わる

## ルール

- テスターにコード・専門用語・エラーログを見せない
- 質問は `AskUserQuestion` の選択式のみ。選択肢は録画の実データから作る
- `e2e/_recordings/` と `.auth/` は絶対にコミットしない
- 生成コードは `e2e-turbo` の Iron Law に必ず従う。録画由来でも例外にしない
- 既存 feature の命名規約・構造を尊重する
- パッケージマネージャは bun（`npx` を使わない）
- 進捗は TaskCreate / TaskUpdate で管理する
