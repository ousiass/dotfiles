# report-sweep

複数の機能要望・バグ報告を 1 セッションでまとめて GitHub Issue 化する軽量な起票ツール。
仕様書やブランチは作らない。純粋な Issue 発行のみ。

## いつ使うか

- 溜まった要望・バグをまとめて Issue 起票したいとき
- 1 件ずつ `/bug-report` `/design-request` を起動するのが煩わしいとき
- コード調査や仕様書作成は不要で、まずは受け皿となる Issue だけ欲しいとき

深い調査や仕様書化が必要な項目は、後で `/bug-report #N` `/spec-gen` を個別に呼ぶ。

## 前提条件

- Claude Code 環境
- `gh` CLI と認証済みリポジトリ

## 引数

- **テキスト**（例: `/report-sweep ログインまわりのバグと通知機能追加`）: 初期メモとして扱う
- **引数なし**: 最初からヒアリング開始

## フェーズ1: 一括計画

### 1-1: 項目数と運用方針

`AskUserQuestion` で以下を確認（1 回にまとめる）:

1. **項目数**（自由入力可、1〜20 程度）
2. **重複チェック**: 「各項目で実行（推奨）」/「スキップ」
3. **プレビュー承認**: 「各項目で確認」/「一括承認（信頼モード）」

### 1-2: 各項目のタイトル・種別収集

項目ごとに 1 回の `AskUserQuestion` で以下を集める（項目数だけ繰り返す）:

1. **タイトル案**（自由入力、1 行）
2. **種別**: `バグ報告` / `機能要望`
3. **一言概要**（自由入力、1〜2 文）

すでに引数のテキストや直前の会話でわかっている情報はスキップする。

### 1-3: 計画確定

収集した項目を番号付きリストで提示:

```
起票予定（順序＝入力順）:
1. [Bug] ログイン失敗 — 正しいPWでも認証が通らない
2. [feat] 通知機能 — メール以外に Slack 通知を追加
3. [Bug] 検索: 日本語入力で0件になる
...
```

`AskUserQuestion` で承認を取ってから、`TaskCreate` で各項目をタスクキュー化する。

### 2-2: 種別ごとの追加ヒアリング（最小限）

**バグの場合** — `AskUserQuestion` で 1 回:

- **再現手順**（自由入力、任意）
- **重大度**: `critical` / `high` / `medium` / `low`
- **領域ラベル**（自由入力、任意。`area:auth` など既存 label があればそれを推奨。無ければ空欄）

**機能要望の場合** — `AskUserQuestion` で 1 回:

- **目的・背景**（自由入力、任意）
- **優先度**: `high` / `medium` / `low`
- **領域ラベル**（自由入力、任意）

概要から明らかに読み取れる情報はデフォルト選択にして、確認だけ取る。

### 2-3: 重複チェック（有効な場合のみ）

```bash
gh issue list --state open --search "<キーワード>" --limit 5
```

- 類似あり → タイトルと URL を提示し、`AskUserQuestion` で「新規作成」/「既存にコメント追加」/「スキップ」から選ばせる
- 類似なし → 続行

### 2-4: ラベル存在チェック

Issue 作成前に:

```bash
gh label list --limit 200 --json name -q '.[].name'
```

未存在ラベルはプレビューで `(NEW)` を付け、承認を得てから `gh label create <name>` で作成。承認なしに作成しない。

### 2-5: プレビュー

「各項目で確認」モードの場合、以下を表示:

- **タイトル**（後述ルール）
- **付与ラベル一覧**（`(NEW)` を明示）
- **本文プレビュー**（テンプレート参照）

`AskUserQuestion` で「作成」/「修正」/「スキップ」を選ばせる。
「一括承認」モードならプレビュー表示のみで即作成。

### 2-6: Issue 作成

```bash
gh issue create \
  --title "<タイトル>" \
  --label "<label1>" --label "<label2>" ... \
  --body-file <本文>
```

- **バグ**: 本文テンプレートは `templates/bug.md`
- **機能要望**: 本文テンプレートは `templates/feature.md`

作成した URL を記録して次項目へ。

## フェーズ3: 完了報告

サマリーを提示:

- 全項目の一覧（タイトル + URL + ステータス: 作成 / コメント追記 / スキップ / 失敗）
- 失敗があれば理由と再開方法
- 次に取れるアクションの案内:
  - バグ深掘り → `/bug-fix #N`
  - 機能要望を仕様化 → `/spec-gen`（該当 Issue 番号を伝える）

## タイトル・ラベル統一ルール

### タイトル形式

- **バグ**: `[Bug] <機能>: <症状>`
  - 例: `[Bug] ログイン: 正しいパスワードでも認証に失敗する`
- **機能要望**: `feat: <概要>`
  - 例: `feat: Slack 通知チャンネルを追加できるようにする`

### ラベル

**バグ**（3 種以上を付与）:

1. `bug` — 固定
2. `severity:<level>` — `critical` / `high` / `medium` / `low`
3. `area:<領域>` — ユーザーが領域ラベルを指定した場合のみ。kebab-case 英小文字

**機能要望**（2 種以上を付与）:

1. `enhancement` — 固定
2. `priority:<level>` — `high` / `medium` / `low`
3. `area:<領域>` — ユーザーが領域ラベルを指定した場合のみ

## エラー時

- 当該項目で停止し、`TaskUpdate` でタスクの状態を明示
- 完了済み項目はそのまま残す
- ユーザーに `項目 N で失敗 / 完了: 1..N-1 / 未着手: N+1..` を報告し、再開可否を確認

## ルール

- 質問は必ず `AskUserQuestion` を使い、1 回 4 問以内
- コード調査はしない（純粋な起票ツール）。バグの原因推定は書かない
- `bug-report` / `design-request` / `spec-gen` の重量級ヒアリングは繰り返さない
- 未存在ラベルはユーザー承認なしに作成しない
- 各 Issue は open のまま残す（後で `/impl #N` `/bug-fix #N` にそのまま渡せる）
- コミットメッセージは `<type>: <説明>` 形式（CLAUDE.md 準拠）
- `git commit` / `git push` で `--no-verify` を使わない
